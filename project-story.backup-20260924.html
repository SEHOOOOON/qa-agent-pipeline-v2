이 프로젝트의 질문

“그럴듯한 테스트”가 아니라, 근거를 확인할 수 있는 테스트를 만들려면?

01 / WHY

빠르게 만들기 전에,
무엇을 확인해야 할지부터 정했습니다.

요구사항이 바뀔 때마다 영향받는 테스트를 찾고, 절차와 기대결과를 수정해야 합니다. 이 작업을 AI에 맡기더라도 요구하지 않은 기능을 추가하거나, 기대값을 잘못 해석한 테스트가 실행되면 결과를 믿기 어렵습니다.

예를 들어, “풍량을 중풍으로 변경해 주세요.”

버튼을 누르는 것만으로 검증이 끝날까요?
요구사항에 따라 장비 카드의 ‘중풍’ 표시와 내부 설정값을 확인하고, 시험이 끝나면 원래 상태로 돌려야 합니다.

AI가 맡는 일

분석 · 테스트 설계 · 자동화 계획

변경 내용을 정리하고, 확인할 조작과 기대결과를 구조화된 초안으로 작성합니다.

시스템과 사람이 맡는 일

검사 · 실제 실행 · 공식 등록 판단

초안을 검사하고 실제 결과를 기록합니다. 제품 기준과 공식 테스트를 바꾸는 최종 결정은 사람이 합니다.

02 / THE PROCESS

요청 하나가, 네 단계를 거칩니다.

입력은 변경 요청·기존 요구사항 명세서(SRS)·기존 테스트케이스(TC)입니다. 앞 단계의 결과를 그대로 믿지 않고, 단계마다 검사한 결과만 다음 단계로 전달합니다.

자동 검사 통과는 다음 단계로 진행할 조건입니다. 사람의 최종 승인과는 다릅니다.

03 / SOURCE OF TRUTH

실행 화면을 ‘정답’으로 삼지 않습니다.

요구사항은 어떻게 동작해야 하는지를 정합니다. 화면과 내부 상태는 실제로 어떻게 동작했는지를 보여줍니다. 둘이 다르면 기대값을 고쳐 통과시키는 것이 아니라, 차이를 결과로 남깁니다.

자료이 프로젝트에서 쓰는 목적
변경 요청 + SRS시험 범위와 기대결과의 근거
기존 TC이미 확인할 수 있는 범위와 재사용 여부 판단
화면 요소 관찰어떤 조작·확인을 자동화할 수 있는지 조사
실제 시험 기록기대값과 실제 관찰값 비교, 실패·복원 결과 확인

요구사항에 알림이나 색상이 없다면 임의로 추가하지 않습니다. 명시된 기능이 화면에 없다면 요구사항을 삭제하지 않고, 현재 자동화 지원 범위와 구분해 기록합니다.

04 / A REAL TEST CASE

“중풍으로 변경”을,
조작과 기대결과로 나누면.

대상과 순서뿐 아니라 무엇을, 언제 확인할지까지 연결합니다. 아래는 실제 사람이 승인한 TC-V2-002를 읽기 쉽게 정리한 예시입니다.

중풍 적용 후 표시와 내부 설정 확인

공식 등록된 TC

시험 전: 오류·잠금이 없는 단일 장비이며, 초기 풍량 LOW를 확인합니다.

조작 순서

  1. 대상 장비 카드를 선택합니다.
  2. 풍량을 MED(중풍)로 선택합니다.
  3. 선택한 풍량을 대상 장비에 적용합니다.

3번 적용 직후 확인

  • 장비 카드에 ‘중풍’이 표시됩니다.
  • 내부 풍량 설정 fanSpeed가 MED입니다.
시험 후 복원 · LOW로 다시 적용하고, 장비 카드와 내부 풍량이 초기 상태로 돌아왔는지 확인합니다.
상세 TC 원문과 추적 정보 보기

연결 요구사항: REQ-FAN-001
공식 TC: TC-V2-002 · 원본 후보: TC-CAND-001

위 절차는 당시 승인된 기록입니다. 최신 생성 지침의 모든 변형을 대표하는 정답지로 사용하지는 않습니다.

사전조건·단계별 기대결과·복원 원문 ↗

이미 같은 TC가 있다면?

변경 조건을 기존 테스트가 확인할 수 있는지 먼저 비교합니다. 충분히 확인할 수 있다면 새 TC를 중복 생성하지 않고 기존 TC를 실행합니다.

코드는 누가 만드나요?

AI는 조작·검증 계획을 작성합니다. 허용된 계획을 프로그램이 Playwright Python 코드로 변환합니다. 생성된 코드는 실행 전 검사합니다.

05 / WHEN TO CONTINUE — OR STOP

모든 요청을 억지로 통과시키지 않습니다.

“수정할 수 있는 초안 오류”와 “사람에게 물어야 하는 조건”은 다릅니다. 같은 실패 처리로 묶지 않고, 이유에 따라 다음 행동을 정합니다.

다음 단계 진행

필수 조건과 자동 검사를 충족한 범위를 전달합니다.예: 중풍 표시·내부 설정값을 확인할 근거가 있음

제한된 재작성

확인된 오류를 AI에 돌려보내고 다시 검사합니다. 단계별 자동 재작성은 최대 1회입니다.기대값을 바꾸거나 검사를 삭제해 통과시키지는 않음

부분 진행·확인

분리 가능한 미정 조건은 제외 사유로 보고하고, 확정 범위만 시험합니다. 핵심 범위가 불명확하거나 모델 검토가 불확실하면 자동 인계를 멈춥니다.예: 동작 조건은 확정됐지만 알림 색상은 미정

중단·제외

오류가 남거나 근거·실행 환경을 확인할 수 없으면 진행하지 않습니다. 지원하지 않는 조작은 제외 사유를 남깁니다.자동화 미지원은 제품 결함이나 시험 성공이 아님

검사 기준은 얼마나 엄격한가요?

단어나 문장 표현이 다르다는 이유만으로 거부하는 규칙은 줄였습니다. 대신 ID·명시된 값·범위·출처 연결과 실제 실행 조건은 유지했습니다.

자연어의 의미와 계획의 검사 연결은 별도 모델이 검토합니다. 모델도 오판할 수 있으므로 인용의 존재·검토 대상 누락·입력 일치 여부를 코드로 확인합니다. 이것이 의미 정확성을 보장하지는 않습니다.

06 / EXECUTION & RECOVERY

통과 여부만큼,
다음 시험에 남긴 상태도 확인합니다.

앞선 시험이 바꾼 값 때문에 다음 시험의 결과가 달라질 수 있습니다. 그래서 TC 유형에 맞게 복원 계획과 확인 방법을 연결합니다.

값을 변경하는 시험

시험 전 기준 상태로 복원하고 실제 값을 확인합니다.

조회만 하는 시험

값을 바꾸지 않으므로 복원은 불필요합니다.

변경을 차단하는 시험

상태가 그대로인지 확인합니다. 실제로 변경됐다면 복원합니다.

복원에 실패한 경우

실패를 기록하고 같은 환경의 후속 시험을 계속하지 않습니다.

화면 캡처·로그·Trace를 근거로 남깁니다. 임시 실행 폴더는 원본과 분리된 작업 공간이며, OS 권한을 격리하는 보안 샌드박스는 아닙니다.

07 / EVIDENCE

성공만 보여주면,
이 프로세스의 절반만 보입니다.

정상 변경, 실제 불일치, 정보 부족은 서로 다른 결과로 남아야 합니다. 아래는 저장된 공개 실행 기록이며, 최신 모델 근거 검토를 도입하기 전 사례입니다.

01 · 정상 변경

중풍 표시와 내부 값 일치

새 중풍 후보와 기존 강풍 TC를 함께 검증했습니다. 환경 점검 결과는 제품 TC와 따로 집계했습니다.

신규 후보 + 기존 TC 재사용의 연결 확인

잠금됐지만 버튼은 활성

내부 잠금값은 맞았지만 온도 버튼의 비활성 기대와 실제 화면이 달랐습니다.

기대값 변경 없이 차이를 보고 · 결함 확정은 별도 판단

08 / HUMAN DECISION

PASS했다고,
제품 기준이 저절로 바뀌지는 않습니다.

Agent 4는 규칙 기반 분석기입니다. 제품 불일치 후보, 자동화·환경 문제, 판정 근거 부족, 미실행을 구분하고 보고 내용을 대조합니다. 최종 검토에서는 실행 근거와 SRS 개정안, 공식 TC로 남길 내용을 사람이 확인합니다.

보류

이유와 추가 확인할 내용을 기록합니다. 기존 SRS와 공식 TC는 바꾸지 않습니다.

승인

SRS 개정에 별도 동의하고, 검증된 후보 TC·자동화 코드를 공식 자산으로 등록합니다. 이후 변경 요청에서 재사용할 수 있습니다.

등록 직전에는 무엇을 다시 확인하나요?

최종 결과·자동 검사·필수 실행 증거와 TC·코드·현재 제품 화면의 연결을 확인합니다. 제품 화면이 바뀌었다면 승인 전 재시험을 요구합니다.

기존 TC만으로 검증이 끝났다면 TC를 중복 등록하지 않고 SRS 개정만 승인할 수 있습니다. 검토서 작성만으로 공식 파일이 바뀌지는 않습니다.

Slack·Notion 보고는 기본적으로 전송 미리보기입니다. 실제 전송은 명시적인 요청이 있을 때 수행합니다.

09 / WHAT THIS PROVES

연결은 구현했습니다.
범용 품질을 증명한 것은 아닙니다.

확인한 것

요청 → 구조화된 분석·TC → 자동화 계획·실행 → 보고 → 사람 승인까지 이어지는 변경관리 흐름과 실행 근거를 연결했습니다.

현재 대상

가상 중앙제어 시스템의 기존 요구사항 변경(MODIFIED)입니다. 지원하는 화면 요소·조작·검증 계획 안에서 실행합니다.

아직 검증할 것

새 모델 근거 검토의 정확도·오탐, 다양한 요청과 반복 실행에서의 품질·비용 편차는 추가 평가가 필요합니다.

범위 밖

실제 장비 통신, 임의 웹사이트 자동화, 전체 회귀, 요구사항 추가·삭제, 완전한 자동 복구는 구현 완료로 소개하지 않습니다.

프로젝트 2는 이 흐름을 반복 실행하며 Agent별 결과가 기준을 지키는지 평가하는 별도 작업입니다. 자동 테스트 통과 수를 실제 모델의 정확도로 해석하지 않습니다.

  • 분기·검사·승인 계약전체 동작 기준을 확인할 때
  • 최신 실행 결과와 남은 문제현재 검증 상태를 확인할 때
  • 내부 자동 테스트 목록제품 TC와 구분한 코드 검증
  • 실행 방법과 저장소 구조직접 실행해 볼 때
