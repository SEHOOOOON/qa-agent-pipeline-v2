# QA Agent Pipeline V2

공통 AI 검토는 원문 ID로 근거를 선택합니다. 근거가 많아 응답 양식의 선택지 한도를 넘는 경우에는 입력 안의 번호로 선택하고 프로그램이 원래 ID·원문을 연결합니다. 근거·검토 항목을 줄이지 않으며, 번호표와 원문 해시·판정·누락 검사는 유지합니다. 과거 검토 기록에는 새 형식을 소급하지 않습니다.

Slack·Notion 보고에는 실행 결과뿐 아니라 검토 실패로 실행하지 못한 TC와 사유도 포함합니다. 미실행은 제품 Fail이 아니며 Notion에서는 Review Needed로 표시합니다. 실제 시험 중 발생한 자동화·환경 오류와 시간 초과는 미실행으로 바꾸지 않고 로그·복원 기록과 함께 보고합니다. 오류 결과를 보고하기 위해 자동 재시험하지 않습니다. 실제 전송은 `report --send`로 명시적으로 실행합니다.

새 Agent 2 작성·재작성과 검토, Agent 3 검토는 지원되는 관제점 복원 계획의 같은 기록 순서를 사용합니다. 원래값은 대상 선택 확인 후 첫 준비 변경 전에 저장합니다. 프로그램이 TC별 계획에서 확인한 선택·캡처 경계도 검토 자료에 연결합니다. 초기 UI 관찰의 다른 선택 장비는 복원 기준이 아닙니다. 이 설명은 실행 성공 증거가 아니며 대상·값·필수 검사·복원 검증을 대신하지 않습니다. 순서가 충돌하는 TC를 자동 수정하거나 과거 검토 자료에 소급 추가하지 않습니다.

새 Agent 2 응답은 SRS 개정안의 기존 인수 기준을 다시 작성하지 않습니다. AI는 대상 ID·변경안·근거를 작성하고, 프로그램이 해당 실행에 고정한 SRS 원문을 붙입니다. 모델 원응답과 원문 연결 내역은 별도 기록하며, 변경안 검토와 승인 시 원문 일치 검사는 유지합니다. 과거 저장 산출물 형식은 바꾸지 않습니다.

상태 변경 시험의 상세 복원 확인 기록은 제품 PASS 여부와 분리합니다. 본시험에 진입하고 복원 비교가 실제로 끝나 불일치가 없을 때 `RESTORE_CONFIRMATIONS_VERIFIED`를 남깁니다. 제품 불일치는 그대로 유지하며, 시험 전 중단·복원 미실행·비교 예외·복원 불일치에는 이 완료 기록을 남기지 않습니다. 과거 실행 로그는 소급 수정하지 않습니다.

검사는 대상·기대값·필수 확인·출처/인계·실행/복원 증거·사람 승인 보호를 위한 것입니다. 고정 비교값의 동일한 중복 표기는 허용하며, 값 충돌이나 검사 누락은 차단합니다.

새 실행에서는 제목·분류 이름·묶음 설명만으로 반려하지 않습니다. 실제 조작·값·확인 시점은 TC의 실행 정의를 기준으로 연결하고, 요청과 의미가 맞는지는 필수 검토에서 확인합니다. 검사 축소가 검토 생략이나 전체 실행 성공을 뜻하지 않습니다.

필수 화면·내부값 확인 외에 추가 화면 관찰이 있어도 허용합니다. 시점 검사는 전체 문장 목록의 일치가 아니라 같은 TEST 조작의 연결을 확인하며, 대상·기대값·필수 검사 누락은 별도 구조 검사와 의미 검토를 유지합니다. 새 모델 출력에서 공백만 다른 참조는 유일하게 대응하는 원문으로 연결하고 원본·변경 기록을 함께 보존합니다. 값이나 문장의 의미를 자동 수정하지 않습니다.

기존 요구사항 명세서(SRS)와 테스트케이스(TC)가 있는 가상 중앙제어 시스템에서, **새 변경 요청을 분석하고 시험한 뒤 사람이 테스트 자산을 승인하는 QA 파이프라인**입니다.

## 전체 흐름

| 단계 | 하는 일 | 결과물 |
|---|---|---|
| Agent 1 · 요구사항 분석 | 변경 요청과 SRS를 비교하고 시험할 범위·미정 조건을 정리 | 요구사항 분석 |
| Agent 2 · 테스트 설계 | 기존 TC로 확인할 수 있는지 비교하고 부족한 시험을 설계 | 사용할 기존 TC와 새 상세 TC |
| Agent 3 · 자동화·실행 | TC를 바탕으로 자동화 코드를 만들고 실제 화면에서 시험·복원 | 코드와 실행 증거 |
| Agent 4 · 결과 분석 | 실행 결과와 미실행 사유를 분류해 보고 | 최종 보고서와 사람 검토 자료 |
| 사람 · 최종 판단 | 결과와 기존 TC를 비교하고 SRS 개정·TC 추가/대체 여부를 결정 | 승인·미등록·보류 기록 |

관련 기존 TC는 이름이 비슷해서가 아니라 **요청과 실제 검증 범위가 관련될 때** 선택합니다. 기존 TC로 충분하면 새 TC를 중복 생성하지 않습니다. PASS는 실행 결과이며 공식 등록 승인이 아닙니다.

승인 화면은 단일 TC의 단계별 실행과 여러 후보의 통합 실행 모두에서, 검증 기록이 가리키는 TC·코드·증거를 읽습니다. 저장 위치가 달라도 인계·해시·실행 증거 확인과 사람 승인 기준은 같습니다.

최종 실행은 신규 후보가 없거나 모두 실행 제외된 경우에도 먼저 Agent 1→2의 인계·Checkpoint·해시를 확인합니다. 기존 TC 선택에는 이 검증을 통과한 설계만 사용하며, 자료가 바뀌거나 빠지면 제품 시험 전에 중단합니다.

통합 실행의 A3 요약은 작성 시 저장한 해시와 대조한 뒤 집계합니다. 실행·제외 항목이 삭제되거나 요약 파일이 사라지면 단일 TC 결과로 대체하지 않습니다. 과거 단일 CLI와 수동 요약은 기존 인계 검증을 유지합니다.

베이직 TC는 기존 Python 검사를 유지하면서 준비·조작·기대결과의 상세 명세를 실행 당시 카탈로그에 저장합니다. 새 복원 계약을 사용하는 실행은 준비 전 전체 장비 상태와 화면을 기록하고 시험 후 복구·비교합니다. 가상 시스템의 저장 상태 복구 방식이며 제품 조작 시험과 구분합니다. 복원 실패는 실행 오류로 기록하고 해당 환경을 폐기합니다. 과거 계약·실행 기록에는 새 검사를 소급하지 않습니다.

## AI와 프로그램의 역할

- Agent 1·2는 OpenAI API로 요구사항을 분석하고 TC를 작성합니다.
- Agent 1의 조건과 SRS 연결은 한 번 작성하고, 프로그램이 영향 분석의 연결 목록을 계산해 다음 단계에 전달합니다. 기존 기능을 확인하는 요청의 인용에는 준비 상태와 실제 요청 조건을 함께 담을 수 있지만, 준비 상태만으로 새 검사를 추가할 수는 없습니다. 원문에 맞는 연결인지는 별도 의미 검토에서 확인합니다.
- 새 TC의 복원 확인은 나눠 쓰거나 묶어 쓸 수 있습니다. 프로그램은 연결이 완전한 경우 같은 확인 문장을 묶고 비교 목록을 ID에 맞춰 정렬합니다. 모든 확인 대상·비교 기준·복원 조작은 보존하며 모델 원본과 정리 내역을 별도 저장합니다. 누락·중복 ID·잘못된 기준을 자동 보정하지 않습니다.
- Agent 3는 새 TC의 시험 내용을 이어받아 코드를 생성·실행합니다. 시험할 값이나 기대결과를 새로 정하지 않습니다.
- 작성 AI에는 실제 연결 가능한 온도 버튼/표시를, 검토 AI에는 카드 문구와 내부 코드 형식 간의 DOM 읽기 방식을 제공합니다. 검토할 항목을 줄이거나 화면 관찰을 내부값으로 대신하지 않습니다. 상세 연결과 과거 입력 호환은 프로젝트 안내를 따릅니다.
- 별도 모델 검토와 코드 검사는 원문 근거·필수 확인·단계 간 전달을 점검합니다. 새 Agent 2 검토는 TC를 개별 문장으로 반복 심사하지 않고 TC 전체·조건별 충족·전체 절차를 대조합니다. 참고 설명만으로 반려하지 않지만 실제 누락·값/대상/시점 충돌은 계속 검토합니다. 모델의 오판 가능성은 남습니다.
- Agent 4는 생성형 AI가 아닌 규칙 기반 분석기입니다. 사람의 최종 승인도 자동화하지 않습니다.

새 A2 검토 입력은 동일한 TC 본문을 한 번 제공하고 조건별 검토에서 참조합니다. 요구조건별 누락 검토·TC 전체 검토·원문 출처는 유지합니다. 요청/SRS의 제품 기준, 프로그램의 실행 방식, 실제 실행 증거를 구분해 전달하며 자료 축소를 AI 판단 품질 향상으로 간주하지 않습니다. 새 카드 잠금 읽기는 상태 클래스와 아이콘이 다르면 판독 불일치로 남겨 잠금 해제 시험이 잘못 통과하지 않도록 합니다. 과거 입력·코드·판정은 당시 계약으로 재검증합니다.

새로 생성한 자동화는 본시험에서 실제 읽은 값과 검사 번호·계획상 대상·기대값·연결 시점을 stdout에 구조화해 남깁니다. P2는 이 기록을 계획과 로컬 대조하며, 코드 생성기의 정확성은 별도 회귀검사로 확인합니다. 이 기록은 독립 센서나 모델 정확도 증명이 아니며 과거 코드를 소급 변경하지 않습니다.

새 자동화와 P2의 값 비교는 참/거짓과 숫자를 구분합니다. 예를 들어 `true`와 `1`은 다르고, 온도 `21`과 `21.0`은 같습니다. 과거 승인 코드와 실행 결과는 당시 기준으로 보존합니다.

V1은 고정 산출물로 흐름을 보여준 **Fixture 기반 Workflow Prototype**입니다. V2는 실제 모델 생성과 제품 시험을 연결합니다. 내부 구현과 과거 TC 호환 방식은 [프로젝트 안내](docs/PROJECT_GUIDE.md)에 설명합니다.

## 진행·중단·승인 기준

Windows에서는 실행 산출물과 임시 파일이 긴 경로 제한에 걸리지 않도록 시작 전에 검사합니다. 안내가 나오면 `--runs-root runs`처럼 짧은 출력 위치를 사용하세요. 기존 Run을 자동 이동하거나 덮어쓰지는 않습니다.

- 근거가 부족한 AI 초안은 정해진 한도 안에서 재작성합니다. 모든 오류를 자동으로 고치지는 않습니다.
- 단계별 Agent 2 실행에서 `--no-rewrite`를 지정하면 반려된 초안·검토·Checkpoint를 저장하고 추가 재작성 없이 종료합니다. 이는 정상 통과나 제품 FAIL이 아니며, 기존 기본 재작성 정책은 그대로입니다.
- 필요한 조건이 미정이면 사람 확인으로 남깁니다. 핵심 조건이 미정인 대기 상태에서는 정보 부족과 질문으로 보존하며 제외 범위로 돌리지 않습니다. 확정 범위와 분리해 부분 진행할 때만 미정 범위를 제외 목록에도 남깁니다. 없는 기능의 시험도 설계할 수 있지만, 실행 수단이 없으면 미실행 사유를 기록합니다.
- Agent 1이 유효한 확인 질문을 남기고 중단하면 로컬 화면에 ‘사용자 확인 대기’와 질문 원문을 표시합니다. 실행 오류나 완료로 표시하지 않으며, 자동으로 답을 추정하거나 다음 단계로 진행하지 않습니다.
- 내부 오류는 이후 후보의 추가 호출을 중단합니다. 복원 실패 시 같은 환경에서 후속 시험을 계속하지 않습니다. 자동화 지원 부족과 실제 제품의 기대결과 불일치는 구분합니다.
- 값을 변경하는 시험은 준비 전 상태를 기록하고 복원·확인합니다. 조회만 하는 시험에는 불필요한 복원을 요구하지 않습니다.
- 온도 조절 중 같은 표시값을 오가면 반복을 중단하고 실행 오류를 남깁니다. 요청값을 반올림하지 않으며, 상한/하한에서 멈추는 시험은 원래 TC의 기대결과로 판단합니다.
- 처음 수집한 화면의 비활성 상태만으로 준비 후 조작을 반려하지 않습니다. 버튼의 존재·종류는 미리 확인하고, 실제 조작 가능 여부는 실행 시 검사합니다. 실행 불가를 성공으로 건너뛰지 않습니다.
- SRS 개정과 공식 TC 등록은 사람의 동의를 받아 반영합니다. 보고서를 작성하거나 PASS가 나온 것만으로 기존 자산이 바뀌지는 않습니다.
- SRS 수정안은 요청한 부분만 변경하되, 승인 시 인수 기준 셀 전체를 교체하므로 바뀌지 않는 기존 기준도 완성 문장에 보존합니다. 그 기준을 보존하는 것과 모든 기능을 이번에 시험하는 것은 다릅니다.
- 기존 승인 TC를 명시적인 요청으로 보완한 버전은 `approved_assets/revisions/`에 두고 현재 카탈로그에서 참조합니다. 최초 승인과 유지보수 검증은 구분하며 이전 파일과 실행 결과는 보존합니다.
- 후보 승인 화면에서 이번 TC와 기존 기본·승인 TC를 비교하고 추가·선택한 TC 대체·미등록·보류를 결정합니다. 요구사항 연결은 목록 정렬 근거이지 중복 판정이 아닙니다. 대체 기록을 남기고 이후 실행 목록에서 제외하며 원본 파일·과거 실행 기록은 보존합니다.

## 구현 범위와 증거 읽는 법

현재 대상은 가상 중앙제어의 전원·모드·풍량·온도·잠금과 MODIFIED 요청입니다. 실제 장비 통신, 임의 웹사이트, 전체 회귀, ADDED·DELETED 요청 처리를 구현 완료로 소개하지 않습니다.

**구현된 기능, 과거 시연, 최신 실제 실행은 서로 구분합니다.** 개별 정상 실행이 성공해도 기존 TC 재사용·SRS 개정·공식 등록까지 모두 검증한 것은 아닙니다. 로컬 테스트 통과는 실제 모델의 정확도나 반복 안정성을 대신하지 않습니다.

- [현재 상태와 다음 작업](PROJECT_HANDOFF.md): 최신 실행 결과, 검증 범위, 남은 과제
- [프로젝트 안내](docs/PROJECT_GUIDE.md): 단계별 계약, 검사·중단·복원·승인 기준
- [의사결정 기록](DECISION_LOG.md): 보완 이유와 과거 변경 이력
- [제품 SRS](docs/01_PRODUCT_SRS.md) · [자동 테스트 목록](docs/07_TEST_CATALOG.md): 제품 기준과 내부 코드 검증

과거 설명·실행 이력은 [archive/](archive/README.md)에 모았습니다. 현재 설명은 위 문서를 먼저 읽고, 과거 판단·실패 경과가 필요할 때만 보관 자료를 참고하세요.

## 실행 방법

### 로컬 실행 준비

저장소 루트에서 실행하는 개발 환경을 지원합니다. 아래 `-e`는 소스를 복사하지 않고 이 저장소에 연결하므로 UI가 제품 HTML·SRS·실행 기록을 같은 위치에서 찾습니다. 독립 설치형 배포는 지원하지 않습니다. 저장소를 이동했다면 같은 환경에서 다시 등록하세요.

Python 3.10 이상이 필요합니다. OpenAI API 키는 실행 환경의 `OPENAI_API_KEY`에 설정합니다. 실제 모델 호출에는 비용이 발생합니다. 기본 모델은 `gpt-6.1-sol / medium`입니다. 명시한 `--model`과 `OPENAI_MODEL`이 기본값보다 우선합니다. 과거 Terra 실행 기록은 당시 모델과 판정 그대로 보존하며, 모델 변경만으로 정확성 향상을 보장하지 않습니다.

```powershell
python -m pip install -e ".[agent3,test]"
python -m playwright install chromium

# 현재 저장소의 코드로 저장된 실제 Run 조회
python src/qa_pipeline_ui.py

# 새 API 실행과 사람 승인 기능 활성화
python src/qa_pipeline_ui.py --allow-live-run --allow-asset-approval
```

브라우저에서 `http://127.0.0.1:8765/`에 접속합니다. 새로 복제한 저장소에는 로컬 실행 기록이 없어 조회 목록이 비어 있을 수 있습니다. `pytest-playwright`는 agent3 설치 옵션에 포함됩니다. 실제 실행·승인 요청은 같은 로컬 페이지의 JSON 요청만 허용합니다.

여러 작업 폴더가 있다면 반드시 실행할 저장소 루트에서 위 명령을 사용하세요. `python -m qa_pipeline_ui`는 Python에 설치 연결된 다른 폴더를 읽을 수 있습니다. 위의 소스 파일 직접 실행은 현재 폴더의 코드를 사용하며, 실제 API 호출이나 승인 권한을 추가로 부여하지 않습니다. 설치형 명령을 사용하려면 `python -c "import qa_pipeline_v2; print(qa_pipeline_v2.__file__)"`로 현재 저장소의 `src`인지 먼저 확인하세요.

HTML을 직접 열거나 공개 웹 주소에 접속하면 MED 풍량 정상 변경의 저장된 데모가 표시됩니다. 데모 승인은 화면 시연이며 파일에 반영되지 않습니다. 실제 시험은 로컬 서버가 별도 브라우저에서 수행하고, 관제 화면에는 실행 상태와 결과가 표시됩니다.

포폴의 저장 데모 링크는 `product_baseline/virtual-controller.html?mode=demo`를 사용합니다. 단순 로컬 정적 서버에서도 실행 서버 없이 열 수 있습니다. `mode=live`의 연결 오류를 데모 성공으로 대체하지 않습니다. 중앙제어 조작 화면은 PC용이며, 모바일에서는 포폴의 요약 영상을 이용하세요.

CLI에서는 현재 SRS와 비교할 변경 요청 JSON을 준비한 뒤 다음 순서로 실행합니다. 아래 `변경요청.json`은 실제 파일 경로로 바꿉니다. [요청·실행 증거 목록](examples/README.md)의 HIGH·MED 요청은 과거 시연 자료이며, 이미 등록된 내용을 신규 등록하는 예시로 사용하지 않습니다.

```powershell
python src/qa_pipeline_v2.py pipeline --request "변경요청.json" --target-html "product_baseline/virtual-controller.html"
python src/qa_pipeline_v2.py execute --run-id "RUN-..." --target-html "product_baseline/virtual-controller.html"
python src/qa_pipeline_v2.py agent4 --run-id "RUN-..."
```

`pipeline`은 Agent 1~3, `execute`는 완료 후보 확인·관련 기존 회귀, `agent4`는 분류·최종 보고를 담당합니다. 후자의 두 명령은 모델을 호출하지 않습니다. Slack·Notion은 기본 미리보기이며 CLI에서 `--send`를 명시할 때 실제 전송합니다. 화면에서 시작한 실행은 외부 보고 미리보기까지 진행합니다.

Notion은 실행 후 TC 제목·결과·분류 요약과 함께, 검증된 설계의 사전조건·단계별 조작과 기대결과·복원을 해당 실행 페이지 본문에 연결합니다. 같은 내용의 재전송은 중복 추가하지 않고 수동 메모는 보존합니다. 과거 TC에 단계 연결 정보가 없으면 임의로 보충하지 않습니다. Agent 2 초안만 별도 게시하는 기능은 없으며, 로컬 미리보기·자동 테스트와 실제 Notion 게시 확인은 구분합니다.

## 로컬 검증

TC 작성·검토·재작성에는 사용자의 판단과 이유를 정리한 동일 참고 사례를 제공합니다. 현재 요청/SRS가 우선이며 예시의 온도·장비를 정답으로 복사하지 않습니다. [판단 기록](examples/reviewer_reference_decisions_20261010.json)에서 직접 답변·후속 설명을 적용한 판단·미확정 항목을 구분합니다. 참고 사례를 보고 맞힌 결과는 독립 평가 성적으로 계산하지 않습니다. 과거 실행에는 당시 지침을 유지합니다.

CLI의 `agent4 --send` 또는 `report --send`는 V2 소스 저장소 루트의 `.env`를 읽습니다. 필요한 설정은 `SLACK_WEBHOOK_URL`, `NOTION_API_KEY`, `NOTION_DATA_SOURCE_ID`이며 기존 환경변수를 덮어쓰지 않습니다. 다른 작업 폴더의 파일은 `--env-file "설정파일경로"`로 지정합니다. V1 파일을 자동 검색하거나 복사하지 않습니다.

미리보기·일반 import·UI 기본 실행은 이 파일을 자동 로드하거나 전송하지 않습니다. OpenAI 호출 설정은 기존대로입니다. 오프라인 도구는 `PYTHON_DOTENV_DISABLED=1`로 로딩을 막습니다. 함수 직접 호출은 호출자가 환경변수를 준비합니다. 실제 전송은 별도 승인 후 수행하며 `.env`는 Git에 추가하지 않습니다.

```powershell
python scripts/verify_offline.py
python -m pytest --collect-only -q
git diff --check
```

`verify_offline.py`는 서비스 키를 제거하고 Python의 외부 연결과 테스트 브라우저의 외부 리소스를 차단한 상태에서 회귀검사를 수행합니다. `--focus`는 일부 역할 검사만 선택합니다. OS 수준 네트워크 격리나 실제 모델 평가 도구는 아닙니다.
