# QA Agent Pipeline V2

기존 SRS와 테스트케이스(TC)가 있는 가상 중앙제어 시스템에서, 변경 요구사항을 분석하고 변경분을 시험한 뒤 사람이 재사용할 테스트 자산을 승인하는 프로젝트입니다.

V1의 QA 기준과 4-Agent 흐름에 실제 모델 호출·자동화 후보 생성·실행 증거를 연결한 MVP입니다.

새 검증 실행은 Agent 1이 남긴 사용자 질문을 해시 검증 후 최종 확인 사항으로 전달합니다. 질문의 답이나 미정 기대값을 자동 생성하지 않으며, 과거 보고서는 소급 수정하지 않습니다.

SRS 개정과 테스트 필요 여부는 구분합니다. 새 Agent 2 실행에서는 요청의 변경 후 문장 전체가 대상 SRS 인수 기준과 앞뒤 공백을 제외하고 같으면 개정안을 요구하지 않습니다. 기존 TC 대조·필요한 시험은 계속하며, 같은 문장을 수정안으로 제출하면 반려합니다. 부분 일치·비슷한 표현·기존 TC 재사용만으로 개정을 생략하지 않고, 실제 변경안은 계속 사람의 승인을 받아야 합니다.

기존 TC를 선택한 것과 특정 조건의 검증 근거로 연결한 것은 구분합니다. 복합 조건을 여러 TC가 나누어 확인하면 각각에 같은 조건 ID를 연결하도록 안내합니다. Agent 2 입력에는 조건별 코드·수치와 재작성 시 현재 연결·미충족 값을 함께 제공합니다. 제한된 진단 자료이며 자동 연결·의미 합격 판정은 아닙니다. 명시 값과 출처 연결은 대조하지만, 단어 조합만으로 반대 동작 여부를 확정하지 않습니다.

[V2 포트폴리오 페이지](https://sehooooon.github.io/qa-agent-pipeline-v2/project.html)는 소개·QA 기준·실행 흐름·사례·승인·설계 경험을 세로 스크롤로 읽는 정적 소개 페이지입니다. [페이지 원본](project.html)에 실제 저장 기록·사용자 승인에 따른 등록 장면의 90초 편집본을 연결했습니다. 새 모델 실행 전 과정의 실시간 녹화가 아니며, 페이지를 여는 것만으로 API 호출이나 자산 승인을 수행하지 않습니다. 공개 반영 여부는 인계 문서에서 구분합니다.

```text
변경 요청 → Agent 1 요구사항 분석 → Agent 2 기존 TC 대조·변경분 설계
         → Agent 3 자동화 계획·코드 생성·시험 → 관련 기존 TC 실행
         → Agent 4 결과 분류·보고 → 사람의 SRS·공식 TC 승인
```

## V1과 달라진 부분

| 영역 | V1 | V2 |
|---|---|---|
| QA 기준 | 3단계 기준·추적성·독립성·UI/내부 상태 이중 검증 | 유지 |
| Agent 1·2 | 고정 산출물 시연 | 실제 OpenAI API로 분석·TC 생성 |
| Agent 3 | 사람이 작성한 기존 자동화 실행 | AI가 계획 작성, 허용 목록 컴파일러가 Python 생성·시험 |
| Agent 4 | 규칙 기반 분류·Slack/Notion 보고 | 유지하며 인계·증거·집계 확인 추가 |
| 최종 판단 | 시연 중심 | 사람이 SRS 개정·공식 TC 등록 승인 |

V1은 Fixture 기반 Workflow Prototype입니다. V2에서도 Agent 4는 규칙 기반 분석기이며, Checkpoint 통과와 사람의 공식 승인은 별개입니다.

현재 범위는 MODIFIED 요청, 중앙 관제 패널, 변경분 후보와 관련 기존 TC 실행입니다. ADDED·DELETED, 전체 회귀, 실제 장비 통신, 모든 UI 기술 지원과 무제한 자동 수정은 포함하지 않습니다. 반복 평가는 별도 프로젝트 2에서 다룹니다.

검사 범위는 요청과 연결해 결정합니다. SRS에 있다는 이유만으로 관련 기능 검사를 추가하지 않습니다. 새 실행의 CP1은 연관 검사 근거 누락을 재작성 대상으로 처리하고, 요청 밖 간접 영향이나 직접 대조할 수 없는 범위는 입력 보완 전까지 인계를 보류합니다. 자연어 영향 판단을 모두 자동 검증하는 기능은 아닙니다.

새 실행은 단어로 시험 제외·준비·복원을 추정하지 않습니다. 요청의 `out_of_scope`는 그대로 보존하고, Agent 1은 시험 절차 원문을 `procedure_notes`에 명시합니다. CP1은 입력 원문 존재·누락·중복 분류를, CP2는 절차 인계를 검사합니다. 분류 자체의 의미 정확성을 증명하지는 않습니다. 설명에만 있는 기존 온도 범위는 동일 대상 SRS의 전체 원문·유지 조건이 정확히 연결된 경우만 인정하며 변경 후 정책의 범위를 대신할 수 없습니다.

사용자가 `[준비]`·`[복원]`·`[시험 절차 메모]`로 표시한 원문은 절차 목록에 보존해야 합니다. 동일 원문이 요청의 `out_of_scope`에도 명시되어 있으면 제외를 우선합니다. 수행할 절차를 제품 기대조건·제외·정보 부족에 중복 기록하면 차단하지만, 절차 본문의 동의어나 문체는 판정하지 않습니다. 새 Agent 2 실행은 이 분류가 검증된 새 Agent 1 결과를 사용합니다. 과거 결과는 조회·재검증할 수 있으나 새 Agent 2를 이어 실행하려면 같은 요청으로 새 Agent 1 Run부터 시작해야 합니다. 이전 절차 필드의 부재를 ‘절차 없음’으로 취급하지 않습니다.

새 실행은 분석·설계 문장의 상태 단어와 경계 표현을 조합해 의미를 판정하지 않습니다. 입력 전후 값·실제 출처·ID·명시 코드와 수치 근거는 계속 대조합니다. 같은 숫자를 사용한 잘못된 해석은 놓칠 수 있으며, CP 통과나 제품 시험 PASS를 요구사항 해석의 정확성으로 설명하지 않습니다. 정보 부족·검사 범위 보류, 사람의 최종 판단과 별도 프로젝트 2 평가가 필요합니다.

이미 요청한 검사에 관련 SRS 근거만 연결할 때는 새 검사와 구분합니다. 요청 출처와 조건 ID는 보존하지만 분석 설명·TC 기대결과의 문장 전체가 원문과 같아야 통과하는 규칙은 새 실행에서 사용하지 않습니다. 관련 요구사항 이름만으로 알림·다른 상태 확인을 추가하거나 SRS 개정을 허용하는 것은 아닙니다. 근거 연결은 관련 SRS 전체를 시험했다는 의미가 아닙니다.

새 TC 초안은 사전조건·대상 선택·값 입력/선택·적용·복원을 기능에 맞게 구분합니다. 제품 기대결과에는 확인 대상과 연결된 조작 단계를 명시하고, 자동화도 그 단계 직후 판정하도록 검사합니다. 과거 TC와 공식 자산은 새 형식으로 자동 덮어쓰지 않습니다.

새 자동화 계획은 온도·모드 시험을 포함해 TC의 조작·중간 초기화 순서를 대조하고, 표시값의 단어 일부만 잘라 검사하는 계획을 차단합니다. 공식 등록 전 재시험은 제품 HTML과 후보 코드가 시험 전후 동일할 때만 유효한 기록으로 남깁니다. 이 규칙은 명시적 오류를 찾는 제한 검사이며 모든 자연어 의미를 검증하지는 않습니다.

작성 지침에는 풍량·온도·읽기 전용 상세 예시를 유지합니다. 특정 조작 문구·대상 이름의 반복 여부는 새 실행의 차단 기준이 아닙니다. 확인 대상·유일한 판정 단계·조건 연결과 구조화 복원은 필수이며 실제 자동화와 연결돼야 합니다. 자연어 품질 전체나 매번 동일한 상세 수준을 보장하지 않습니다.

새 TC는 상세 복원 설명과 별도로 `restoration`에 복원 조작 목록·확인 대상 ER ID·비교 기준·확인 시점을 담습니다. Agent 2의 CP2-023과 Agent 3는 같은 구조화 계약을 검사합니다. Agent 3는 확인 문장을 다시 해석하지 않고 승인된 연결을 그대로 받으며, 기존 ER의 동일한 읽기 위치에서 준비 전 실제 관찰값과 복원 후 값을 비교합니다. 누락·중복·기준 변경·읽기 구현 부재는 계속 차단합니다.

새 복원 비교는 `OBSERVED_BASELINE`과 `AFTER_RESTORE`로 한정합니다. 화면·내부값 각각의 실제 관찰 상태가 기준이며 내부 코드로 화면 초기 표시를 추정하지 않습니다. 복원 설명은 보존하지만 문장의 허용 단어 목록으로 통과 여부를 결정하지 않습니다. 실행 의미는 구조화 필드가 기준이며 설명 문장 전체의 의미 일치를 자동 증명하지는 않습니다. 복원 조작의 허용 목록·근거 검사, 제품 기대결과와 사전조건 검사는 유지합니다. 과거 계약은 당시 규칙으로 읽고 기존 공식 TC는 자동 변환하지 않습니다.

Agent 3 입력에는 사전조건 문장별로 현재 검사기가 허용하는 기본 확인 항목도 전달합니다. 화면 관찰 목록 전체를 새 검사 범위로 오해하지 않도록 돕는 안내이며, 초기값 같은 조건은 별도 읽기 근거가 필요합니다. 재작성 때는 지적된 항목만 수정하도록 안내하고, 최종 계획과 실제 값은 기존 검사로 다시 확인합니다. 안내만으로 모델의 오류가 방지됐다고 간주하지 않습니다.

## 새 TC의 상태 복원 기준

Agent 1은 인수 조건 원문을 제품 조건·절차·제외·정보 부족으로 전달하고 검사기는 원문 연결과 기록 누락을 확인합니다. Agent 2의 대상·판정 시점 연결 검사는 재작성 진단에도 같은 함수를 사용합니다. 새 복원 확인은 구조화 계약을 전달합니다. 과거 계약의 문장 검사는 과거 증거 재검증용으로만 유지합니다. 새 CLI 최초·재작성·후속 검증은 Manifest의 `wording_policy=STRUCTURAL_ONLY_V1`을 사용합니다. 내부 평가 함수의 기본값은 과거 호출 호환용이므로 새 정책을 직접 시험할 때는 `legacy_wording_checks=False`를 명시합니다.

문자열 처리를 모두 제거한 것은 아닙니다. 출처 원문 일치, 코드·수치의 근거, 실제 비교할 표시값, 사전조건의 지원 읽기 방식, 조작 순서와 복원 연결은 실행 보호 검사로 유지합니다. 새 동의어 목록을 추가하지 않았으며 모든 자연어를 지원한다는 의미도 아닙니다. Agent 4·제품·공식 자산·사람 승인 동작은 바꾸지 않습니다.

새 TC는 조회·값 변경·변경 차단으로 구분합니다. 조회는 복원하지 않고, 값을 변경하는 TC는 시험 전 관찰 상태로 복원·비교합니다. 차단 TC도 예상 밖 변경에 대비한 복원 절차를 갖추되, 상태가 유지됐으면 복원 조작을 생략합니다. 복원 실패는 제품 판정과 별도로 보고하고 해당 브라우저 환경을 종료합니다. 다른 TC는 분리된 새 환경에서만 실행합니다.

준비 전 원래 상태와 시험 직전 준비 상태를 구분합니다. 중앙 관제 모드·온도 준비는 관찰 복원 계약이 있을 때 허용하며, 준비 도중 실패해도 원래 상태로 복원·확인합니다. 차단 시험은 준비 상태가 유지됐는지 판정하지만, 준비하면서 바꾼 값은 최종적으로 되돌립니다. 다른 기능의 안전한 준비·복원 방법은 추정하지 않습니다. 기존 공식 TC와 과거 실행 기록에는 이 기준을 소급 적용하거나 코드를 덮어쓰지 않습니다. 실제 새 모델의 작성 품질 검증과 로컬 자동 테스트는 구분합니다.

## 실행 방법

Python 3.10 이상이 필요합니다. OpenAI API 키는 실행 환경의 `OPENAI_API_KEY`에 설정합니다. 실제 모델 호출에는 비용이 발생합니다. 기본 모델은 `gpt-5.6-terra / medium`입니다.

```powershell
python -m pip install ".[agent3,test]"
python -m playwright install chromium

# 저장된 실제 Run 조회
python -m qa_pipeline_ui

# 새 API 실행과 사람 승인 기능 활성화
python -m qa_pipeline_ui --allow-live-run --allow-asset-approval
```

브라우저에서 `http://127.0.0.1:8765/`에 접속합니다. 새로 복제한 저장소에는 로컬 실행 기록이 없어 조회 목록이 비어 있을 수 있습니다. `pytest-playwright`는 agent3 설치 옵션에 포함됩니다. 실제 실행·승인 요청은 같은 로컬 페이지의 JSON 요청만 허용합니다.

HTML을 직접 열거나 공개 웹 주소에 접속하면 MED 풍량 정상 변경의 저장된 데모가 표시됩니다. 데모 승인은 화면 시연이며 파일에 반영되지 않습니다. 실제 시험은 로컬 서버가 별도 브라우저에서 수행하고, 관제 화면에는 실행 상태와 결과가 표시됩니다.

CLI에서는 다음 순서로 실행합니다.

```powershell
python -m qa_pipeline_v2 pipeline --request "examples/change_request.success-medium-fan.json" --target-html "product_baseline/virtual-controller.html"
python -m qa_pipeline_v2 execute --run-id "RUN-..." --target-html "product_baseline/virtual-controller.html"
python -m qa_pipeline_v2 agent4 --run-id "RUN-..."
```

`pipeline`은 Agent 1~3, `execute`는 완료 후보 확인·관련 기존 회귀, `agent4`는 분류·최종 보고를 담당합니다. 후자의 두 명령은 모델을 호출하지 않습니다. Slack·Notion은 기본 미리보기이며 CLI에서 `--send`를 명시할 때 실제 전송합니다. 화면에서 시작한 실행은 외부 보고 미리보기까지 진행합니다.

Notion은 실행 후 TC 제목·결과·분류 요약과 함께, 검증된 설계의 사전조건·단계별 조작과 기대결과·복원을 해당 실행 페이지 본문에 연결합니다. 같은 내용의 재전송은 중복 추가하지 않고 수동 메모는 보존합니다. 과거 TC에 단계 연결 정보가 없으면 임의로 보충하지 않습니다. Agent 2 초안만 별도 게시하는 기능은 없으며, 로컬 미리보기·자동 테스트와 실제 Notion 게시 확인은 구분합니다.

## 검증과 공개 증거

촬영 전 미리보기는 `python scripts/record_demo.py`로 생성합니다(`.[agent3,video]` 설치 필요). Playwright·FFmpeg 기반이며 OBS는 필수가 아닙니다. 이 도구는 저장 결과 조회만 허용하고 실제 승인·API 호출·외부 게시를 수행하지 않습니다. [녹화 방법과 최종본 구분](docs/PROJECT_GUIDE.md#승인-전-영상-미리보기-생성)을 먼저 확인하세요.

이 미리보기 도구는 지정 Run의 미등록 상태를 전제로 합니다. 이미 공식 등록됐다면 중단하며, 촬영을 위해 등록을 취소하지 않습니다. 실제 등록 상태와 영상 준비 현황은 인계 문서를 확인하세요.

새 후보는 본 시험 직전에 사전조건의 실제 값을 확인합니다. 증명을 연결하지 못한 TC는 제외 사유를 남기고, 실제 준비 상태가 다르면 제품 결함과 구분해 보고합니다. 과거 성공 Run이 새 사전조건 검증까지 받았다는 뜻은 아닙니다.

```powershell
python -m pytest -q
python -m pytest --collect-only -q
git diff --check
```

[MED 성공 사례](examples/results/agent1-agent2-agent3-agent4-medium-fan/README.md)와 [잠금 불일치 사례](examples/results/agent1-agent2-agent3-agent4-lock-disable/README.md)는 실행 당시 공개 증거입니다. 최신 로컬 실행과 공개 예시의 날짜·상태는 [현재 상태](PROJECT_HANDOFF.md)에서 구분합니다. 자동 테스트 통과는 새 실제 API 실행의 성공을 뜻하지 않습니다.

[미정 조건이 남은 사례](examples/results/agent1-agent2-agent3-agent4-partial-information/README.md)는 실행한 시험이 통과해도 정보 부족이 남으면 사람 검토로 넘기는 흐름의 공개 요약입니다. 실행 통과와 요청 전체의 검증 완료를 구분합니다.
