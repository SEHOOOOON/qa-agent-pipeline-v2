01 · 정상 변경중풍 적용과 기존 강풍 TC를 함께 검증

무엇을 확인했나요?

새 중풍 후보의 표시·내부 설정과 관련 기존 강풍 TC를 검증했습니다. 환경 점검은 제품 시험과 별도 집계했습니다.

확인한 결과

새 후보와 기존 TC 모두 통과했습니다. 공식 등록 여부는 이 실행의 PASS와 별도로 사람이 판단합니다.

당시 실행 결과 원문 ↗
02 · 제품 불일치 후보잠금 상태인데 온도 버튼은 활성

기대와 실제가 어떻게 달랐나요?

내부 잠금값은 true였지만, 비활성 상태여야 하는 온도 버튼이 실제로는 활성 상태였습니다.

통과로 바꾸지 않고 보고

기대값을 유지하고 제품 불일치 후보로 분류했습니다. 제품 결함 확정은 근거를 검토한 뒤 결정합니다.

실패 관찰·분류 원문 ↗
03 · 확정 범위만 진행동작은 시험하고, 미정 색상은 별도 확인

어디까지 시험했나요?

확정된 중풍 동작은 시험했습니다. 함께 요청했지만 목표가 정해지지 않은 알림 색상은 임의로 정하지 않았습니다.

시험 통과 ≠ 요청 전체 확인 완료

실행한 시험은 통과했지만 미정 조건이 남아 사람 검토로 넘겼습니다. 정보 부족을 실패 TC로 집계하지 않습니다.

부분 진행·검토 기록 ↗
90초 데모 · 정상 변경 / 실패 보고 / 부분 진행

저장된 실행 기록과 사용자 승인에 따른 대행 등록 장면의 편집본입니다. 새 AI 실행 전 과정을 연속 촬영한 영상은 아닙니다. 펼친 뒤 재생 버튼을 눌러 확인할 수 있습니다.

04 / 상세 테스트 설계

조작 순서만이 아니라,
확인 대상과 시점까지 연결합니다.

실제 사람이 승인한 TC-V2-002를 읽기 쉽게 정리했습니다. ‘중풍 적용’ 한 단계에도 화면과 내부 설정이라는 두 개의 확인 대상이 있습니다.

중풍 적용 후 표시·내부 설정 확인

TC-V2-002 · 공식 등록 기록

시험 전오류·잠금이 없는 단일 장비, 초기 풍량 LOW 확인

조작 순서

  1. 대상 장비 카드를 선택합니다.
  2. 풍량을 MED(중풍)로 선택합니다.
  3. 선택한 풍량을 대상 장비에 적용합니다.

3번 적용 직후 · 기대결과

ER-001 · 장비 카드‘중풍’이 표시됩니다.

ER-002 · 내부 풍량 설정fanSpeed 값이 MED입니다.

시험 후LOW로 복원·적용하고, 카드 표시와 내부 풍량이 초기 상태로 돌아왔는지 확인합니다.

상세 TC 원문·복원 절차 펼치기
사전조건
  • 중앙 관제 패널에서 오류와 잠금이 없는 단일 장비를 대상으로 합니다.
  • 첫 실행 기본 상태인 LOW 풍량을 확인한 뒤 시험을 시작합니다.
복원 절차
  1. 시험 뒤 대상 장비를 LOW 풍량으로 복원하고 적용합니다.
  2. 복원 후 대상 장비 카드가 실행 전 상태와 같은지 확인한다.
  3. 복원 후 대상 장비의 내부 fanSpeed가 초기값 LOW인지 확인한다.

연결 요구사항: REQ-FAN-001 · 원본 후보: TC-CAND-001
당시 승인된 기록으로, 최신 생성 지침의 모든 유형을 대표하지는 않습니다.

승인된 TC 전체 원문 ↗

이미 같은 TC가 있다면?

변경 조건을 기존 TC로 확인할 수 있는지 먼저 비교합니다. 충분하다면 새 TC를 중복 생성하지 않고 재사용합니다.

코드는 누가 만드나요?

AI는 조작·검증 계획을 작성합니다. 프로그램은 허용된 계획을 Playwright Python 코드로 변환하고 실행 전에 검사합니다.

TC 유형별 복원 기준 보기
값을 변경하는 TC

시험 전 기준 상태로 복원하고 실제 값을 확인합니다.

조회만 하는 TC

값을 바꾸지 않으므로 복원은 불필요합니다.

변경을 차단하는 TC

상태가 그대로인지 확인하고, 실제로 바뀌었다면 복원합니다.

실행 증거

화면 캡처·로그·Trace로 시험과 복원 결과를 남깁니다.

복원 실패 시에는 실패를 기록하고, 같은 환경의 후속 시험을 계속하지 않습니다.

05 / 진행과 중단의 기준

수정할 오류와,
사람에게 물을 조건은 다릅니다.

잘못 작성된 초안은 고칠 수 있지만, 정해지지 않은 기준까지 AI가 추측해서는 안 됩니다. 원인에 따라 다음 행동을 구분했습니다.

조건 충족 → 다음 단계

필수 조건과 검사를 충족한 범위를 전달합니다. 원문과 연결된 결과인지도 확인합니다.

확인된 오류 → 제한된 재작성

오류 항목을 AI에 돌려보내 수정·재검사합니다. 단계별 자동 재작성은 최대 1회입니다.

기대값 변경이나 검사 삭제로 통과시키지 않습니다.

정보 부족 → 부분 진행 또는 확인

분리 가능한 미정 조건은 별도 보고하고 확정 범위만 시험합니다. 핵심 조건이나 모델의 판단이 불확실하면 자동 인계를 멈춥니다.

미해결·미지원 → 중단 또는 제외

남은 오류는 다음 단계로 넘기지 않습니다. 지원하지 않는 조작은 제외 사유를 남기며, 제품 결함이나 성공으로 처리하지 않습니다.

표현이 다르다는 이유만으로 거부하지 않나요?

단어나 문장 표현만으로 거부하는 규칙은 줄였습니다. ID·명시 값·범위·출처 연결·실제 실행 조건은 유지했습니다.

자연어 의미와 검사 계획의 연결은 별도 모델이 검토합니다. 인용 존재·검토 누락·입력 일치는 코드로 확인하지만, 모델 판단의 의미 정확성까지 보장하는 것은 아닙니다.

전체 분기·재작성·중단 기준 ↗
06 / 보고 이후 · 사람 승인

PASS는 실행 결과입니다.
공식 기준 반영은 사람이 결정합니다.

Agent 4는 결과와 근거를 분류해 보고합니다. 사람은 실행 증거, SRS 개정안, 재사용할 TC를 검토한 뒤 등록 여부를 판단합니다.

  • 실행 근거

    요청한 내용을 시험했는지, 기대와 실제 관찰이 일치하는지 확인합니다.

  • SRS 개정안

    제품 기준을 무엇으로 바꿀지, 변경 전후 내용을 검토하고 별도 동의합니다.

  • 공식 테스트

    TC와 코드가 일치하는지, 다음 변경에도 재사용할 테스트인지 확인합니다.

보류

이유와 추가 확인할 내용을 기록합니다.
기존 SRS와 공식 TC는 유지합니다.

승인

동의한 SRS 개정과 검증된 후보 TC·코드를 등록합니다. 이후 변경에서 재사용합니다.

등록 직전 자동 확인과 기존 TC만 재사용한 경우

최종 결과·자동 검사·필수 증거와 TC·코드·현재 제품 화면의 연결을 확인합니다. 화면이 바뀌었다면 승인 전 재시험이 필요합니다.

기존 TC만으로 검증했다면 새 TC를 중복 등록하지 않고 SRS 개정만 승인할 수 있습니다. 검토서 작성만으로 공식 파일이 바뀌지는 않습니다.

보고 분류: 제품 불일치 후보 / 자동화 문제 / 환경 문제 / 판정 근거 부족 / 미실행
Slack·Notion은 기본 전송 미리보기이며, 실제 전송은 명시적으로 요청할 때 수행합니다.

07 / 구현 범위와 다음 검증

구현한 것과,
더 검증할 것을 구분합니다.

대표 실행의 성공을 모든 요구사항에 대한 품질 보장으로 설명하지 않습니다. 현재 동작과 과거 실행 증거를 구분해 관리합니다.

구현한 연결

변경 요청 → 분석·TC 설계 → 자동화·시험 → 보고 → 사람 승인. 단계별 산출물과 실행 근거를 연결했습니다.

현재 대상

가상 중앙제어의 기존 요구사항 변경(MODIFIED)입니다. 지원하는 화면 요소·조작·검증 방식 안에서 자동화합니다.

추가 검증

새 모델 근거 검토의 정확도·오탐, 다양한 요청과 반복 실행에서의 품질·비용 편차를 더 평가해야 합니다.

현재 범위 밖

실제 장비 통신, 임의 웹사이트, 전체 회귀, 요구사항 추가·삭제, 완전한 자동 복구는 구현 완료로 소개하지 않습니다.

검증 환경과 프로젝트 2의 역할

후보 코드는 원본과 분리된 임시 폴더에서 실행합니다. 이 작업 공간은 OS 권한을 격리하는 보안 샌드박스가 아닙니다.

프로젝트 2는 같은 흐름을 반복해 Agent별 산출물이 기준을 지키는지 평가하는 별도 작업입니다. 내부 자동 테스트 통과 수는 실제 모델의 정확도가 아닙니다.

  • 전체 분기·검사·승인 계약 ↗왜 진행하고, 왜 멈추는지
  • 최신 실행 결과와 남은 과제 ↗현재 검증 상태
  • 자동 테스트 목록 ↗제품 TC와 구분한 내부 검증
  • 프로젝트 소개·실행 방법 ↗설치와 저장소 구조
