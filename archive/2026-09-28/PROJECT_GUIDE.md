## 기대결과의 범위와 제품 판정

### 관찰된 조작 유형과 버튼 설명 구분

UI Inventory의 action_hint는 새 관찰에서 설명 문장이 아니라 실제 DOM의 태그·역할·입력 종류로 정한 조작 유형입니다. 기존 selector 목록과 일반 탐색 모두 같은 판별 함수를 사용합니다. CLICK/FILL/SELECT_OPTION/CHECK_OR_UNCHECK와 표시 전용 READ_STATE를 구분하며, 숨김·비활성·중복 selector 차단 및 TC 실행 정의 일치 검사는 CP3에 유지합니다. 버튼이라는 사실만으로 올바른 기능 연결이나 제품 동작까지 보장하지 않으므로 실행 증거와 의미 검토는 그대로 필요합니다. 과거 저장 관찰/실패 기록은 다시 쓰지 않습니다.

### 제품 제어 패널의 적용 전후 표시

적용 전에는 편집 중인 대기값을 유지합니다. 적용 후에는 성공·차단 여부와 관계없이 선택 장비의 실제 상태를 다시 표시합니다. 잠금 때문에 24→22°C 명령이 차단되었다면 패널·카드·내부값 모두 24°C입니다. 전원·모드·풍량·온도·잠금에 같은 읽기 경로를 사용합니다. 잠금 해제만 허용되는 명령에서는 다른 대기값을 함께 적용하지 않습니다.

복수 선택은 기존의 마지막 선택 장비를 표시 기준으로 사용하고 헤더에 해당 장비를 명시합니다. 표시 동기화는 전체 적용 반복문이 끝난 뒤 수행하며 다른 장비에 값을 다시 쓰지 않습니다. 연결 끊김 상태는 실제값을 표시하되 조작 비활성을 유지합니다. 이는 사용자 지시에 따른 V2 제품 수정이며 TC 기대값 완화나 파이프라인의 공식 자산 등록은 아닙니다.

### 검토 근거 원문은 프로그램이 연결

source_selection_schema는 각 검토 입력의 기존 source_id 전체를 그대로 enum으로 제한한 응답 모델을 만듭니다. Agent 1·2·3 공통이며 원문·근거 번호·저장 구조는 변경하지 않습니다. 250개씩 서로 겹치지 않는 anyOf enum에 담는 것은 API 형식 제한 대응이며 검토/API 호출을 나누는 것이 아닙니다. 근거가 여러 개면 각 정확한 번호를 별도로 선택합니다. 부모 경로·연결한 문자열·미등록 번호는 허용 목록에 없습니다.

공식 Structured Outputs 한도에 맞춰 verdict 3개를 포함한 enum 총 1000개, 속성/정의 이름 및 enum/const 문자열 합계 120000자를 확인합니다. 빈/중복 ID 목록이나 한도 초과는 API 호출 전에 오류로 중단합니다. 목록을 생략·재번호화하거나 자유 문자열로 자동 전환하지 않습니다. 동적 응답 형식은 입력/처리 크기에 영향을 줄 수 있으며, 정확한 ID가 의미적으로 맞는 근거임을 보장하지 않습니다. API 거절·미완성 응답·모델 지원 여부는 실제 검증과 별개입니다. 기준 출처: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

공통 검토 지침/캐시는 grounding-1.17이며 Agent 1·2·3 검토에 동일하게 적용합니다. 새 모델 응답 GroundingSourceSelection은 item_id·verdict·single_fact·source_ids·reason만 작성하며 quote/citations 필드는 없습니다. 프로그램의 bind_review_sources가 선택 ID의 source_documents 원문 전체를 복사합니다. 유사도·맞춤법·접속사 보정이나 없는 ID의 자동 추측은 하지 않습니다.

기록은 기존 grounding-1.0 입력 해시와 함께 citation_binding_contract=source-id-1.0, 실제 source_selection, 원문이 연결된 review를 보존합니다. 저장 검토·후속 인계·사람 승인 재검사는 선택 ID로 재구성한 결과와 기록을 비교합니다. 없는/중복 ID, 빈 근거, 항목 누락, 원문/판정 변경, 입력 해시 불일치는 거부합니다. 선택이 잘못된 응답도 수신 결과와 사용량을 먼저 보존한 뒤 검토 오류로 중단하며 AI 재호출로 숨기지 않습니다.

기존 형식의 검토 기록은 기존 인용 검사로 읽고, 과거 FAIL/ERROR를 자동 PASS로 바꾸지 않습니다. 새 방식은 모델이 인용문을 의역하는 경로를 없애지만, 근거가 판단을 실제로 뒷받침하는지는 여전히 모델의 의미 판단 대상입니다. ID 존재 검사는 의미 정답 검사가 아닙니다. 선택 문서 전체를 연결하므로 일부 문장만 인용하던 기록보다 길어질 수 있습니다. Agent 1 분석 자체의 source_text 등 생성 필드는 이번 변경 대상이 아닙니다.

### 제품 연결표: 시험 내용은 TC, 위치는 어댑터

| fanSpeed.low | #det-fan-low | 약풍 선택 |

정의는 src/qa_pipeline_agent3.py의 controller_connection_catalog 한 곳에 둡니다. 연결표는 제품 위치·읽기 수단이며 시험 정답 값이나 시나리오 목록이 아닙니다. 같은 온도 위치에 21·27 등 어떤 시험값을 적용할지는 TC가 정합니다. 전원·모드·풍량·온도·잠금에 같은 방식으로 적용합니다. 현재 어댑터의 시험 장비는 ID 1이며 임의 장비·임의 웹사이트를 지원한다고 주장하지 않습니다.

알 수 없는 항목, 없는/중복된 위치, reader와 필드 불일치는 연결하지 않습니다. 이후 CP3와 코드 생성 진입점에서도 TC·연결표 동일성을 확인하므로 카드 확인을 패널 확인으로 바꿔치기하지 못합니다. 화면의 표시·활성 상태 및 실제 제품 동작은 기존 관찰·실행 검사에서 확인합니다. 준비 전 기록·화면/내부값 복원·실패 시 후속 중단·사람 승인은 유지합니다.

Agent 2의 논리 항목 선택이 원래 요구와 맞는지는 별도 의미 검토 대상입니다. 연결표가 오래되거나 화면 의미가 바뀌면 어댑터 점검이 필요합니다. 새 연결표 경로는 실패했다고 AI 위치 생성으로 우회하지 않으며, 과거 기록은 당시 계약으로 읽습니다. 사람용 상세 TC와 실행 정의의 중복 작성 제거 및 과거 호환 코드 정리는 이번 변경에 포함하지 않았습니다.

새 인계는 **상세 TC + 실행 정의 → 화면 위치 연결 → 기존 코드 생성·시험**입니다. Agent 2의 `execution_spec`은 조작·입력값·ER별 reader/기대값·확인 시점·시작 상태 확인을 정의하고 DOM 선택자는 포함하지 않습니다. 새 TC의 binding_contract=controller-map-1.0에서는 제품 연결표가 그 ID와 실제 위치를 연결하며 위치 생성용 AI를 호출하지 않습니다. 정의는 프로그램이 복사하며 Agent 3에서 값과 순서를 재작성할 수 없습니다.

CP2-024는 원문/ER/시점 참조 구조를 검사합니다. 의미 검토는 실행 정의가 원문 요구와 상세 TC에 맞는지 대조합니다. CP3-014와 컴파일 진입점은 인계 중 조작·기대값·시점·사전조건·복원 연결의 변경을 차단하고, CP3의 기존 인터페이스·계층·장비 검사와 모델의 화면 위치 연결 검토를 유지합니다. 새 정의에서는 문장 속 수치·단어를 다시 추출해 값과 비교하지 않습니다.

위치 연결 원본과 조립 결과를 함께 저장하고 저장 검증에서도 같은 TC로 다시 조립합니다. 준비 전 기록·실측·복원 확인·사람 승인은 기존 실행기가 담당합니다. 없는 기능도 요청에 근거한 TC는 생성할 수 있지만 관찰된 실행 수단이 없으면 지원 부족 REVIEW로 남깁니다. 기존 산출물은 새 정의로 자동 변환하지 않으며 당시 계획/검토 계약으로 읽습니다. Agent 2의 잘못된 논리 항목 선택·연결표 노후화·의미 검토 오판 가능성은 남고, 실제 모델 안정성은 별도 검증 대상입니다.

연결 응답의 배열 순서는 시험 순서가 아닙니다. 중복·누락·알 수 없는 ID는 조립 오류로 중단하지만, 올바른 ID의 나열 순서는 바뀌어도 Agent 2 순서로 조립합니다. 새 연결표 경로의 오류는 동일 연결을 재작성하지 않고 중단합니다. 과거 모델 연결 경로만 기존 CP3 재작성을 유지합니다. 실행 시에는 기존의 관찰된 관제점 유한값 표기 정리만 적용하고 원본/변환을 보존합니다. TC 동일성 비교에서도 같은 표기 정리만 허용하며, 숫자·다른 의미·임의 단어 추출은 허용하지 않습니다. 비교용 표기 정리는 실제 UI 지원을 증명하지 않고 CP3의 관찰·장비 검사가 별도로 수행됩니다.

작성기(A2 2.54)와 공통 검토(1.16)는 같은 기대결과 범위 안내를 사용합니다. 새 위치 연결기(controller-map-1.0, 저장 인계 형식 A3 3.43)는 검토된 TC 실행 정의를 재작성하지 않으며, 과거 TC의 계획기 3.42는 기존 안내를 유지합니다. 금지 동작과 유지할 상태를 동의어로 처리하지 않고 요청·SRS의 대상·값·시점을 보존합니다. 패널 선택값과 적용 후 장비값을 구분하며 실제 제품에서 관찰된 결과를 정답으로 삼지 않습니다. 원문에 명시된 유지 검사의 누락·범위 확대는 필수 의미 검토의 대상이며 모델 오판 가능성은 남습니다.

A2 2.54의 최초·재작성 입력은 controller_connection_catalog의 정확한 논리 키와 action_type/strategy/read_kind를 투영합니다. selector·내부 실제 읽기 경로는 제외하고 키는 축약·번역하지 않습니다. 작성 지침의 별도 축약 목록을 제거했으며 새로운 별칭이나 검사 단계를 추가하지 않습니다. 미등록 키는 기존 Agent 3 검사에서 계속 제외하며 unsupported 항목으로 없는 기능의 TC를 작성하는 경로는 유지합니다. 잘못된 의미 선택이나 모델의 목록 이탈 가능성은 남습니다.

controller-map-1.0의 device.select 값은 생략(null)하거나 연결표와 동일한 정수 ID를 명시할 수 있습니다. resolver와 CP3가 같은 비교를 사용하며 null을 임의 장비 탐색으로 해석하지 않습니다. TC/계획의 null을 다른 값으로 재작성하지 않고 실행기는 고정된 target_device_id를 확인합니다. 다른 ID·문자열·boolean은 거부하고 비연결표 계획은 명시적 ID를 계속 요구합니다. 공통 복원의 조사/검사 목록은 쓰기 버튼과 온도 표시·제한 안내·장비 카드를 포함한 같은 상수를 사용하며 누락되면 여전히 실패합니다.

기본 UI 조사의 내부 관찰값도 같은 연결표의 INTERNAL_VALUE 항목에서 수집 필드를 가져옵니다. 현재 전원·모드·풍량·온도·잠금과 대상 식별 ID를 읽으며 대상 ID 1의 실제 배열 위치를 기록합니다. 없는 필드를 null/default로 만들지 않고, 실제 null/문자열/boolean/유한 숫자만 보존합니다. 객체·함수·미등록 개인정보 필드는 일반 수집에 추가하지 않습니다. generic 탐색의 기존 계약과 대상 ID 검사는 유지하며, 관찰 성공은 준비/시험/복원 성공과 별개입니다.

새 A3 Manifest의 product_verdict_contract=1.0은 최초 컴파일·실행 인계·재시험·승인 재검사에 같은 정책으로 전달됩니다. TC Assertion은 계속 판정하고, BLOCKED_CHANGE 분류에 따라 준비 상태 전체와 같아야 한다는 별도 제품 실패를 추가하지 않습니다. 스냅샷 차이는 복원 필요 여부만 결정하며 실제 복원 후 화면·내부값 비교와 실패 시 환경 종료는 유지합니다. 과거 계약의 코드/검토 입력은 그대로 재현하고 새 검토의 입력 해시를 과거 기록에 재사용하지 않습니다. 정책 누락·혼합은 거부합니다. 새 AI 단계·재작성·호출 상한 증가는 없습니다.

같은 계약에서는 본 시험의 조작 방식을 기대 출력값으로 선택하지 않습니다. 기존 온도 버튼 어댑터의 TEST는 패널이 더 변하지 않으면 시도를 끝내고 연결된 Assertion에서 판정합니다. 준비·복원은 목표 상태를 반드시 확보해야 하는 기존 엄격한 경로를 유지합니다. UI/읽기 부재·정착하지 않는 조작은 기술 오류이며, 다른 값을 관찰했다고 기대값을 자동 수정하거나 통과시키지 않습니다.

### 기존 기능 시험과 기준 변경의 구분 · 작업 경계 1.3

Agent 3 실행 인계와 승인 직전 재검사의 값 역할·공통 근거·실행기 계약 포함 여부는 `_agent3_review_options` 한 곳에서 선택합니다. 각 기록의 계약 버전을 검증한 뒤 당시 옵션으로 검토 입력을 재구성합니다. 최신 작업 경계 1.3도 승인에서 누락되지 않으며, 과거 기록을 새 기준으로 재해석하거나 필수 검토·해시 검사를 우회하지 않습니다.

- Agent 1의 대상 Requirement도 VERIFY(기존 기준 시험) 또는 MODIFIED(정책 변경)로 분류합니다. 입력의 change_type=MODIFIED와 시험 중 상태 변경만으로 SRS 개정을 강제하지 않습니다. Agent 2는 기존 개정 범위 계산을 그대로 사용하므로 VERIFY에는 개정안을 요구하지 않습니다. 기존 TC가 요청된 시험을 충족하지 못하면 대상 VERIFY도 CHANGE_VALIDATION 후보로 작성할 수 있습니다. 대상 외 VERIFY 회귀의 무단 중복은 계속 차단합니다. 실제 정책 변경의 잘못된 VERIFY 분류는 최초 요청/SRS와 대조하는 필수 의미 검토 대상입니다.
- CP1-007은 SRS 근거 설명에 포함된 요청 시험값을 요청 원문과 함께 확인합니다. SRS의 숫자 범위에 모든 시험값이 개별 표기돼 있을 필요는 없습니다. 대상 VERIFY의 before_value는 시험 시작값 근거로 사용할 수 있고 CP1-004는 분석과의 일치를 검사합니다. 새 검토 입력에는 before_value도 원문 역방향 항목으로 보존합니다. 이 검사는 숫자의 출처이지 범위 안/밖 판정이 아닙니다. 기존 기준에서 범위 밖 준비·성공 요구, 범위 밖 입력의 차단 시험, 명시적인 정책 변경을 의미 검토에서 구분합니다. 관련 없는 수치의 차용·범위 반전 등 의미 오판을 코드가 모두 탐지한다고 주장하지 않습니다.
- Agent 2의 준비·복원·중간 초기화와 분석의 모든 절차 원문은 PROCEDURE/ALL 한 항목에서 대조합니다. 개별 preconditions/restore_steps를 다시 각각 반려하는 중복을 없앱니다. 조작·제품 기대결과·조건 연결 검토는 유지합니다. Agent 3도 PRECONDITION_COVERAGE에 포함된 checks를 독립 항목으로 다시 검토하지 않습니다. 요청된 시작 상태의 의미 연결, 실제 runtime check, 복원 계획/확인 및 실패 중단은 없애지 않습니다.
- 현재 UI에 없는 독립 기능도 명시된 요구사항을 근거로 TC를 작성합니다. 없는 선택자·내부 필드나 비슷한 AUTO 기능을 만들어 연결하지 않습니다. TC 작성 가능과 자동 실행 지원은 별개이며, 지원 부족은 시험 전 보류이지 실행 FAIL이나 제품 결함 확정이 아닙니다.
- 계약 인용의 source_id만 잘못된 경우, 호스트 계약 문서(TASK_BOUNDARIES/EXECUTION_CONTRACT/REVIEW_RESPONSIBILITIES) 사이에서만 **전체 문장의 정확·유일 일치**를 확인해 연결합니다. 요청·SRS로의 출처 이동, 없는 문장, 부분 문장, 모호한 중복, 미등록 출처 ID는 거부합니다. 원본 검토 응답은 변경하지 않고 CheckResult.message에 연결 보정을 기록합니다. 검토의 FAIL/REVIEW 판정은 보정으로 바꾸지 않습니다.
- 과거 작업 경계 1.0~1.2는 당시 항목·규칙으로 읽습니다. 새 인계는 작업 경계 1.3과 프롬프트 A1 2.23 / A2 2.54 / A3 3.43(과거 TC는 3.42)을 함께 확인하며 과거 검토 해시를 새 입력에 재사용하지 않습니다. A1의 범위 계약 1.2는 분류명·요청의 SRS ID/전체 문장 포함 여부에 따른 보류를 제거하고 기존 필수 의미 검토에 범위 판단을 맡깁니다. 스키마·모델·API 한도·공식 승인·실행/복원 기능은 확대하지 않습니다.

## 먼저 보기: 어떤 판단을 왜 하는가

이 절은 **현재 구현을 읽는 지도**입니다. 검사를 추가하거나 제거한 계획이 아닙니다. 세부 업무 규칙은 아래 단계별 목록에서, 실제 조건문·예외·종료 지점·스키마·상태값은 [코드 위치별 색인](../../docs/logic_inventory.json)에서 확인합니다. `CP` 번호는 자동 검사의 이름이며 모델 호출 횟수나 사람 승인 단계를 뜻하지 않습니다.

### 가장 중요한 보호 6가지

| 중요하게 지킬 것 | 쉬운 설명 | 담당 |
|---|---|---|
| 요청과 다른 시험을 만들지 않기 | 없는 기능·값을 덧붙이거나 해야 할 검사를 빠뜨리지 않음 | CP1·CP2, 공통 모델 근거 검토 |
| 모르는 것을 아는 것처럼 넘기지 않기 | 미정 조건·지원하지 못하는 자동화를 기록하고 진행 가능한 범위와 구분 | A1 진행 판단, A3 실행 자격, 최종 권고 |
| TC와 실제 코드가 같은 것을 검사하기 | 대상·값·조작 순서·확인 시점·기대결과 연결 유지 | CP2·CP3·컴파일 검사 |
| 시험 환경을 다음 시험에 오염시키지 않기 | 사전조건을 실제로 확인하고 변경 상태를 복원·확인 | CP3·시험 코드·결과 분류 |
| 실행하지 않은 일을 성공이라고 보고하지 않기 | 실패·미실행·제외·환경 점검을 구분하고 증거와 집계를 대조 | execute·Agent 4·CP4 |
| 사람 동의 없이 공식 기준을 바꾸지 않기 | 통과는 등록 자격일 뿐, SRS·공식 TC는 별도 사람 승인 | 승인 서버·현재 증거/해시 확인 |

**공통 토대:** 단계마다 같은 입력·TC·코드·증거인지 SHA-256과 계약 버전으로 확인합니다. 이 확인이 빠지면 위 여섯 보호가 다른 파일의 결과를 근거로 판단할 수 있습니다. 해시는 내용의 동일성을 확인하지 의미적 정답이나 외부 공격자에 대한 서명을 보장하지는 않습니다.

### 새 실행의 검사 책임과 남는 위험

**요청 의미와 실행 절차의 경계:** 새 A1은 `after_value`·`description` 각각에서 `REQUEST_COVERAGE`를 열거하고 기존 필수 모델 검토에서 분석의 전달 내용을 대조합니다. 문장 내 모든 온도 범위를 새 필수 범위로 보는 CP1 휴리스틱은 과거 실행용으로만 남습니다. 다른 값·누락·경계/허용 정책 반전은 검토 대상이며, 구조 통과만으로 올바른 해석이라고 결론내리지 않습니다.

새 A2/A3 작성기와 검토기는 같은 `TASK_BOUNDARIES`를 받습니다. 명시된 시험 맥락과 그 맥락의 확인을 무조건 새 기능으로 반려하지 않고, 실제로 요청 밖 결과를 추가했는지 구분합니다. 준비/복원을 구현하려고 제품 ER을 늘리지 않습니다. A3의 `compiler_plan_facts.controller_recovery`는 실제 RESTORE 단계의 공통 복원 동작이 있을 때만 제공되며, 준비 전 캡처·복원 후 전체 내부/화면 snapshot 비교가 ER ID와 독립임을 설명합니다. 해당 동작이 없거나 읽기 전용·지원 확장 계획이면 이 자동 복원 근거는 없습니다. 개별 ER 복원 비교·사전조건 런타임 검사·실행 증거는 계속 필요합니다.

| 항목 | 코드가 확인할 것 | 기존 모델 검토가 확인할 것 |
|---|---|---|
| TC 기대결과 | 출처·ID·조건 연결·구조화 계약 | 조작값과 기대값의 의미, 요청 밖 값·누락·범위 확대 |
| 원래 값 기록 | 준비 전 실제 관찰·동일 위치 복원 비교 | 기록 지시가 실제 자동 기록 대상에 연결되는지 |
| 시험 시작 상태 | 제공된 읽기 방식·대상·타입 및 실행 시 실제 값 | 원래 TC의 모든 시작 조건에 필요한 상태 검사가 있는지 |
| 장비 선택/읽기 | 대상 ID 관찰·실행 시 ID 보호 | TC가 의도한 장비·필드와 계획의 의미가 일치하는지 |
| 승인 전 재검사 | 새 A2는 공통 로더의 전체 CP2, CP3/검토·증거·해시 검사. 과거 A2의 추가 CP2-017 승인 보호는 유지 | 저장된 필수 검토 결과를 그대로 재검증; 새 판단을 추측하지 않음 |

CP2의 기대결과 문장 전체 값 추출과 CP3의 문장마다 검사 1개 강제는 새 실행에서 사용하지 않습니다. `PRECONDITION_COVERAGE`는 생성 계획이 아니라 원래 TC의 모든 사전조건에서 열거하므로 계획에서 삭제해도 검토 대상이 사라지지 않습니다. 컴파일러 기록 대상/ID 보호는 호스트가 생성한 사실 설명이고 실제 시험 성공 증거가 아닙니다. 자동 캡처로 고정 시작 상태나 목록 밖 관찰 대상의 확인을 대신할 수 없습니다. 지원 확장 요청은 빈 실행 계획을 요구하므로 이 실행 계획용 역방향 검토에서 제외하고 확장 사유를 검토합니다.

**부작용과 한계:** 의미가 틀린 값이나 누락을 모델이 잘못 지지하면 구조 검사만으로 모두 잡지는 못합니다. 검토 누락·UNSUPPORTED·UNCERTAIN·해시 불일치는 인계를 막지만, 검토 통과가 정확성 보장은 아닙니다. 정상/오류의 대역 검사는 분기 연결만 입증하며 실제 모델의 판정 품질은 별도 Live 검증 대상입니다. 새 분류기·AI 단계·TC 필드는 추가하지 않습니다. 기존 FAIL 재작성, REVIEW 사람 확인, API 오류 중단, 복원 실패 환경 종료, 공식 자산의 별도 승인을 유지합니다.

### 설명 형식은 덜어내고 실제 검사 연결은 유지

| 새 실행에서 허용할 차이 | 계속 확인할 내용 | 남는 위험 |
|---|---|---|
| 검토 응답 배열의 순서 | 입력 item_id 전체와 1:1 대응, 누락·중복·없는 ID·잘못된 인용 차단 | 순서가 맞는다고 내용이 옳지는 않음 |
| 공통·도메인·기능 QA 분류의 누락/분류 차이 | 분류는 참고 메시지. 기재한 기능 ID가 TC 밖이면 차단. 필수 요구/조건/ER 연결은 별도 검사 | 분류표가 비면 보고의 분류 정보가 줄 수 있으나 검증 완료로 자동 보충하지 않음 |
| independence_reason 미기재 | 단독 실행 불가 선언·다른 TC에 의존하는 실제 절차는 차단. 사전조건·준비·단독 실행·복원 확인 유지 | 자연어 의미 검토에도 오판 가능. 실제 성공 여부는 실행 증거로 확인 |

세 항목은 새 `output_tolerance_contract=1.0`으로만 선택합니다. 생성 TC의 상세 단계·관찰 대상·기대결과를 축약하지 않고, single_fact·CP3 사전조건의 기존 검사·안전 실행·해시·사람 승인 규칙도 추가로 완화하지 않습니다. 검토 모델에도 선택 설명의 누락만으로 반려하지 않도록 같은 기준을 전달합니다. 이 표시 자체는 합격 판정이 아니며 필수 모델 검토와 입력 해시에 연결됩니다. 과거 표시 없는 실행은 당시 순서/필수 설명 기준을 유지합니다.

### 완료 판정은 고정된 실제 실행 묶음으로

유료 검증 전에는 무료로 확인 가능한 실패를 먼저 제거합니다. 이는 검사 면제나 저장 판정의 자동 승격이 아닙니다.

| 변경/질문 | 먼저 수행할 무료 확인 | 유료 확인이 필요한 부분 |
|---|---|---|
| 실행기·복원·분기·보고 변경 | 관련 회귀와 전체 `scripts/verify_offline.py`, 저장 계획 무수정 실행 | 새 모델 생성이 해당 실행 경로로 연결되는지 |
| 작성/검토 지침·의미 판단 | 원문·실제 저장 TC와 반례, 검토 대상 누락/잘못된 인용 검사 | 정상/오류 산출물에 대한 실제 모델 판정 |
| 설명 문서·포폴 표현 변경 | 코드·실행 증거와 대조 | 동작 변경이 없다면 문서 수정만으로 API 재실행하지 않음 |
| API 한도·연결 오류 | 보존된 호출 장부와 설정 확인 | 사용자 확인·승인 후 최소 요청부터, 자동 반복 금지 |

충전 후에는 여러 전체 흐름을 한꺼번에 반복하기보다 승인된 한 건을 먼저 확인하고 결과를 보고 다음 범위를 정합니다. 저장 자료의 한 단계 검토는 진단이며, 과거 검토 해시를 새 입력에 붙이거나 생성/검토를 생략한 전체 완료로 취급하지 않습니다. 후보 한 건·재작성 없는 전체 흐름도 생성 3회와 검토 3회가 필요하고, 재작성/복수 후보는 별도 비용이 듭니다. 호출 수 상한은 지출 금액 상한이 아니며 실행 도중 모델 교체·새 재작성·상한 확대를 하지 않습니다.

현재 일반 CLI/UI에는 Run 전체의 금액·호출 총량 차단기가 내장돼 있지 않습니다. 단계별 재작성 제한과 SDK 자동 재시도 금지는 내장돼 있고, 최근 승인 배치의 총량 제한은 별도 실행 도구의 영속 호출 장부에서 적용했습니다. 따라서 총 상한을 승인받은 검증은 그 제한 도구를 통해 수행해야 합니다. 이번 보완을 모든 진입점의 예산 관리 완성으로 설명하지 않으며, UI 공통 예산 기능은 별도 범위입니다.

실행 전에 대표 요청·정답 범위·소스/프롬프트·제품/SRS/TC와 해시를 고정합니다. 상세 TC 예시는 작성 수준의 참고이고, 정답 값은 각 요청/SRS에서 사람이 확인해야 합니다. 사람이 검수하지 않은 것을 정답지 검수 완료로 표시하지 않습니다.

배치 중 코드를 수정하지 않고, 종료 후 생성 오류·검토 오판·검사 충돌·실행 지원 부족·제품 불일치·API/환경 오류를 증거로 구분합니다. 검토 AI의 PASS와 FAIL 모두 사람 기준과 대조하며 애매하면 원인 미확정입니다. 저장된 판정을 수동 PASS로 바꾸지 않습니다. API 한도 오류와 호출되지 않은 항목은 모델 품질 실패나 정상 완료로 집계하지 않습니다.

배치 후 공통 원인 보완은 한 차례로 제한하고 같은 요청 묶음을 재검증합니다. 이후에도 대표 정상 흐름이 막히면 실제 성공 범위와 사람 검토가 필요한 MVP로의 변경을 사용자와 결정합니다. 작업이 바뀌어도 횟수를 초기화하지 않습니다. 이는 AGENTS.md의 작업 규칙이며 새로운 런타임 분류기·자동 보완 루프·자동 승인 기능이 아닙니다. 고정 요청, 현재 단계와 보완 이력은 인계 문서에서 관리합니다.

### 중요도와 규칙 종류를 섞지 않기

| 분류 | 의미 | 정리할 때의 원칙 |
|---|---|---|
| 핵심 보호 | 잘못된 시험·잘못된 등록을 막는 조건 | 근거 없이 제거하지 않음. 코드·모델·사람 중 실제 책임자를 명시 |
| 실행 지원 | 허용 행동·읽기 방식·현재 중앙 관제 지원 범위 | 제품 요구의 옳고 그름과 구분. 미지원은 제품 결함이 아님 |
| 운영 보호 | 타임아웃·파일 경로·중복 실행·보고 전송·오류 기록 | 정상 기능처럼 보이지 않아도 실패 시 필요 |
| 작성 지침 | 읽기 쉬운 상세 TC, 문장 분할, 설명 방식 | 프롬프트 안내와 실제 차단 조건을 구분. 모든 안내가 코드 검사인 것은 아님 |
| 과거 호환 | 이전 Run을 당시 계약대로 읽는 조건 | 새 실행의 규칙으로 설명하지 않음. 과거 증거를 지우며 단순화하지 않음 |

### PASS가 보여도 같은 뜻이 아니다

| 표시/결정 | 실제 의미 | 다음 처리 |
|---|---|---|
| CP1 통과 / 인계 CONTINUE | 분석 검사를 통과하고 다음 설계가 가능 | Agent 2. 부분 진행이면 미정 항목을 보존 |
| CP1 REVIEW + CONTINUE | 확정 범위는 진행 가능하지만 마지막 확인 사항이 남음 | 확정 범위 설계, 질문·미정 항목을 보고에 유지 |
| CP1 범위 REVIEW 또는 WAITING_FOR_USER | 검사 범위/입력을 확정할 수 없음 | PAUSE. 입력 보완 후 새 Run; 중단 지점 자동 재개 아님 |
| 공통 근거 검토 REVIEW | 내용의 근거/검사 연결을 확신할 수 없음 | 해당 단계/후보 인계 중단. 수정 가능한 문제와 함께 있어도 추측 재작성하지 않음 |
| CP2 REVIEW | 설계에 후속 자동 진행을 막는 확인 사항이 있음 | Agent 3로 자동 인계하지 않음 |
| CP3 PASS | 계획·코드 검사가 통과 | 제품 시험 결과는 별도 확인 |
| 제품 시험 PASS | 해당 시험의 기대값·실행 조건을 만족 | 공식 승인 아님. 남은 제외·미정 범위와 증거 확인 |
| 제품 기대값 불일치 | 기대값과 관찰값이 다름 | 유효한 실패 증거이면 Agent 4로 전달. 기대값을 바꿔 통과시키지 않음 |
| CP4 PASS | 보고의 출처·증거·집계가 일치 | 제품 실패가 있는 보고도 CP4는 통과 가능 |
| 최종 권고 PASS | 현재 실행 범위·증거·남은 확인 항목 기준으로 등록 검토 가능 | 사람의 별도 승인 필요 |
| HUMAN_REVIEW / HOLD | 사람 판단 필요 / 기술·증거 문제 등으로 보류 | 승인 자격과 구분. 조치 후 필요한 검증 수행 |
| 공식 승인 | 사람이 동의하고 서버 등록 조건까지 확인 | SRS·TC 반영 또는 SRS만 반영, 출처·판단 기록 보존 |

### 반복 처리의 경계

| 상황 | 처리와 범위 |
|---|---|
| A1·A2·A3 생성 결과의 자동 검사 FAIL | 각 단계/후보의 기존 1회 재작성 범위에서 수정. 수정본도 재검사 |
| 구조 검사 FAIL | 해당 시도의 추가 모델 근거 검토는 생략. 검토 생략을 PASS로 간주하지 않음 |
| 모델 근거 검토 UNSUPPORTED, 인용/대상 연결 오류 | FAIL 피드백. 남은 재작성 기회가 없으면 중단 |
| 모델 근거 검토 UNCERTAIN | REVIEW로 해당 인계 중단. 답을 추측하는 재작성 금지 |
| 모델 응답 누락·호출 오류 | ERROR 기록. 생성/검토 SDK 자동 재시도 0회. 통과로 대체하지 않음 |
| 컴파일 정적 검사 실패·제품 시험 실패 | 위 생성 재작성 분기와 별개. 이 실패 뒤 무제한 코드 수정/재실행 없음 |
| 한 A3 후보 미지원/검토 필요 | 후보 제외와 이유를 기록. 다른 독립 후보 및 후속 보고 가능. 내부 오류는 ERROR로 별도 집계 |
| 시험 시간 초과 | 프로세스 트리 종료·증거/오류 기록. 제품 성공으로 집계하지 않음 |
| API 총 호출 제한 | 생성과 검토를 모두 세어야 함. 현재 CLI의 보편적인 전역 예산 기능으로 오해하지 않음; 승인 실행 래퍼의 한도와 별개 |

### 전체 Checkpoint 규칙 목록

아래는 번호를 기준으로 묶은 업무 규칙입니다. 한 번호 안에 여러 조건문이 있고, 동일 번호가 성공/실패 경로에 반복될 수 있습니다. 현재/과거 적용 조건은 색인의 `guards`와 소스의 호출 옵션에서 확인합니다. **표의 항목 수는 검사 실행 횟수도 분기 테스트 커버리지도 아닙니다.**

### 누락과 문서 노후화를 확인하는 방법

1. [정적 색인](../../docs/logic_inventory.json)은 전체 `src/*.py`의 함수/클래스, if/삼항식/불리언 단락 평가, 반복/내포식 필터, try/except, raise/return/break/continue, with, match, assert를 자동 추출합니다. 각 항목에 원본 행·함수·조건식·상위 if/else를 남깁니다. 스키마 선언·상태값·Checkpoint 호출·프롬프트/생성 코드 문자열 위치도 함께 찾을 수 있습니다.
2. baseline 테스트·승인 자동화·촬영 보조는 별도 파일 항목으로 포함합니다. 제품/포폴 HTML의 인라인 JavaScript와 이벤트 핸들러도 Acorn으로 파싱해 조건·반복·예외·종료·단락 평가·선택적 접근을 색인화합니다. 외부 script 라이브러리 내부는 포함하지 않습니다. 동적 생성 Python/JavaScript는 builder/문자열 위치를 연결한 것이지 모든 생성 변형을 실행한 결과가 아닙니다.
3. 색인 생성기는 소스를 파싱할 뿐 import·모델 호출·브라우저 시험·공식 승인을 하지 않습니다. 파일 해시와 색인을 다시 대조하면 코드 변경 후 목록이 낡았는지 알 수 있습니다.
4. 이 목록은 **정해진 범위의 정적 누락 방지 장치이지, 전체 경로 테스트 완료나 모든 의미 규칙의 수작업 검수 완료 주장이 아닙니다.** 테스트와 실제 API 검증 상태는 인계 문서에서 별도로 관리합니다. 외부 라이브러리 내부·프로젝트 2·과거 Run·ignored 임시 스크립트는 대상 밖입니다.

색인 갱신에는 Python 3.10+와 Node가 필요합니다. 로컬 Acorn 또는 Node에 내장된 Acorn을 사용하며 별도 다운로드/설치는 하지 않습니다. 내장 파서 경로는 Node 내부 구현이므로 배포판에 따라 없을 수 있습니다. 그 경우 JavaScript를 몰래 생략하지 않고 실패합니다. 사용한 파서와 Node 버전은 색인에 남깁니다.

```powershell
python scripts/audit_logic_inventory.py --self-test
python scripts/audit_logic_inventory.py          # 현재 소스로 기술 색인 갱신
python scripts/audit_logic_inventory.py --check  # 변경 없이 현재 소스와 대조
```

### 미실행·미사용·중복 코드를 구분하는 기준

[분기 감사 색인](../../docs/branch_audit.json)은 이전 미실행 목록의 각 분기를 기준 커밋·함수·조건·목적·유지 사유·재검증 상태에 연결합니다. `scripts/audit_branch_coverage.py`가 기준 커밋 소스와 현재 소스의 변하지 않은 행을 대조합니다. 이는 보수적인 정적 분류이며, `STILL_NOT_OBSERVED`는 삭제 판정이 아닙니다. 줄이 바뀐 항목은 `SOURCE_CHANGED_REQUIRES_REVIEW`로 남기고 커버리지 개선으로 자동 계산하지 않습니다. 관련 테스트 이름도 해당 분기를 통과했다는 증거와 구분합니다.

| 구분 | 사용되는 상황 | 정리 원칙 |
|---|---|---|
| 측정에서 누락된 실행 | Playwright 동기 API의 greenlet 전환, 별도 CLI 프로세스 | 측정 조건/직접 재현부터 확인. 미사용으로 삭제하지 않음 |
| 다른 입력·시험 유형 | 여러 후보, 조회·변경·차단, 선택/입력/해제와 복원 | 요구사항·상태별 테스트 보강 |
| 실패/무결성·승인 경계 | 변조된 해시, 파일 누락, 잘못된 결과, 중복 승인 | 정상 실행에서 드물어도 보호 유지. 임시 복사본에서 반례 검사 |
| 과거/플랫폼 호환 | 이전 Run 계약, 기존 import 이름, Windows 외 잠금 | 현재 환경의 미실행을 삭제 근거로 삼지 않음 |
| 앞선 스키마가 제한한 분기 | MODIFIED만 허용, 기대결과 최소 1건 | 정상 CLI에서는 도달이 제한됨을 기록. 직접 호출/향후 계약 변경을 고려해 유지 |
| 같은 책임의 반복 구현 | CP1·CP2 상태 우선순위, 단일/다중 후보 선택 래퍼 | 정책을 바꾸지 않고 공통 구현으로 위임 |

CP1·CP2는 공통 상태 집계에서 `ERROR → FAIL → REVIEW → PASS` 우선순위를 유지합니다. 현재 두 검사기가 ERROR 항목을 만들지 않는다는 이유로 공통 오류 상태를 삭제하지 않습니다. `qa_pipeline_v2`의 재수출 이름과 단일 후보 선택 호환 함수는 유지합니다. 같은 해시를 인계 시점과 승인 시점에 다시 확인하는 것은 서로 다른 경계의 보호입니다.

부모 Python 분기 커버리지는 자식 프로세스의 생성 코드·브라우저 JavaScript·모델 의미 판단을 포함하지 않습니다. greenlet 추적이 없는 측정에서는 브라우저 관찰 함수 내부를 실제 실행해도 누락할 수 있습니다. 이 환경에서는 greenlet와 thread 동시 추적 시 Windows 접근 오류가 발생했으므로 결과를 폐기하고, greenlet 단독·pytest 캡처 비활성(`-s`) 측정과 정상 pytest 실행 결과를 구분합니다. 측정 환경별 결과와 실제 수치는 인계 문서에 기록합니다.

### 앞으로 정리할 우선순위

- 먼저 현재 실행/과거 호환/모델 안내/실제 차단을 구분해 읽습니다. 오래된 단어 규칙이 파일에 남아 있다는 이유로 새 실행에서도 모두 작동한다고 보지 않습니다.
- 사전조건 검사 번호는 CP3-006D로 분리했고 조작 순서는 CP3-006A를 유지합니다. 과거 저장 체크포인트는 그대로 읽으며 현재 승인 재검사에서 두 원인을 구분합니다.
- 계약 옵션·재수출 import의 명시화는 후속 정리 후보입니다. 파일 안에서 직접 참조되지 않은 import도 `__all__`·별칭·CLI 콜백을 통해 쓰일 수 있어 일괄 삭제하지 않았습니다.
- 공통 모델 검토는 제한된 실제 호출 비교를 수행했지만 판정 일관성과 최신 전체 흐름 성공은 아직 확인이 필요합니다. 개별 검토 통과를 단계 전체의 성공으로 해석하지 않으며 실제 결과와 남은 검증은 인계 문서에 기록합니다.

### 현재 공통 근거 검토 계약

새 인계 버전은 **Agent 1 2.11 / Agent 2 3.13 / Agent 3 4.10**이며 `grounding_contract=1.0`을 요구합니다. 생성 프롬프트는 각각 2.23 / 2.54 / 3.43(실행 정의 없는 과거 TC는 3.42), 공통 검토 프롬프트/캐시 키는 grounding-1.17입니다. 저장 검토 응답의 구조 계약은 grounding-1.0으로 유지합니다. 새 Agent 2는 `procedure_preservation_contract=2.0`을 사용합니다. A2/A3의 `review_responsibility_contract=1.0`은 대응 프롬프트·인계 버전·필수 검토·문장 정책과 함께 검증합니다. 표시가 빠지거나 구버전 표시와 섞이면 거부하고, 과거 실행은 기존 입력/검사로 재구성합니다. 세 단계의 `output_tolerance_contract=1.0`은 검토 입력 해시에도 포함되며, A2 2.46 이후에는 필수입니다. 없는/알 수 없는 계약·이전 검토 재사용으로 새 정책의 인계를 우회하지 않습니다. 아래 세부 계약의 이전 버전 설명은 각 보호 장치가 도입된 시점입니다.

새 A1/A2/A3는 `task_boundary_contract=1.3`입니다. 해당 프롬프트·기존 구조 버전·필수 검토와 함께 확인하고 검토 입력 해시에 포함합니다. 과거 1.0~1.2의 검사와 검토 입력은 보존하며 새 표시에 과거 검토를 재사용할 수 없습니다. 1.1 이후에는 검토 항목 누락·중복·유효하지 않은 원문 인용·근거 없는 지지/반려를 산출물 FAIL이 아닌 검토 응답 오류로 중단합니다. 1.3에서 정확·유일한 호스트 계약 전체 문장의 출처 ID 보정만 예외이며 보정 내역을 기록합니다. 받은 응답과 사용량은 진단 자료로 보존하고, 의미상 UNSUPPORTED만 기존 재작성에 사용하며 UNCERTAIN은 사람 확인으로 중단합니다.

1.2의 Agent 1은 요청의 여러 실제 인용을 출처·조건 전달·영향 범위에서 같은 함수로 확인합니다. Agent 3은 관찰된 기존 제어 필드와 표시값 연결을 작성/검토에 동일하게 전달하고 TC의 영문 필드명 등장 여부로 내부 경로를 숨기지 않습니다. UI와 내부 유한값의 의미 일치는 필수 원문 검토가 담당하며 Selector·읽기 지원·장비 ID·누락·시점·실측·복원은 기존 코드가 확인합니다. 어댑터는 사용 가능한 기능의 근거이지 TC 범위의 권한이 아닙니다. 없는 기능을 유사한 AUTO 모드로 대체하면 안 됩니다. 코드 검사에서 유효한 enum이라도 TC와 다른 값일 수 있으므로 모델 검토의 오판 위험은 남습니다.

작성·검토에는 같은 호스트 실행 계약을 전달합니다. 일반 복원은 restoration과 restore_required로 판단하고 과거 HVAC 전용 플래그 false를 전체 복원 비활성으로 해석하지 않습니다. 대상 선택 완료 대기, 준비 전 자동 기록, 대상 ID로 내부값 읽기, 복원 확인의 ER 연결, 사람 승인 정책을 제품 기대값과 구분합니다. 계약은 기능 설명이지 실행 성공 증거가 아닙니다. 새 작성 지침 버전의 검토 입력에만 포함하고 과거 검토 입력 해시는 그대로 재구성합니다.

현재 작성·검토 지침은 요청된 시험, 준비 상태, 참고용 SRS를 구분합니다. 준비→목표 상태 한 번의 확인은 SINGLE_FLOW이며 준비값은 본 시험의 requested 값이 아닙니다. initial_mode·requested_mode(s)는 운전 모드 필드이며 다른 관제점의 값을 넣지 않습니다. 전원·풍량·잠금은 기존 사전조건·단계·기대결과 필드에 기록합니다. Condition statement는 이번 범위를 설명하고 source_text는 실제 인용을 보존합니다. 보조_근거 연결은 인용된 모든 선택지의 시험 완료를 뜻하지 않습니다. 명시적 복수 시험 누락·요청 밖 조작·미실행 범위 확인 주장은 반려하며, 요구와 제외가 충돌하면 사람 확인으로 남깁니다. 이 지침만으로 모델의 올바른 생성·판정을 보장하지 않습니다.

공통 검토 1.4는 Agent 1의 `decision`을 공식 승인 문구가 아니라 입력의 충분성에 따른 후속 설계 진행 판단으로 검토합니다. 원문에 PROCEED 또는 승인이라는 단어가 없어도 실제 시험 조건을 근거로 판단하며, 누락·충돌·불명확성은 그대로 검토합니다. 과거 REVIEW 기록을 새 PASS로 바꾸거나 인계하지 않습니다.

Agent 2 3.13은 REQUEST_TRACE_ONLY 조건이 포함된 ER에서 근거 ID를 하나로 제한하던 CP2-017의 개수 제한만 새 실행에 적용하지 않습니다. 복수 근거와 복수 검증 사실을 구분하며 없는 ID·TC 밖 연결·명시 수치·원문 근거·실제 검사 누락은 기존 구조/의미 검사 대상으로 유지합니다. 초기·재작성·저장 재검증은 `_agent2_checkpoint_options`에서, 승인 직전 재검사도 같은 계약 버전에서 `allow_multiple_trace_sources`를 선택합니다. 기본값은 과거 직접 호출 호환을 위해 False이며 3.12 이하 저장 판정·검토 입력은 그대로 읽습니다. 기존 실패 기록을 새 PASS로 덮어쓰지 않습니다.

작성 지침 2.40/검토 지침 1.3은 유지 SRS 전체와 이번 요청의 시험 범위를 구분하고, 요청 원문·명시적 제외와 후보/기존 TC를 합친 검사 범위를 대조하도록 안내합니다. 모든 확정 조건의 역방향 검토는 유지하며 ‘유지’라는 이유로 자동 면제하지 않습니다. 요구된 대상·동작·확인값 누락, 일부 검증을 전체 SRS 검증으로 주장하는 것은 허용하지 않고 범위 불명확/요구·제외 충돌은 UNCERTAIN으로 처리하도록 합니다. 조건을 코드로 삭제·자동 축소하지 않으며, 이 범위 판단은 모델의 의미 검토로서 실제 판정 정확성을 보장하지 않습니다.

작성 지침 2.41은 기존 TC를 전체 단위로 재사용한다는 실행 계약을 명시합니다. 일부 검사가 관련돼 있어도 TC 전체에 명시적 제외와 충돌하는 검사가 있으면 선택하지 않으며, 기존 assertion을 지우거나 일부만 실행했다고 가정하지 않습니다. 요청된 변경 후보가 실제로 확인하는 유지 기준은 함께 연결할 수 있지만 관련 없는 유지 조건을 붙이거나 요청 밖 회귀를 새로 만들 수는 없습니다. 기존 CP2 연결·값·중복 검사와 의미 검토는 유지합니다. 이 지침 전달의 로컬 검사와 실제 새 TC 생성 성공 여부는 구분합니다.

Agent 2 2.39는 설명란에 내부 분류명·정책 키·코드 검사 과정을 반복하지 않고 실제 시험 범위와 확인 사항만 쓰도록 안내합니다. 구조화된 분류·SRS 개정안은 그대로 유지합니다. 검토 지침 1.2는 근거 있는 시험에서 변경·검증하는 대상의 준비 전 값을 기록하고 같은 관찰 위치에서 복원 후 비교하는 절차를 QA 복원 절차로 구분합니다. 관련 제품 원문 인용은 계속 필요하며 새 확인 대상·기대값·임의 초기값·검사 누락은 허용하지 않습니다. 준비·복원 검토를 생략하거나 실행 검사 분기를 추가한 것이 아닙니다. 지침 전달 검증과 실제 모델의 정상/오류 판정 확인은 구분합니다.

Agent 2 3.12부터 생성 결과가 아니라 입력의 모든 확정 조건을 기준으로 `CONDITION_COVERAGE` 검토 항목을 열거합니다. 조건별 후보 TC 전체·기대결과·선택한 기존 TC의 실제 검증 동작을 함께 전달하므로, 결과 삭제로 그 조건의 검토 항목이 사라지지 않습니다. 같은 Requirement ID만으로 다른 모드·값의 검증을 대체할 수 있는지는 의미 검토에서 판단합니다. 준비·조작·복원 조건은 절차 연결을 검토하며 모두 제품 기대결과로 만들지 않습니다. 모델의 SUPPORTED 오판 가능성은 남고 실제 검출 정확도는 별도 Live 평가 대상입니다. 3.11의 저장 검토는 당시 입력 형태로 재검증합니다.

Agent 3 4.10의 `plan_fidelity_contract=1.2`는 `window.__vccs.devices[index]`로 내부값을 읽을 때 해당 경로의 관찰된 `.id`가 `target_device_id`와 같은지 확인합니다(CP3-004). 인덱스와 장비 ID가 같다고 추정하지 않으며 신원을 확인할 수 없으면 보완 대상으로 반환합니다. 최초·재작성·실행 인계·사람 승인 재검사에 같은 기준을 적용합니다. 과거 4.9의 계약 1.1은 소급 변경하지 않습니다. 복합 기대결과의 의미 누락은 기존 single_fact/Assertion 연결 모델 검토로 다루고, 자연어에서 필드 목록을 추정하는 새 단어 규칙은 만들지 않습니다.

실행 결과의 `candidate_result`와 `candidate_results[0]`가 함께 존재할 때는 내용이 같아야 합니다. 다르면 성공/실패 어느 한쪽으로 덮지 않고 스키마 오류로 중단합니다. 한쪽만 제공된 과거 형식의 보충은 유지합니다. 사람용 검토서는 UI·Notion과 공통 TC 조회 함수를 사용하며, 승인 TC 스냅샷 해시가 틀리면 현재 자산으로 대체해 숨기지 않습니다. 실행 결과 검토 항목 수는 SRS 개정·TC 등록 승인 및 미결 정보 수와 구분합니다.

| 단계 | 별도 모델이 검토하는 내용 | 근거 |
|---|---|---|
| Agent 1 | 조건·역할·영향·절차/제외/정보부족 분류 | 최초 변경 요청·SRS |

코드가 검토 대상을 열거하고 모델은 모든 항목에 `SUPPORTED / UNSUPPORTED / UNCERTAIN`, 인용문과 이유를 반환합니다. `SUPPORTED`의 인용은 실제 원문에 있어야 합니다. 누락·중복·순서/ID 오류·없는 인용은 실패입니다. 기대결과의 `single_fact`는 독립된 사실 하나인지 모델이 판단한 값이며 마침표/단어 규칙이 아닙니다. 여러 사실을 묶은 기대결과는 기존 요구를 보존해 분리하도록 반환합니다. 코드가 인용의 의미적 지지 여부 자체를 증명하는 것은 아닙니다.

생성·검토 클라이언트의 SDK 전송 자동 재시도는 모두 0회입니다. 명시적인 단계 재작성만 사용합니다. 외부에서 지정한 총 호출 예산은 생성뿐 아니라 검토 전송도 함께 계수해야 하며 예산 소진을 통과로 처리하지 않습니다.

구조 검사 실패 시 검토 API는 생략합니다. 새 책임 계약에서 의미 검토로 옮긴 문장/누락은 구조 단계에서 막히지 않으므로, 이전에 생략됐던 검토 호출과 입력량이 증가할 수 있습니다. 새 API 단계나 승인 상한을 추가하지 않으며 모든 생성·검토·재작성·실패를 기존 총량 안에서 계산합니다. 근거 부족/연결 실패는 기존 1회 재작성의 피드백으로 전달하고 수정본도 다시 검토합니다. 불확실은 REVIEW로 중단하며, Agent 1의 부분 진행 REVIEW와 달리 근거 검토의 REVIEW는 다음 단계 진행을 허용하지 않습니다. 통신/응답 오류는 ERROR 경로로 남기며 통과로 대체하거나 검토기를 자동 재호출하지 않습니다. 생성 시도와 별도로 검토 모델·응답 ID·사용량을 기록하고 총 사용량에 합산합니다.

`agentN_grounding_input_attempt_K.json`은 전송할 데이터 미리보기, `agentN_grounding_review_attempt_K.json`과 `agentN_grounding_review.json`은 시도별/최종 검토 기록입니다. Manifest는 최종 검토 파일 SHA-256을 보존합니다. 입력 전체와 생성 산출물의 해시를 묶어 수정 전 검토 재사용을 차단하고, 후속 인계·사람 승인 경로에서 다시 확인합니다. 저장 재검사는 API를 재호출하지 않습니다. 과거 기록은 당시 계약으로 읽으며 새 검토가 있었다고 소급 표시하지 않습니다.

근거 있는 미구현 기능은 유효한 시험 요구일 수 있습니다. UI 부재만으로 요구를 삭제하지 않으며 기존 자동화 지원 분기와 실제 제품 시험 결과를 따릅니다. 모델 검토는 생성자와 별도 호출이지만 같은 계열 모델일 수 있어 독립적인 정답 보장이 아닙니다. 새 검토의 실제 정확도·정상 표현 오탐·일관성은 별도 Live 평가가 필요합니다. 새 연결표 후보 1개는 재작성 없이 생성 2회+검토 3회이며, A1·2의 각 1회 재작성을 포함하면 최대 생성 4회+검토 5회입니다. 과거 모델 위치 생성 경로는 당시 호출 구조를 유지하며, 모델 호출 승인 상한을 늘리지 않습니다.

공통 구현은 `src/qa_pipeline_grounding.py`에 두고 세 단계의 실행 연결은 `qa_pipeline_execution.py`에서 관리합니다. 순수 `evaluate_checkpoint1/2/3`는 기존 결정론적 코드 검사이며 단독 호출로 새 모델 검토를 실행하지 않습니다. 실제 CLI와 저장 로더는 두 결과를 합쳐 최종 Checkpoint를 판정합니다.

사용자 확인 질문은 새 검증 실행에서 Agent 1 분석 파일의 Manifest 해시를 검증한 뒤 `사용자 확인 요청:` 접두어로 기존 `최종_확인_사항`에 전달합니다. Agent 4 JSON·사람 최종 검토서·해당 필드를 보여주는 UI에서 확인할 수 있습니다. 질문 원문을 보존하고 중복만 제거하며, 답을 추정하거나 자동 승인으로 해석하지 않습니다. 기존 실행 보고서와 외부 게시물을 소급 갱신하지 않습니다.

## 1. 무엇을 하는 프로젝트인가

기존 제품 SRS와 베이직 TC가 있는 상태에서 새로운 변경 요청을 받습니다. 이미 관리하는 TC로 확인할 수 있는 조건은 재사용하고, 새로 필요한 조건만 후보 TC로 만들어 시험합니다. 결과와 근거를 보고 사람이 공식 자산으로 채택할지 판단합니다.

| 용어 | 의미 |
|---|---|
| SRS | 제품이 어떻게 동작해야 하는지 정한 요구사항 |
| TC | 사전조건·절차·기대 결과·복원을 가진 테스트케이스 |
| 기존/베이직 TC | V1 기준 TC와 사람이 승인한 V2 공식 TC |
| 후보 TC | 이번 변경을 위해 만든 TC. 시험 통과 후에도 공식 승인 전에는 후보 |
| 관련 회귀 | 이번 변경과 관련 있고 여전히 유효한 기존 TC의 재실행 |
| Checkpoint(CP) | Agent 산출물의 구조·근거·값·인계를 검사하는 자동 단계 |
| Run | 변경 요청 한 번의 입력·분석·TC·시험·보고 묶음 |
| 후보 시험(Candidate Trial) | 생성한 자동화 코드를 별도 임시 위치에서 실제 실행하는 과정 |

```text
기존 SRS + 기존 TC + 변경 요청
  → Agent 1 / CP1: 확정 조건·정보 부족 분리
  → Agent 2 / CP2: 기존 TC 대조·변경분 후보 설계·SRS 개정 제안
  → Agent 3 / CP3: 후보별 UI 위치 연결·TC 정의 조립·컴파일·시험
  → 변경 검증: 완료 후보 확인·환경 점검·선택한 기존 TC 실행
  → Agent 4 / CP4: 원인 분류·증거/집계 확인·보고
  → 사람: SRS 개정·공식 TC 등록 승인 또는 보류
  → 승인한 자산을 다음 Run에서 기존 TC로 대조
```

Agent 1·2는 모델이 구조화 JSON을 작성합니다. 새 Agent 2는 상세 TC와 함께 실행 정의를 작성하고, 새 Agent 3는 제품 연결표로 그 ID에 실제 UI/내부값 위치를 연결하며 위치 생성 AI는 사용하지 않습니다. 별도 의미 검토 AI는 유지합니다. 프로그램이 TC의 조작·값·순서·시점을 그대로 조립하고 기존 컴파일러가 Playwright Python을 생성합니다. 실행 정의가 없는 과거 TC는 당시 계획 생성 경로를 유지합니다. Agent 4는 생성형 AI를 사용하지 않습니다.

| 모드별 온도 범위 | AUTO 18~30°C, COOL·HEAT 16~30°C, FAN·DRY 온도 비활성화 요청 | 조건·경계값 설계와 기대/관찰 비교 |
| 제품 불일치 | 잠금 시 온도 버튼 비활성화 요구와 실제 활성 상태를 비교 | 실패 증거와 제품 불일치 후보 분류 |
| 정상 변경의 후속 승인 | PASS 후보와 SRS 개정안을 사람이 검토 | 공식 등록 또는 보류, 이후 기존 TC 재사용 |

위 기능명·값은 시연용 예시입니다. 요구사항을 생성 규칙에 고정하지 않습니다. 정상 요청에는 MED 변경만 요청하는 입력과 HIGH 유지 조건을 포함한 입력이 있습니다. 기존 TC 선택 여부는 해당 Run의 실제 결과로 확인하며 항상 HIGH를 실행한다고 고정하지 않습니다. 짧은 소개 영상은 정상 변경·사람 승인, 제품 불일치, 미정 조건 분리의 세 사례로 구성하며 온도 범위는 추가 자료로 유지합니다.

잠금 실패 사례는 실패 증거로 보존합니다. 제품을 고치거나 기대값을 바꿔 이 결과를 PASS로 만드는 자동 절차는 없습니다. 제품 TC가 실패해도 그 실패의 증거와 집계가 유효하면 CP4는 통과할 수 있습니다.

영상은 정상 변경·관련 TC 재사용·사람의 SRS/TC 등록을 먼저 보여주고, 제품 불일치와 미정 조건 사례를 비교합니다. 로컬 실제 실행 영상의 대기 구간을 편집하면 표시합니다. 공개 HTML의 저장 데모, 실제 API 실행, 저장된 실제 결과 조회를 구분합니다. 루트 project.html은 세로 스크롤형 정적 소개 페이지이며, 실행 결과에는 풍량·잠금·미정 조건이 남은 사례를, 분석·보고 이후에는 실제 자산 등록 상태를 보여줍니다. 초기 온도 시험은 별도 추가 사례로 유지합니다. V1 원본은 보존하며, 사용자 요청으로 V2 소개에 V1의 표현 형식을 참고했습니다. 영상 미촬영 상태를 표시하고 당시 공개 증거와 최신 로컬 실행을 구분합니다.

#### 승인 전 영상 미리보기 생성

V1의 녹화 원리를 참고한 V2 전용 `scripts/record_demo.py`는 로컬 브리지에서 저장된 실제 Run을 읽고 Playwright 녹화와 FFmpeg 편집으로 무음 자막 영상을 만듭니다. V1 스크립트·영상·고정 결과를 복사하거나 실행하지 않습니다. OBS는 필수가 아니며 `imageio-ffmpeg` 패키지의 FFmpeg를 사용합니다.

```powershell
python -m pip install -e ".[agent3,video]"
python scripts/record_demo.py --smoke  # 4초 시험 녹화
python scripts/record_demo.py          # 90초 승인 전 미리보기
```

출력은 새 `runs/manual_checks/video-preview-.../` 폴더에만 생성되며 기존 폴더를 덮어쓰지 않습니다. 원본 화면은 수정하지 않고 촬영 세션에서 글자 확대와 설명 자막만 적용합니다. 각 장면의 준비 대기 구간을 잘라 합친 편집 영상이며 실시간 전체 실행이 아닙니다. 선택한 Run의 본문 ID가 일치한 뒤 녹화하고, 원본 증거·SRS·공식 자산 해시 보존과 MP4 디코딩/길이를 검사합니다.

스크립트는 현재 로컬 브리지의 GET 조회만 허용하며 새 API 실행·외부 접속·승인/보류 POST를 차단합니다. 원본 MED가 미등록인 상태의 **승인 전 미리보기**만 생성합니다. 위 최종본 대본의 39~51초 승인 완료 구간은 대신 미등록 검토 화면으로 표시하고 마지막 자막도 원본 불변으로 바꿉니다. 이 미리보기를 실제 공식 등록 완료 영상으로 게시하지 않습니다. 실제 승인 장면은 사용자 승인과 별도 녹화 후 교체해야 합니다.

원본이 이미 등록됐다면 이 도구는 중단합니다. 승인 전 상태를 재연하기 위해 SRS·Registry를 되돌리지 않습니다. 사용자의 명시적 지시에 따라 대행 등록할 때에는 검토자·메모에 승인 주체와 대행 사실을 구분해 기록하며, 해당 지시를 다른 후보의 포괄 승인으로 사용하지 않습니다.

공식 자산 파일은 Registry의 SHA-256과 연결되므로 Git에서도 줄바꿈을 변환하지 않고 원래 바이트를 보존합니다. 파일 내용을 편집하거나 포맷팅한 뒤 해시만 맞추는 방식으로 승인 증거를 갱신하지 않습니다.

이 도구의 촬영 범위는 로컬 Run 요약·상세 TC·실행 결과·승인 전 문구입니다. 별도 제품 시험 브라우저의 움직임이나 실제 Notion 페이지 방문을 녹화한 것은 아닙니다. 최종 대본의 해당 장면은 저장된 시험 증거/승인된 외부 화면 자료와 별도로 편집해야 합니다. 미리보기의 페이지 오류·파일 무결성 검사는 최종 영상의 전체 내용 검수를 대신하지 않습니다.

#### 실제 클릭과 녹화 체크리스트

- 정상 사례는 **조회할 Run** 선택 후 본문 Run ID가 같은 값으로 바뀐 것을 확인합니다. 전환 대기 중 이전 결과를 촬영하지 않습니다. Agent 버튼으로 단계를 바꾸고 TC ID를 눌러 상세를 펼칩니다. UI는 실제 장비 조작을 중계하지 않으므로 실행 중 장면은 저장된 Trial 증거나 별도 브라우저 원본 녹화로 보여줍니다.
- 등록 전: 원본 SRS·Registry·승인 대상 Run의 백업과 해시를 남기고, 최신 자동 등록 조건이 충족됐는지 다시 확인합니다. 검토자는 본인 이름과 실제 검토 근거를 입력합니다. **SRS 동의 → 공식 TC·자동화 등록 승인 → 확인: 공식 자산 등록**의 두 번 클릭을 녹화합니다. 앞선 리허설은 임시 사본이며 실제 공식 등록으로 소개하지 않습니다.
- 등록 후: 화면의 공식 TC ID, `approved_assets/registry.json`, 해당 TC JSON과 자동화 파일, SRS의 MED 문구 추가를 확인합니다. 공식 ID는 화면에 나온 실제 값을 사용하며 번호를 미리 고정하지 않습니다. 등록 후 새로고침에서도 완료 상태가 유지돼야 합니다. 단순 JSON 문서 생성이나 Notion 게시를 공식 승인으로 표현하지 않습니다.
- 실패·미정 사례는 **당시 실제 실행 기록 조회**라고 표시합니다. 현재 검사 계약/제품과 차이가 있다는 승인 경고를 숨기거나 과거 Run을 최신 모델 실행처럼 설명하지 않습니다. 실패 결과와 미정 조건은 서로 다른 이유의 사람 검토이며, CP4 PASS는 제품 시험 PASS가 아니라 보고 일관성 검사입니다.
- 편집: 1920×1080 기준 본문 중심으로 확대하고 한 컷의 강조는 1~2개만 둡니다. 긴 JSON 전체나 모델 대기 시간을 90초에 억지로 넣지 않습니다. 실제 승인 쓰기가 늦어지면 완료 시점으로 컷하되 ‘처리 대기 구간 편집’ 표기를 둡니다. API 키·`.env`·로컬 사용자 경로·다른 Notion 페이지는 녹화하지 않습니다.
- 촬영 종료 뒤 영상 길이·자막 겹침·수치/Run ID·승인 후 파일 일치·민감정보를 검수하고 포트폴리오에 영상 링크를 연결합니다. 등록은 자동 원복되지 않습니다. 재촬영을 위해 공식 기준을 임의로 되돌리거나 과거 실패를 덮어쓰지 않습니다.

## 3. 공통 QA 기준과 TC 구성

| 기준 | TC에 담는 내용 |
|---|---|
| 1단계 공통 QA | 해당 규칙의 정상·예외·경계·복구 관점 |
| 2단계 도메인 QA | 올바른 장비 선택, 화면·내부 상태 정합성 |
| 3단계 기능 기준 | 요구사항에 명시된 값·동작·표시 |
| 추적성 | Requirement·확정 조건·단계·기대 결과의 연결 |
| 독립성 | 다른 TC에 의존하지 않는 준비·초기 상태·복원 |
| 이중 검증 | 필요한 경우 같은 동작 직후 화면과 내부 상태 확인 |

하나의 TC는 하나의 관제점에서 하나의 업무 규칙을 검증합니다. 같은 범위의 하한·상한이나 같은 비활성 규칙의 여러 모드는 한 TC로 묶을 수 있습니다. 무관한 요구사항·제어 경로·실패 원인은 분리합니다.

| 조건 구성 | 계약 | 실행 방식 |
|---|---|---|
| 단일 흐름 | SINGLE_FLOW | 한 흐름의 동작과 판정 |
| 독립 입력 조건 | INDEPENDENT_VARIANTS | 조건 사이 재준비·초기화 기록 |
| 순차 전환 자체가 목적 | SEQUENTIAL_TRANSITION | 승인한 전환 순서 유지 |

관찰값 하나마다 기대 결과를 나누고 `verify_after_step`으로 판정 위치를 지정합니다. 화면 표시와 내부 값이라는 이유로 같은 조작을 두 번 반복하지 않습니다. Agent 3는 `after_action_id`로 해당 동작 직후 검증을 배치합니다. REQUIRED 이중 검증은 두 관찰 계층의 판정 단계 집합이 일치해야 합니다. 두 계층 모두 판정 단계가 없는 단일 흐름은 기존 종료 시점 검증을 유지합니다.

CP는 구조·명시 값·연결 관계를 검사합니다. 자연어 의미가 완전히 같은지, 모든 누락을 탐지했는지, 기준에 적은 모든 관점을 시험했는지까지 보장하는 것은 아닙니다.

## 4. Agent 1: 요구사항 분석과 CP1

변경 요청과 관련 SRS에서 변경 전·후 값, Requirement 영향, 출처가 있는 확정 조건, 제외 범위, 정보 부족을 만듭니다. 조건 역할은 변경·유지·보조 근거로 구분합니다. 현재 자동화 지원 여부를 이유로 제품 영향도를 낮추거나 명확한 조건을 버리지 않습니다.

CP1은 요청 ID·변경 유형·Requirement·값 보존, 요청/SRS 근거, 인수 조건의 전달과 진행 판정 일관성을 검사합니다.

새 실행의 CP1-011은 대상 외 VERIFY·UPDATE_REQUIRED에 `scope_evidence`를 요구합니다. 요청에서 나온 긍정 확정 조건 ID, 해당 연관 SRS 원문, 직접 요청/간접 영향 구분을 보존하며 영향 경로는 기존 `reason`에 설명합니다. SRS에 존재한다는 사실이나 같은 화면에서 실행한다는 이유만으로 범위를 추가하지 않습니다. 근거가 없는 항목은 NO_IMPACT로 검토 기록만 남기되, 명시된 요청 조건을 지워 검사를 피해서는 안 됩니다.

- 근거 누락·허위 출처·존재하지 않는 조건 ID·다른 Requirement 연결: FAIL → 기존 제한 재작성 1회 → 미해결 시 차단.
- 분류명은 보존하되 새 CP1-011은 `DIRECT_REQUEST`·`REQUEST_TRACE_ONLY`·`CHANGE_DEPENDENCY`에 서로 다른 통과/보류 규칙을 적용하지 않습니다. 요청 문장 안에 SRS ID·전체 SRS 문장을 다시 적게 하는 조건도 제거했습니다.
- 실제 요청 원문 조건·연관 SRS 인용·Requirement 연결은 여전히 필요합니다. 인용과 연결이 맞다는 것만으로 검사 범위가 타당하다고 인정하지 않습니다.
- 범위의 의미는 기존 필수 검토가 판단합니다. 요청 밖 기능·기대값·검사 확대나 필요한 조건 누락은 UNSUPPORTED → 제한 재작성 → 미해결 차단, 실제 판단 근거 부족은 UNCERTAIN → REVIEW·PAUSE입니다. 준비/제외를 제품 조건으로 삼는 오류도 의미 검토 대상입니다. 새 검사기나 AI 단계를 추가하지 않습니다.

새 Agent 1 Manifest 2.11은 `scope_guard_contract=1.2`와 prompt 2.23을 함께 저장하며 범위 정책을 검토 입력 해시에 포함합니다. 이전 1.0/1.1 범위 계약의 분류별 차단 코드는 과거 기록 재검증에만 남깁니다. 새 정책 누락·알 수 없는 정책·버전 혼합 및 과거 검토 응답 재사용은 거부합니다. 입력 분류·SRS 인용·문장 정책과 정보 부족 전달 계약은 유지합니다. 이 지침이 모델의 올바른 해석을 보장하지는 않습니다. 과거 결과나 기존 공식 TC 원문을 수정하지 않습니다.

새 정책은 분석·설계의 상태 단어·경계 표현 비교와 특정 유지 표현 요구를 차단 기준에서 제외합니다. 근거 밖 수치, 코드·수치의 부분 문자열 인용, Requirement별 원문 누락은 계속 검사합니다. 같은 값으로 다른 의미를 작성한 오류를 놓칠 수 있으므로 CP 통과를 의미 정확성으로 설명하지 않습니다.

| 분석 결과 | 후속 처리 |
|---|---|
| PROCEED | 확정 범위 계속 |
| PARTIAL_PROCEED | 확정 범위 계속, 정보 부족은 별도 보고 |
| WAITING_FOR_USER | 핵심 시험 범위를 정할 수 없어 보류 |

기존 REVIEW는 확정 범위가 있으면 마지막 확인 사항으로 전달합니다. 필수 의미 검토의 UNCERTAIN은 PROCEED·PARTIAL_PROCEED여도 인계를 멈춥니다. 과거 범위 계약 1.0/1.1의 CP1-011 REVIEW·PAUSE도 보존합니다. 중단 Run을 이어 붙이는 재개 기능은 없으며, 새 정책 검증은 새 Run으로 수행합니다.

PARTIAL_PROCEED의 정보 부족·제외된 정보 부족·제외 범위 연결은 유지합니다. 새 정책은 미정 여부를 특정 단어로 판정하지 않습니다. 원문이 제품 조건·절차·제외·정보 부족 중 어디에 전달됐는지 확인하되 분류 자체가 올바른지 자동 증명하지는 않습니다. 필수 제품 조건을 절차나 제외로 잘못 분류하는 위험은 평가·사람 검토 대상입니다.

시험 시작 전 확인·종료 후 복원 메모는 제품 판정 조건과 구분해 Agent 2로 전달합니다.

Agent 1 입력에는 인수 조건의 원문과 가능한 전달 위치를 제공합니다. 절차는 `procedure_notes`에 입력 원문 그대로 명시합니다. CP1-012는 입력에 없는 절차·중복·제품 조건/제외/정보 부족/제외된 정보 부족과의 중복 분류를 차단합니다. `[준비]`·`[복원]`·`[시험 절차 메모]`로 시작하는 인수 조건은 같은 전달 목록을 사용해 절차 원문 보존을 요구합니다. 같은 원문이 요청의 `out_of_scope`에도 있으면 제외가 우선이며 절차와 중복할 수 없습니다. 본문의 동사·동의어를 정규식으로 다시 분류하지 않습니다. 새 절차 2.0은 사전조건·단계·복원 반영 여부를 필수 모델 검토에서 확인하며, 기존 TC만 선택해도 절차를 검토 대상으로 유지하고 최종 사람 검토 메모로 인계합니다.

기존 기록의 누락 필드는 조회 시 빈 목록으로 읽으며 과거 원문에서 새 필드를 추정하지 않습니다. 이를 새 실행의 ‘절차 없음’으로 사용하지 않도록 새 `agent2` 실행은 검증된 Agent 1 2.8·2.9·2.10 / `STRUCTURAL_ONLY_V1` 인계만 받습니다. 과거 Agent 1에서 시작하려 하면 모델 클라이언트 생성·실행 예약·카탈로그 사본 작성 전에 새 Agent 1 Run을 안내하고 중단합니다. 완료된 과거 Agent 1·2 결과의 조회·당시 계약 재검증은 그대로 지원하며 기존 파일을 바꾸지 않습니다.

Agent 1·2의 문장 의미 추정 검사를 자동 평가 모델로 대체하지 않았습니다. 모든 미지원 문장을 REVIEW로 보내는 기능도 아닙니다. CP1의 정보 부족/범위 보류와 사람의 최종 승인, 별도 반복 평가를 유지합니다. Agent 3에서는 UI 이름·설명·내부 경로 간 단어 중첩 요구를 제거하지만, 실제 값의 원문 근거·사전조건 읽기 지원·조작 순서·표시값 축약 방지 검사는 실행 보호를 위해 유지합니다. 따라서 문자열 처리가 모두 사라진 것은 아닙니다.

과거 정책 설명입니다. `task_boundary_contract` 표시가 없는 실행에 아래 범위 포함 검사를 적용하며, 새 실행에서는 원문 역방향 의미 검토로 대체합니다. 배경 설명의 유지 온도 범위는 Agent 1 계약 2.9부터 대상 SRS 전체 원문·같은 Requirement ID·UNCHANGED 역할로 근거를 확인합니다. 분석 설명이 원문과 똑같아야 한다는 요구는 제거했습니다. 원문 변조·다른 요구사항의 숫자 차용·새 수치·변경 후 정책을 기존 SRS로 대체하는 것은 계속 차단합니다. 같은 값의 반대 의미까지 자동 판별하는 것은 아니며, 2.8 이하의 저장 판정은 당시 문장 일치 기준으로 읽습니다.

2.10의 SRS 인용 계약은 `|`를 원문 조각 구분자로만 사용합니다. 조각의 순서·개수로 필드 종류를 가정하지 않습니다. 각 조각은 연결된 Requirement의 요구사항 또는 인수 기준 한 필드 안에 연속 원문으로 존재해야 하고, 각 연결 ID도 최소 한 조각의 근거가 있어야 합니다. 여러 ID를 연결한 경우 출처 없는 조각과 근거 없는 ID 추가를 모두 거부합니다. 범위 근거 `scope_evidence.srs_source_text`는 해당 effect의 ID만 사용합니다. 빈 조각을 조용히 제거하지 않으며 코드·수치 토큰 경계 검사를 유지합니다. 단일 인용과 2.9 이하의 저장 판정은 기존 방식입니다.

과거 정책 설명입니다. `task_boundary_contract` 표시가 없는 실행에 아래 범위 포함 검사를 적용하며, 새 실행에서는 원문 역방향 의미 검토로 대체합니다. CP1-007(출처), CP1-008(배경 범위), CP1-011(범위 근거)이 같은 분할/근거 검사 함수를 사용합니다. 배경 범위에는 연결된 모든 조각의 출처가 맞고 같은 대상의 전체 기준을 인용한 조각이 있어야 합니다. 새 조건의 의미 조합을 증명하거나 TC를 자동 분리하는 기능이 아닙니다.

새 Agent 1 작업 경계 1.2에서는 CHANGE_REQUEST 출처에도 동일한 다중 실제 인용 원칙을 적용합니다. 전체 문자열 자체가 실제 원문이면 그 안의 `|`를 임의 분할하지 않습니다. 그 외에는 각 조각이 after_value·description·reason·acceptance_notes 중 실제 한 필드에 존재해야 하며 빈 조각과 없는 원문은 거부합니다. 인수 조건은 더 큰 인용 안에도 전체 원문으로 보존되어야 합니다. 숫자 출처와 절차/제외 중복 보호를 유지하고, 조각 순서로 준비값/목표값을 추론하지 않습니다. 범위 연결은 기존 긍정 요청 필드만 권한으로 사용하므로 reason이나 before_value만으로 제품 검사를 늘릴 수 없습니다. TC 기대값·절차·SRS 개정 문구를 새롭게 분할하는 기능은 아닙니다.

## 5. Agent 2: 기존 TC 대조·설계와 CP2

확인 대상·판정 단계·복원 기준은 기존 구조화 필드를 사용합니다. observation_target의 누락과 판정 단계 연결은 검사하지만 설명 안에 같은 이름이 반복되는지는 검사하지 않습니다. CP2와 재작성 안내에 같은 연결 함수를 사용합니다. 단어가 같다는 이유로 같은 대상이라고 보장하지 않으며 값·시점·출처 검사를 유지합니다.

CP2·CP3는 복원 기준의 제한된 시점 표현을 공통으로 읽습니다. ‘시험 전’, ‘시험 시작 전’, ‘실행 시작 직전’ 등은 같은 관찰 기준 표현으로 처리하되, 원문 자체는 변경하지 않습니다. 실제 복원 비교는 기존 ER·읽기 경로·대상별 기준에 연결되어야 하며 다른 대상의 비교 구절이나 내부 코드를 화면 값으로 빌려 쓰는 것은 계속 거부합니다. CP2는 작성 검사, CP3는 지원 계획·컴파일러 연결 검사이므로 둘의 전체 판정 범위가 같다는 뜻은 아닙니다.

입력은 검증된 Agent 1 결과, 확정 조건, 관련 SRS, 기존 TC 카탈로그입니다. 카탈로그에는 기준 회귀와 승인 공식 TC의 ID·Requirement·함수·검증 동작이 있습니다. 승인 파일의 경로·SHA-256·TC 구조·단일 함수를 검사해 Run별 카탈로그 사본으로 고정합니다. 새 사본에는 승인 TC 원문도 보존합니다.

승인 공식 TC는 기대결과 요약 외에 검증된 명세의 사전조건·조작 절차·시험 데이터·기대결과와 판정 시점·중간 초기화·복원·독립 실행 선언/선택 설명도 Agent 2에 전달합니다. 검토자·등록 이력·파일 경로·자동화 코드는 이 명세 입력에 포함하지 않습니다. 설명 문장이 없으면 만들어 채우지 않으며 실제 단독 실행 증거를 대신하지 않습니다. 명세의 절차가 실제 실행됐다는 증거는 Run에서 별도로 확인합니다. 과거 카탈로그에는 없는 상세 정보를 소급 추가하지 않으며, 기준 회귀는 기존 검증 동작 요약을 유지합니다.

모델은 조건과 기존 TC의 실제 검증 동작을 대조합니다. Requirement ID만 같다고 재사용하거나 관련 회귀를 자동 보충하지 않습니다. 모든 확정 조건은 신규 후보 또는 관련 기존 TC에 연결되어야 합니다. 기존 TC로 모두 검증되면 신규 후보 0건도 허용합니다.

|---|---|
| 추적성 | 범위 밖 ID·조건 누락 차단 |
| TC 품질 | ID 고유성, 업무 규칙 묶음, 조건별 판정·중간 초기화 |

CP2-018은 이 범위 밖의 개정안, 변경되지 않은 전·후 문구, 필요한 개정안 누락을 반려합니다. 이미 반영된 문장을 다시 제안하면 그 개정안을 제외하라는 피드백을 주며 검사기가 결과를 몰래 삭제하거나 통과시키지 않습니다. SRS 개정이 없어도 TC 대조·필요한 시험·실행 증거 검사는 유지합니다. 실제 개정안은 전·후 인수 기준과 근거를 실행·보고·사람 검토까지 전달하고, 이 단계에서 기준 SRS를 변경하지 않습니다.

새 인계는 SRS 개정 계약 1.1을 재검사하며 누락·하향 변경을 거부합니다. 과거 계약 1.0 실행은 당시의 개정 필수 규칙으로 재검사하므로 과거 실패 기록을 성공으로 소급 변경하지 않습니다. 정확한 전체 문장 일치만 처리하는 제한 규칙으로, 표현이 다른 문장의 의미 동일성이나 자유 서술 전체의 타당성을 자동 판정하지 않습니다.

새 계약의 기존 TC 재사용과 SRS 제안은 명시 값·근거를 계속 대조하되, 상태 단어의 반전으로 의미를 판정하지 않습니다. SRS 제안의 코드·수치는 현재 기준과 변경 근거 안에 있어야 합니다. 의미 일치는 자동 확정하지 않으며 사람의 SRS 동의는 계속 필요합니다.

Agent 2의 2.29 입력은 복합 조건의 담당 TC 연결과 조건별 추출 값·미충족 값을 제공했습니다. 현재 2.50 입력은 조건 원문·연결된 기존 TC ID·신규 담당 후보 ID를 제공하고 단순 토큰 추출 결과는 제공하지 않습니다. 다른 조건에만 연결된 TC는 현재 조건의 근거로 합산하지 않습니다. 하나의 조건을 여러 TC가 나누어 검증할 수 있지만 값만 같다는 이유로 자동 연결하지 않습니다. 작업 경계 계약 1.1에서 CP2-019의 단순 값 포함 검사를 필수 CONDITION_COVERAGE 의미 검토로 대체합니다. 과거·부정·제외 값과 실제 요구 값을 구분하고 대상·조작·결과·복원을 대조합니다. 검토 누락은 오류, 실제 근거 부족은 FAIL, 불확실은 REVIEW이며 조건이나 기대값 삭제로 통과시키지 않습니다. 과거 1.0 이하의 저장 판정은 기존 규칙으로 재검증합니다.

## 6. Agent 3: 자동화 계획·컴파일·시험과 CP3

신규·수정 후보를 한 건씩 독립 처리합니다. 기존 TC의 자동화는 다시 만들지 않습니다.

1. 후보의 자동화 가능성을 확인하고 필요한 UI만 조사합니다.
2. AI가 실제 관찰 요소로 조작·검증 계획을 만듭니다.
   최초 및 재작성 응답에서 관찰된 기존 관제점의 유한값만 공통 표기 정리합니다. 전원·모드·풍량·잠금 필드의 대소문자·앞뒤 공백·끝 마침표 하나·알려진 제품 표시명을 표준 값으로 연결합니다. `heat.`/`난방`은 `HEAT`, 풍량의 `강풍`은 `HIGH`입니다. 문장 속 단어 추출·부정/복수 값 추측·온도 해석은 하지 않습니다. Selector·TC·출처·시점·제품 관찰값도 바꾸지 않습니다.
3. CP3가 TC·값·관찰 계층·판정 시점·복원·근거를 검사합니다.
4. 필요하면 기술 계획을 최대 1회 재작성합니다.
5. 컴파일러가 허용 조작으로 Python을 생성하고 정적 검사합니다.
6. 분리된 임시 위치에서 시험하고 로그·화면·Trace·해시를 저장합니다.

API 입력에는 해당 TC, 관련 SRS와 필요한 UI 확인 결과를 사용합니다. 키·로컬 절대경로·전체 HTML·Screenshot·Trace를 넣지 않습니다.

값 정리 후 CP3·모델 검토·컴파일은 동일한 계획을 사용합니다. 정리된 값도 TC 근거·대상·시점 검사에서 통과해야 하므로 `cool.`을 `COOL`로 정리했다고 난방 TC가 통과하는 것은 아닙니다. `agent3_plan_value_format_attempt_N.json`에 원본 계획과 필드별 변경 내역을 보존하고 Manifest의 `plan_value_formats`에 해시를 기록합니다. 실행 인계 시 원본으로 변환을 재계산해 최종 계획과 비교합니다. 기록이 없는 과거 Run에는 변환을 소급 적용하지 않습니다. 기존 계획/검토 해시와 검사 기준은 유지하며 추가 모델 호출은 없습니다.

이 처리는 구조화 값의 표기 차이만 줄입니다. TC가 자연어로만 내부값을 설명한 경우의 근거 연결, 문장에 따른 UI Inventory 선택, 앞단의 요청 인용·숫자 추출에는 기존 제한이 남습니다. 실제 제품이 잘못된 값을 반환하면 표기를 고쳐 PASS로 만들지 않습니다.

### UI 조사와 허용 범위

기존 기능은 필요한 Selector·하네스 키만 확인합니다. 처음 보는 기능도 안정적인 ID·data-testid·접근성 이름과 단순 상태로 구현 가능한지 조사합니다.

| 구분 | 허용 범위 |
|---|---|
| 공통 조작 | CLICK, FILL, SELECT_OPTION, CHECK, UNCHECK |

내부 필드 사용은 실제 조사에서 확인되고, TC 기대 결과에 필드·기대값 근거가 있으며, 허용 루트 아래의 단순 읽기여야 합니다. 임의 JavaScript·쉘·파일 변경·외부 호출·Assertion 삭제·기대값 변경은 허용하지 않습니다. 드래그·Canvas·복잡한 위젯처럼 지원하지 않는 기술이 필요한 TC는 사유와 함께 제외합니다.

조사한 Selector는 일치 요소 수를 기록하고 단일 요소일 때만 조작·범용 검증에 사용합니다. 장비 필드는 다른 장비의 합집합이 아닌 고정 시험 대상 ID 1에서 수집합니다. 범용 계획은 TEST·RESTORE의 모든 조작 문장과 순서를 반영해야 합니다. 마지막 읽기 전용 확인 문장은 연결된 검증 조건으로 수행하므로 불필요한 클릭을 만들지 않습니다. 비활성을 활성 True로 검사하거나 ‘표시’ 같은 일반 단어만 검사하는 계획은 거부합니다.

새 실행 정의에서는 위 값/문장 의미 대조를 Agent 2의 원문 검토에서 수행하고, Agent 3의 코드 검사는 승인된 자료형·값·시점의 동일성으로 확인합니다. Agent 3 입력의 문장 기반 사전조건 힌트도 실행 정의의 확인 대상 목록으로 대체합니다. SRS를 다시 해석해 TC 값을 변경하는 입력으로 사용하지 않습니다. 실제 UI 위치·장비·reader 지원 확인은 생략하지 않으며, 과거 문장형 계획에는 기존 검사와 입력을 유지합니다.

변경 후 동적 텍스트는 초기 조사에 없을 수 있습니다. 승인 기대 결과가 대상 장비 카드를 명시하고 정확한 대상 카드 Selector를 사용할 때만 실행 후 텍스트 검증을 허용합니다. 다른 카드나 상위 컨테이너로 대신 검증하지 않습니다. 차단 안내는 Toast 존재만으로 통과시키지 않고 차단 의미를 확인합니다.

### 시험·복원·증거

복원 절차의 동일 문장 중복은 CP2/CP3 공통 검사에서 구체적인 수정 안내를 제공합니다. 같은 대상과 준비 전 관찰값을 확인하는 경우에만 하나의 `confirmation`에 관련 `result_ids`와 `comparisons`를 모두 연결할 수 있습니다. 다른 대상·기준의 확인이나 별도 조작을 문장이 같다는 이유로 합치지 않습니다. 프로그램이 문장을 자동 병합하거나 ER을 삭제하지 않으며, 기존 통과/차단 기준도 바꾸지 않습니다.

#### 새 후보의 유형별 상태 복원 계약

복원 정책은 Agent 2 인계 3.10 / 프롬프트 2.37 및 Agent 3 프롬프트 3.32에서 도입했습니다. 현재 버전·절차 계약은 위의 공통 근거 검토 계약을 따르며, `scope_restoration_policy=STRUCTURED_V1`, `wording_policy=STRUCTURAL_ONLY_V1`, `input_routing_contract=1.0`, `state_restoration_contract=1.0`, `structured_restoration_contract=1.0`은 유지합니다. 각 새 TC의 `state_effect`와 복원 필요 여부를 CP2-022에서, 구조화 확인 연결은 CP2-023에서 검사하고 후속 로더도 재검사합니다. 계약 누락·하향 변경을 차단하며 과거 계약은 당시 기준으로 읽습니다. CP3-006C는 다음 정책을 계획·컴파일에 연결합니다.

| TC 유형 | 실행 기준 |
|---|---|
| READ_ONLY · 조회 | 값 변경·복원 조작 없음. 대상 장비 선택과 관찰만 허용 |
| STATE_CHANGE · 값 변경 | 시험 전 관찰값 저장 → 시험 → 승인된 복원 조작 → 동일 대상 관찰값 비교 |
| BLOCKED_CHANGE · 변경 차단 | 시험 직전 상태와 비교. 예상 밖 변경은 제품 불일치로 기록하고 복원. 상태가 유지됐고 준비 조작도 없었던 경우에만 복원 생략 |
| 복원 실패 | 원래 제품 불일치도 보존하고 복원 실패를 별도 기록. 해당 브라우저 문맥을 종료하며 재사용하지 않음 |

`RESTORE_STATUS`는 RESTORED(복원·비교 완료), UNCHANGED(상태 유지), NOT_REQUIRED(조회), NOT_STARTED(변경 동작 전 중단), FAILED(복원 실패)로 남습니다. Agent 4의 사람 검토서에는 해시 검증된 로그의 상태만 표시합니다. 복원 실패 후 다른 TC를 실행한다면 기존처럼 별도의 초기 브라우저·실행 사본에서 수행하며, 실패 환경에서 이어서 실행하는 것이 아닙니다.

복원 비교 범위는 TC·계획에 연결된 관찰 대상입니다. 과거 동적 HVAC 복원은 대상 장비의 모드·설정 온도를 추가 비교하고, 새 `RESTORE_OBSERVED_CONTROLLER`는 준비로 영향을 받는 전원(status)·mode·fanSpeed·setTemp·locked 및 관련 패널·카드 표시를 함께 비교합니다. 이는 복원 확인이지 요청 밖 제품 시험 기대결과의 추가가 아닙니다. 시스템 전체 또는 다른 장비의 복원을 보장하지 않습니다. 고정 복원값을 임의로 만들지 않으며 안전한 관찰·복원 근거가 부족하면 자동화 지원 보완 대상으로 남깁니다. 과거 준비·복원 동작과 기존 공식 자산은 변경하지 않습니다.

이 공통 복원 경로는 MED 전용이 아닙니다. 화면 표시와 내부 풍량을 확인하는 TC라면 LOW·MED·HIGH 모두 동일하게 시작값 확인 → 선택·적용 → 두 결과 확인 → 복원·두 관찰값 비교를 수행합니다. LOW 변경 시험도 MED/HIGH처럼 다른 시작값에서 확인해야 실제 전환을 검증할 수 있습니다. 시작값·복원 조작은 해당 TC에 명시하고 실행 전에 확인하며, 맞지 않는 환경을 임의로 바꿔 통과시키지 않습니다. 이 설명은 두 관찰 대상이 근거와 TC에 포함된 경우이며 모든 요청에 내부 검사를 임의 추가한다는 뜻이 아닙니다.

기존 TC 실행도 후보 실행과 같이 성공한 시험의 출력 로그를 보존합니다. TC가 실제로 남긴 사전조건·복원 확인만 증거에 포함하며, PASS라는 이유로 없는 확인을 만들어 넣지 않습니다. 과거 승인 HIGH 자산처럼 복원 비교가 화면에만 있는 코드는 이 변경으로 자동 재작성되지 않습니다. 새 공통 경로의 검증과 과거 자산의 개정·재승인은 구분합니다.

새 다섯 관제점 준비에는 구조화 복원 조작 하나와 `RESTORE_OBSERVED_CONTROLLER`를 연결합니다. 새 TC 불리언 필드나 풍량별 실행기는 추가하지 않습니다. 준비·시험에는 관찰된 다섯 관제점 버튼, 기존 모드·온도 조작, 장비 선택과 적용만 허용합니다. 공기청정 등 범위 밖 버튼이나 임의 FILL의 역동작은 이 계약으로 허용하지 않습니다. 과거 `restore_observed_hvac_state`/`RESTORE_OBSERVED_HVAC`는 이전 범위를 유지합니다.

`initial_mode`·`initial_temperature_c`는 준비 완료 조건이고, 복원 값은 준비 전 실제 관찰값입니다. 대상 선택 후 첫 변경 전에 원래 상태를 보존하고 TEST 직전에 준비 상태를 별도 보존합니다. 준비 실패·사전조건 불일치도 finally에서 복원하며 조회 TC는 상태를 바꾸지 않습니다. 복원은 미적용 대기 명령을 대상 재선택으로 정리하고, 잠겼다면 잠금 해제를 먼저 별도 적용한 뒤 값을 되돌리고 마지막에 원래 잠금을 적용합니다. FAN·DRY의 원래 온도가 바뀌었다면 온도 조작 가능한 모드에서 온도를 먼저 적용한 뒤 원래 모드를 적용합니다. 내부값 직접 쓰기·HTML 초기값 교체·고정 복원값을 사용하지 않습니다. UI로 복원할 수 없으면 실패를 기록하고 브라우저 문맥을 종료합니다.

`CONTROLLER_UI_FIELDS_EQUALS`는 `#device-card-1`에서 카드의 전원/모드 CSS 상태·모드/풍량 표시·설정 온도 숫자·잠금 표시를 읽습니다. `.detail-panel`은 별도로 패널 버튼의 active 상태와 온도 표시를 읽습니다. TC의 관찰 위치에 맞춰 둘을 구분하며 고정 버튼 글자나 내부값으로 화면 상태를 대체하지 않습니다. 다섯 필드는 동일한 코드/불리언/숫자로 해석해 비교합니다. 내부 상태는 별도의 `INTERNAL_DEVICE_FIELDS_EQUALS` 등으로 읽습니다. 숫자가 숨겨진 송풍·제습 온도를 임의의 숫자로 추정하지 않습니다. 현재 공통 복원 범위는 대상 장비 1대, 섭씨, 공기청정이 켜지지 않은 기존 중앙제어 제품이며 다른 조건은 별도 지원 확인이 필요합니다.

사전조건의 `CONTROLLER_UI_FIELD`는 `card.status`·`panel.mode`처럼 위치와 필드를 연결한 제한된 reader 이름으로 같은 DOM 읽기를 재사용합니다. 지원 필드는 status/mode/fanSpeed/setTemp/locked이며 `card.selected`는 대상 카드의 선택 CSS 상태를 확인합니다. 임의 JS/CSS 입력은 지원하지 않고 실제 해당 화면의 유일한 관찰을 요구합니다. 모든 준비 동작 뒤, 본 시험 전에 읽으며 화면과 내부 확인이 명시되면 각각 확인합니다. 다른 위치·값·명시 조건 누락의 의미 검토는 유지합니다.

새 의미 검토 경로에서 DOM 해석값 DRY와 TC의 ‘제습’ 표시 문구가 문자 그대로 같아야 한다고 요구하지 않습니다. 이 UI 전용 읽기는 제품 어댑터가 지원하는 enum/불리언을 구조 검사하고 실제 의미 일치는 공유 실행 계약을 받은 모델 검토가 확인합니다. 수치 근거와 지원하지 않는 값은 계속 차단하며 과거 문자 대조 경로는 유지합니다. 자연어 의미를 코드로 완전히 증명한다는 뜻이 아닙니다.

아래는 과거 계약을 포함한 공통 실행 설명입니다. 새 정책은 위 제한을 추가로 적용합니다.

시험은 초기 문맥 확인 → 승인된 준비 → 조건 조작 → 해당 결과 검증 → 필요한 중간 초기화/전환 → 다음 조건 순서입니다. 마지막 제품 관찰 Screenshot을 남기고 finally에서 복원·재확인한 뒤 Trace를 종료합니다. 실행 전후 대상 파일 해시를 확인합니다.

생성 코드는 같은 판정 단계의 UI·내부 관찰 묶음을 최대 2초 동안 50ms 간격으로 다시 읽습니다. 조작은 재실행하지 않습니다. 브라우저 조회 자체의 대기 때문에 전체 시간이 정확히 2초라는 뜻은 아니며, 실제 장비 응답 완료나 불변 상태의 지속 시간을 증명하지 않습니다.

고정 초기값이 없는 V1 온도·모드 묶음은 `restore_observed_hvac_state` 계약으로 실행 전 mode·setTemp를 저장하고 UI로 복원·적용한 뒤 다시 비교합니다. 고정 복원과 혼합하거나 일반 기능 내부 쓰기로 확장하지 않습니다. 범용 복원에서도 검증 대상의 관찰 상태를 실행 전후 대조합니다.

시험 결과는 PASS, PRODUCT_MISMATCH_CANDIDATE, AUTOMATION_ERROR, ENVIRONMENT_ERROR, TIMEOUT입니다. 앞의 두 상태가 필수 증거를 갖추면 완료 후보로 인계합니다. 실패·미지원 후보는 제외 사유를 남겨 다른 후보 처리를 계속합니다.

제품 불일치 분류는 실제 `PRODUCT_MISMATCH:` 오류·출력 행을 근거로 합니다. Pytest가 함께 보여 준 코드 문자열이나 주석에 같은 표시가 있다는 이유로 제품 불일치로 바꾸지 않습니다. 복원만 실패한 후보 시험은 AUTOMATION_ERROR로 남으며, 실제 제품 불일치도 함께 발생했다면 그 관찰은 보존하고 Agent 4에서 복원 실패를 별도로 보고합니다.

예상된 기술 실패·미지원 제외와 프로그램 내부 예외는 구분합니다. 내부 예외 또는 agent3_error.json이 있으면 그 시점에 이후 후보 호출을 멈추고 전체 상태 ERROR·종료 코드 1을 기록하여 정상 후속 인계를 차단합니다. 나머지 선택 TC는 unattempted_tc_ids와 미실행 사유를 남기며, 실패한 TC나 이미 완료한 TC의 증거는 보존합니다. API/실행 환경이 정상이라고 가정한 추가 비용을 방지하는 조치이며, 다른 TC가 독립적으로 성공 가능하더라도 이 Run에서는 대기한다는 한계가 있습니다. 요구사항 반려·자동화 미지원 같은 정상 제외는 다른 후보를 계속 처리합니다. 일부 TC만 명시 선택하면 나머지는 미선택 사유로 남기고 PARTIAL로 표시합니다. 설계에 없는 TC ID는 오류이며, 오류 기록 중 손상 JSON을 만나도 원래 오류 유형과 읽지 못한 파일명을 남깁니다.

시험 기본 제한은 90초입니다. 초과하면 pytest·Playwright 자식 프로세스를 정리하며 쓰기가 끝나지 않은 Trace는 증거에서 제외합니다. 정상 Trace도 로컬 경로·비밀정보 정제를 마친 뒤 SHA-256을 기록합니다. 과거 Run을 소급 수정하지 않습니다.

`evidence_complete`는 Screenshot·Trace 존재 확인이며 복원 성공까지 의미하지 않습니다. 실제 해시가 맞는 로그의 RESTORE_MISMATCH를 Agent 4가 확인합니다. 제품 불일치와 복원 실패가 함께 있으면 두 관찰을 보존하고 자동화 문제·HOLD로 분류합니다. 같은 TC를 두 번 집계하지 않으며 코드에 인용된 표식이나 변조 로그는 근거가 아닙니다.

임시 작업공간은 원본과의 파일 분리를 제공하며 컨테이너·OS 권한 격리를 제공하지 않습니다. 실행기는 시작 상태를 위해 브라우저 저장소를 초기화하고, 기존 회귀에는 준비·오류 주입 하네스가 있습니다. 이를 일반 사용자의 UI 조작으로 표현하지 않습니다.

### 사전조건을 실제 값으로 확인하는 절차

필수 사전조건 범위 검토(`review_precondition_coverage`)가 활성화된 계약에서는 한 원문에 연결된 BASELINE_CONTEXT·INTERNAL_VALUE 등 모든 reader를 함께 검토합니다. BASELINE_CONTEXT 항목만 다시 세는 중복 완전성 검사는 실행하지 않습니다. 다른 장비·미관찰 경로·원문에 없는 연결·런타임 실제 불일치 차단은 유지합니다. 해당 검토가 없는 과거/직접 호출은 기존 문맥 완전성 검사를 유지합니다. 의미 검토의 오판을 코드가 모두 보완하는 것은 아닙니다.

공통 근거 계약(`shared_evidence`)의 입력 Action은 시험 데이터와 대조하고 출력 Assertion은 해당 ER의 근거 및 필수 의미 검토와 대조합니다. 경계 입력과 출력이 다를 수 있으므로 출력까지 초기/요청 값 목록에 포함하도록 강제하지 않습니다. ER에 없는 수치·관찰 위치/시점 오류는 기존 검사를 받으며, 유효 enum의 의미 오판은 모델 검토의 남은 위험입니다.

컴파일러는 TEST 온도 입력 Action에서 첫 적용 Action까지의 Assertion 연결로 경계 요청 여부를 판단합니다. 다음 온도 입력이나 다른 phase를 넘어 기대값을 차용하지 않습니다. 준비·중간 초기화·복원은 엄격한 상태 설정을 유지하고, 연결이 없는 명시적 구간에는 다른 구간의 결과를 대신 사용하지 않습니다. 옛 시점 없는 단일 흐름의 fallback만 유지합니다. 생성 코드가 바뀐 저장 후보는 기존 해시 PASS를 그대로 재사용하지 않고 현 코드 재시험 경로를 거칩니다.

보고 요약은 CP4 PASS만으로 성공을 표시하지 않습니다. 제품 결과 0건·최종 HOLD·HUMAN_REVIEW·과거 필드 누락을 구분하며 최종 판정과 승인 기준 자체를 변경하지 않습니다. UI·검토서·외부 전송 미리보기는 같은 요약 함수를 사용합니다. 과거 저장 파일은 소급 덮어쓰지 않습니다.

새 Agent 3 계획은 실제 시작 상태에 `precondition_checks`를 연결합니다. 준비 Action을 실행했다는 사실이나 UI Inventory의 초기 값만으로 충족을 확정하지 않습니다. 검토 책임 계약 1.0은 TC의 모든 사전조건에서 필수 의미 검토 항목을 열거하고, 원래 값 기록만 요구한 문장은 실제 자동 캡처 대상과 대조합니다. CP3-006D는 제공된 검사의 원문 불일치·미관찰 경로·기대값 변형을 검사합니다. 작업 경계 계약 1.1은 같은 문장에 언급된 모든 코드·수치를 기대값으로 강제하지 않고 실제 시작 값의 의미를 PRECONDITION_COVERAGE에서 대조합니다. 1.0 이하에서는 기존 단순 값 포함 검사를 유지합니다. 확인 항목 전체가 빠진 문장은 역방향 의미 검토가 담당하므로 모델 오판 위험이 남습니다. 과거 계약과 직접 평가 함수의 기본값은 문장별 확인 누락을 계속 차단하며 과거 저장 기록의 중복 CP3-006A도 원본을 수정하지 않습니다. 의미 검토의 오판 위험은 남으며, 런타임 비교는 계획된 기대값과 실제 값의 일치이지 자연어 해석의 정답 증명은 아닙니다.

읽기 방식은 UI 텍스트·입력값·체크 상태·활성 상태, TC에 근거하고 관찰된 내부 단일 값, 기존 중앙제어 장비의 제한된 기본 문맥입니다. 기본 문맥은 대상 카드 표시·오류 없음·잠금 해제·온라인을 각각 확인합니다. 온라인은 가상 제품의 OPERATION/STOP/ERROR 상태이며 실제 장비 통신 증명이 아닙니다. 관리자 로그인·인증을 장비가 보인다는 사실로 대신 증명하지 않습니다.

관찰 정보에 있는 모든 상태를 검사하는 것은 아닙니다. TC 사전조건에 적힌 내용만 확인하며, 원문에 없는 온라인·선택 상태 등을 추가 요구하지 않습니다. 기본 문맥 확인이 실패하면 항목 번호·관찰 이름·연결 원문·실패 이유를 재작성 입력으로 전달합니다. 불필요한 추가 확인을 제거하는 것과 실제 조건을 삭제하는 것을 구분하며, 기존 검사 기준·최대 1회 재작성·런타임 비교는 유지합니다.

모델 입력의 `precondition_context_bindings`에는 원문별 허용 BASELINE_CONTEXT 항목을 표시합니다. 검사기가 이미 사용하는 원문 패턴·관찰 근거를 기준으로 만들며 새 의미 해석이나 기대값을 추가하지 않습니다. 목록이 비어도 실제 시작 조건을 생략할 수 없고, 내부 초기값 등은 다른 허용 읽기 방식으로 확인해야 합니다. 기록 지시는 별도 고정 초기값을 만들지 않고 자동 캡처 연결로 검토합니다. 실제 관찰값이 false이면 이를 true로 바꾸지 않으며 런타임에서 원래 기대값과 비교합니다. 최초 계획과 재작성에 같은 목록을 전달하고, Action만 지적된 경우 정상 사전조건·Assertion·복원 연결을 유지하도록 안내합니다. 허용 행동/읽기와 재작성 횟수는 유지하며 구조 검사는 CP3, 전체 조건의 의미상 연결은 필수 모델 검토로 나눕니다.

Agent 3는 각 모델 계획을 검사 전에 시도별 파일로 보존해 이후 검사 오류와 분리합니다. 공통 저장 함수는 같은 폴더의 짧은 고유 임시 파일을 쓴 뒤 원자적으로 교체합니다. 최종 경로 자체가 운영체제 제한을 넘는 경우까지 지원한다는 뜻은 아니므로 실행 루트는 짧게 유지합니다.

| 상황 | 처리 |
|---|---|
| 사전조건 확인 항목 누락·부적합 | 구조 검사 또는 필수 의미 검토의 FAIL은 기존 제한 재작성, UNCERTAIN은 사람 확인. 지원 확장 필요는 실행하지 않고 사유 기록 |
| 허용된 읽기 방식으로 확인 불가 | 지원 범위 확장 사유를 남기며 실행 코드를 만들지 않음 |
| 준비 뒤 실제 값이 기대와 다름 | 본 TEST를 시작하지 않고 사전조건 불충족 기록. 자동화 실행 문제·HOLD이며 제품 불일치가 아님 |
| 모든 확인값 일치 | 본 TEST 진행. 성공한 시험도 stdout에 읽은 값과 확인 완료 기록 보존 |

컴파일러는 모든 PRECONDITION Action 뒤, 첫 TEST 앞에서 확인합니다. 비동기 상태 반영은 기존 2초 재관찰 helper를 이용하며 준비 조작을 반복하지 않습니다. 같은 시점의 일반 복원 기준은 유지하고, 원래 HVAC 상태 복원은 별도 계약대로 준비 전 값을 사용합니다. 실패 시 Screenshot·Trace와 오류 로그를 남깁니다.

새 Manifest의 `precondition_proof_contract=1.0`은 이 계약을 사용했다는 표시입니다. 과거 Manifest가 없는 계약의 인계·조회는 역사적 동작을 유지하지만 새 증명을 완료한 것으로 해석하지 않습니다. 현재 공식 후보 승인과 승인 전 재검증에는 증명 계획이 필요하므로 과거 계획은 새 계약의 계획·시험 확보가 필요할 수 있습니다. 기존 승인 자산을 소급 취소하거나 바꾸지는 않습니다.

이 계약은 **사전조건마다 확인 근거를 연결하고 실제 값을 비교하는 것**입니다. 임의의 자연어·복합 문장 전체가 올바르게 해석됐다는 수학적 증명이나 모든 제품의 의미 동등성 보장은 아닙니다. 관찰 가능한 조건과 확인 불가능한 조건을 구분하며, 최신 프롬프트의 실제 모델 생성 검증은 별도 실행 결과로 판단합니다.

## 7. 변경 검증과 기존 회귀

`execute`는 Agent 3 Manifest·계획·코드·시험·증거를 확인하고 현재 CP3로 다시 검사합니다. 현재 컴파일러 출력과 같으면 시험 결과를 재사용하고, 다르면 별도 위치에서 재컴파일·재시험합니다.

환경 점검 TC-ENV-000을 먼저 실행하고 Agent 2가 명시한 관련 기존 TC만 중복 없이 실행합니다. 신규 후보가 없거나 전부 제외돼도 요약·환경 점검·선택 기존 TC·보고를 계속할 수 있습니다. 환경 점검이 실패하면 기존 회귀를 중단합니다.

기본 대상은 `product_baseline/virtual-controller.html`, 기존 회귀는 같은 폴더의 `tests/test_controller.py`입니다. 테스트와 HTML을 임시 Workspace에 복사하고 선택 함수만 실행합니다. 승인 공식 TC도 카탈로그 사본과 현재 자산 해시가 같아야 실행하며 기준 파일은 변경하지 않습니다.

기존 회귀도 후보 시험과 같은 프로세스 트리 종료 함수를 사용합니다. SKIPPED 여부는 임의 경고문 단어가 아닌 pytest 결과 요약 형식에서 판독합니다. 임의 테스트 프레임워크 출력 전체를 지원하는 파서는 아닙니다.

## 8. Agent 4: 분류·보고와 CP4

모델 호출이나 시험 재실행 없이 저장 결과를 제품 불일치 후보·자동화 문제·환경 문제·근거 부족·미실행으로 분류합니다. TC 설계 유형인 정상·경계·예외·상태 정합성과 실행 후 원인 분류는 별도 정보입니다.

| 상황 | 최종 권고 |
|---|---|
| 실행 범위 통과, 증거 유효, 자동화 제외·정보 부족 없음 | PASS |
| 유효한 제품 기대값 불일치 | HUMAN_REVIEW: 사람이 판단 |
| 실행한 TC는 통과했지만 자동화 제외·정보 부족이 남음 | HUMAN_REVIEW: 미확인 범위 검토 |
| 실행 결과의 자동화·환경 오류, 미실행·증거 부족 | HOLD: 보류 |
| 제품 TC 결과가 0건이고 환경 점검·고정 사례만 존재 | 기존 증거 부족 분류로 HOLD. CP4 보고 일관성 PASS와 제품 시험 통과는 별개 |
| 제품 불일치와 복원 실패 동시 발생 | HOLD, 두 관찰 보존 |
| CP4의 증거·집계 검사 실패 | HOLD, 외부 전송 차단 |

앞 단계에서 기술 실패 후보가 제외 목록으로 전달되면 자동화 제외·사람 검토 경로를 따릅니다. 의도적으로 정한 범위 밖 항목만으로 사람 검토를 강제하지 않습니다. 개별 기대 결과의 관찰 근거가 없으면 통과로 추정하지 않습니다.

CP4는 Run·입력 해시, TC 중복, 상태·종료 코드·메시지·증거, 제품/환경 집계, Agent 3→실행 전체 인계와 보고 수치를 확인합니다. V1 회귀는 기준 코드 해시, 승인 회귀는 카탈로그 사본과 승인 코드 해시로 검증합니다.

`사람_최종_검토.md`에는 기대·실제 관찰·증거, 제품 수정/요구사항 보완/자동화 재검토/환경 재실행/종결 선택지, 검토자·일자·기한·후속 조치란이 있습니다. Manifest는 생성 원본과 보고의 해시를 연결합니다. 사람이 편집한 문서는 자동 갱신으로 덮어쓰지 않으며, 미편집 원본만 `human-review --refresh`로 갱신할 수 있습니다.

CP4와 최종 보고 해시가 통과해야 Slack·Notion Payload를 생성합니다. 기본은 미리보기, CLI `--send`는 실제 전송입니다. Notion은 Run ID:TC ID로 같은 실행만 갱신하고 다른 실행을 보존합니다. 최초 전송 기록은 유지하고 후속 시도는 별도 폴더에 저장합니다. 화면은 최신 시도와 과거 실제 전송을 구분합니다.

Notion 기록은 실행 결과가 있는 TC의 제목·결과·분류·보고 요약과 상세 TC 본문입니다. Agent 2 인계 Manifest가 있고 기존 보고 소비 단계에서 해시·Checkpoint 재검증이 통과한 Run에 한해 저장된 사전조건·조작·기대결과의 확인 대상/판정 단계·복원을 `notion_payload.json`의 `tc_detail`로 전달합니다. 본문은 사전조건 → 조작 순서·단계별 기대결과 → 복원 순서입니다. 기대결과는 설계이며 실제 관찰값이나 공식 등록 승인으로 표시하지 않습니다. 승인 TC는 해시가 맞는 보존 명세를 사용하고, 원문 단계에 유일하게 연결되지 않는 과거 기대결과는 별도 목록으로 표시합니다. 상세 설계 연결이 없는 환경 점검·과거 기록에는 미기록 상태를 표시하며 내용을 추정하지 않습니다. Agent 2 초안만 별도 게시하는 기능은 없습니다.

본문은 내용 해시로 구분한 자동 기록 펼치기 블록을 추가합니다. 같은 내용은 기존 본문과 대조한 뒤 건너뛰고, 변경된 내용은 새 기록으로 남깁니다. 사람이 작성한 블록을 삭제하지 않으며 자동 기록 내부의 문구가 편집됐으면 덮어쓰지 않고 실패로 알립니다. 긴 본문은 나누어 전송하고, 중간 실패 뒤 재시도하면 확인된 부분은 유지합니다. 요약 속성 저장 후 본문 전송이 실패할 수 있으므로 상세 전송까지 끝나야 해당 건을 완료로 집계합니다. 동시에 같은 기록을 보내는 작업의 중복 방지나 오류 자동 재시도는 보장하지 않습니다. 읽기·삽입 권한과 실제 계정에서의 게시 확인은 별도로 필요합니다. 요청 크기·중첩은 [Notion 본문 추가 규격](https://developers.notion.com/reference/patch-block-children)과 [요청 제한](https://developers.notion.com/reference/request-limits)을 따릅니다.

## 9. 중앙제어 화면과 사람 승인

| 모드 | 동작 |
|---|---|
| HTML 직접 열기·공개 접속 | MED 정상 변경 저장 데모, API·시험·실제 파일 반영 없음 |
| 기본 로컬 서버 | 저장된 Run 조회 |
| --allow-live-run | 허용된 변경 요청 선택·화면 확인 뒤 Agent 1→4 실행 |
| --allow-asset-approval | 조건이 유효한 후보의 사람 승인·보류 |

로컬 입력은 `examples/change_request*.json`이며 임의 경로·쉘 명령은 받지 않습니다. Run ID를 명시하고 기존 ID 재사용을 거부합니다. 서버 SRS·승인 자산 경로를 분석·실행·승인에 함께 전달하며 저장소 단위 파일 잠금으로 중복 Live 실행을 막습니다.

쓰기 POST는 서버 포트의 localhost/127.0.0.1 Host와 동일 Origin, application/json 본문을 요구합니다. 외부 출처·Origin 없음/null·다른 Host 요청은 거부합니다. 이는 로컬 브라우저 요청 보호이며 사용자 인증이나 악성 로컬 프로그램 격리가 아닙니다. 공개 서버를 추가하지 않습니다.

제품 시험은 별도 브라우저에서 수행됩니다. 페이지는 실행 상태·결과를 조회하며 재접속 후에도 갱신합니다. 조회한 Run과 실행 중 Run을 구분하고 늦은 응답은 현재 선택을 덮지 않습니다. 연결 실패는 확인 불가로 표시·재시도합니다. GET 대기는 10초, 승인/재검증 POST는 180초이며 HTTP 대기 종료가 서버 시험 취소를 의미하지 않습니다. Run 전환 시 승인·SRS 동의·메모를 초기화합니다.

최종 보고가 없으면 중간 단계 PASS를 전체 PASS로 표시하지 않습니다. 환경 실패로 유효한 BLOCKED 실행 결과가 저장됐으면 Run·해시 확인 뒤 Agent 4로 넘기며, 결과 누락·손상이나 다른 실행 오류는 중단합니다.

TC 표는 설계·실행·제외·분류를 합쳐 유형·결과·사전조건·절차·기대·복원·관찰·증거를 보여줍니다. 기록 없는 유형·우선순위·기존 TC 상세는 추정하지 않습니다. 새 Run은 승인 TC 원문 사본을 사용하고 과거 Run은 지정된 자산 폴더와 해시를 확인합니다.

### 공식 TC 등록

1. 사람이 PASS 후보의 명세·증거·확인 사항을 검토합니다.
2. 서버가 최종 PASS, CP3·CP4 PASS, 변경 검증 PASSED, 필수 증거와 코드·현재 HTML 해시를 확인합니다.
3. HTML이 바뀌었으면 같은 후보를 현재 화면에서 모델 호출 없이 재검증합니다.
4. SRS 제안이 있으면 후보 Requirement·Condition에 연결된 개정 전후 문구를 보여주고 별도 동의를 받습니다.
5. 승인 TC·Python과 검토자·메모·출처·해시를 approved_assets에 기록합니다.
6. 다음 Agent 2가 등록 자산을 기존 TC 카탈로그에서 대조합니다.

승인 후보 코드는 Agent 3와 변경 검증 기록의 코드 해시 모두와 일치해야 합니다. 다른 코드이면 승인과 승인 전 재검증을 차단합니다. 재검증 Raw 증거는 로컬 Run에, 공개 가능한 요약은 approved_assets/provenance에 보존하고 두 해시를 구분합니다.

승인 전 재시험은 입력 무결성을 확인한 뒤 실행 전에 `latest.json`에 `INCOMPLETE`와 대상 해시를 기록합니다. 이 기록 저장에 실패하면 시험을 시작하지 않습니다. 실행 오류·중단·완료 기록 저장 실패가 발생하면 미완료 상태가 남아 과거 PASS로 승인할 수 없습니다. 정상 종료 후 시작/종료의 제품 HTML·후보 코드 해시가 같아야 완료 결과를 기록하며, 다르면 미완료를 유지하고 재시험을 요구합니다. 시험 도중 변경 후 종료 전에 원복하는 행위까지 감시하는 기능은 아닙니다. 원래 Run의 시험 결과와 기존 증거 파일은 수정하지 않습니다.

파일이 바뀌지 않은 채 재시험을 완료했다면 실패·시간 초과·증거 부족도 최신 기록에 반영합니다. 현재 제품·코드와 일치하는 최신 재시험 결과를 과거 PASS보다 우선하며, 정상 PASS와 필수 증거를 다시 확보하기 전에는 등록하지 않습니다. 제품 파일이 이전 시험 때와 같아도 이 기준은 동일합니다. 기존 실행 원본은 덮어쓰지 않습니다.

같은 Run·TC 중복 승인은 같은 기록을 반환합니다. 보류는 사유만 남기며 이미 승인한 자산을 보류로 되돌리지는 않습니다. 등록 중 일반 오류 또는 Ctrl+C/SystemExit가 발생하면 해당 승인에서 바꾼 SRS·TC·Python·Registry·임시 파일을 기존 보상 처리로 복구한 뒤 예외를 다시 전달합니다. 기존 TC 전용 SRS 승인에도 같은 중단 원칙을 적용합니다. 전원 종료·프로세스 강제 종료·복구 중 추가 장애까지 원자성을 보장하는 저장소는 아닙니다. 사람 검토서 작성만으로 Registry가 바뀌지 않습니다.

UI의 JSON 저장도 `qa_pipeline_io`의 공통 원자적 저장 함수를 재사용합니다. 같은 디렉터리의 고유 임시 파일로 기록한 뒤 교체하며, 교체 실패 시 원본을 보존하고 임시 파일 정리를 시도합니다. 디스크 장애로 정리 자체가 실패하는 경우까지 정상 저장이나 복구 완료로 간주하지 않습니다.

기존 TC만 실행한 Run도 유효한 Agent 1/2 인계·실행·현재 제품·기존 TC 조건 연결·SRS 원문을 확인해 SRS_ONLY 승인을 할 수 있습니다. 검토자·메모·SRS 동의와 화면 확인이 필요하며 TC·Registry는 새로 만들지 않습니다. 판단 기록 실패 시 SRS를 원상복구합니다. 동일 제안은 멱등 처리하고 다른 원문으로 바뀐 SRS는 거부합니다.

단일 agent3 CLI는 루트 agent3_manifest.json·agent3_trial.json을 사용하며 다중 요약이 없습니다. CP4는 정확한 단일 경로·해시를 검사하고, 다중 실행에는 요약을 요구합니다. 과거 일괄 모델 호출 agent3_batch_*는 현재 실행 계약이 아닙니다.

공통 구조는 Pydantic JSON·SHA-256 인계·단계별 최대 1회 재작성입니다. 역사적 existing_procedure_review_contract, existing_behavior_values_contract, double_assert_timing_contract가 없는 Run에는 새 CP2 규칙을 소급 적용하지 않습니다. 현재 후보 재검사와 과거 증거 조회는 서로 다른 처리입니다.

과거 CP1·CP2의 재검증에서는 SHA-256 원본 확인과 Manifest 계약 확인을 먼저 수행합니다. 이후 저장 결과와 재계산 결과에서 양쪽 모두 PASS인 항목의 `message`만 비교에서 제외합니다. 검사 ID·개수·순서·판정, FAIL/REVIEW 메시지, 인계 상태·최종 검토 사항 등 나머지 필드는 정확히 일치해야 합니다. `STRUCTURAL_ONLY_V1` 계약은 PASS 메시지까지 비교합니다. 원본 기록을 재작성하지 않으며, 검사 항목이나 실제 판정이 다른 오래된 기록까지 수용하는 마이그레이션은 아닙니다. 과거 조회가 가능해져도 새 Agent 2 실행은 새 Agent 1 인계가 필요하다는 조건은 유지됩니다.

새 정책에서도 meaning_guard_contract=1.0의 출처·명시 값 근거 검사는 유지합니다. 문장 의미 추정 사용 여부는 wording_policy로 구분합니다. 과거 인계는 당시 기준으로 대조하며 원본 판정·해시를 바꾸지 않습니다.

공개 진입점 src/qa_pipeline_v2.py는 import·CLI 호환을 유지합니다. 내부 구현은 contracts, agent1, agent2, agent3, execution, reporting, orchestrator와 공통 grounding/io/trace, UI 표시 계층으로 나뉩니다. 테스트는 grounding을 포함한 8개 역할 파일과 pipeline_test_support.py를 사용합니다.

### 후속 감사에서 보완한 연결 검사

- 신규 TC의 기대 결과는 연결된 조건의 코드·수치 근거를 보존해야 합니다. 테스트 입력을 정상 출력의 근거로 삼지 않습니다. 명시 범위 안 값·유지 조건의 사전 값·차단 입력 근거 검사는 유지하지만, 분석·설계 문장 속 상태 단어 비교만으로 의미 정확성을 판정하지 않습니다.
- 새 Agent 2 Manifest의 `candidate_expectation_contract=1.0`은 이 검사를 실행했다는 표시입니다. 과거 Run은 당시 CP2 판정으로 조회하되 현재 신규 자산 승인에서는 기대 결과와 CP3 계획을 다시 검사합니다.
- 상태를 확인하는 문자 검사는 고정된 제어 이름만 검사해서는 안 됩니다. 비활성 전용 전략은 명시적 비활성 기대에만 사용합니다.
- 과거 계약의 일반 고정 복원은 TC 준비 완료 직후, TEST 이전의 상태와 비교합니다. 새 state_effect 계약은 준비 전 원래 상태를 보존하고, 공통 관제점 복원은 다섯 값과 관련 표시를 비교합니다. 과거 `RESTORE_OBSERVED_HVAC`는 모드·온도 범위를 유지합니다. 사전조건 원문별 읽기 근거와 실행 직전 실제 값 확인은 위 사전조건 절차를 따릅니다. 임의 자연어 의미 전체의 동등성은 보장하지 않습니다.
- 보고 재사용 시 실행 JSON→Agent 4 분석→최종 보고의 해시와 공통 내용, 후보·회귀 증거, 존재하는 Agent 1·2 원본 연결을 재검사합니다. 공식 후보 승인과 승인 전 재검증은 TC→계획·관찰·CP3 연결도 확인합니다.
- 필수 UI 인터페이스 누락은 그 TC의 제외 사유이며 예기치 않은 코드 예외는 내부 오류입니다. 같은 서버의 동시 승인 요청은 잠금으로 직렬화하고 Run 전환 후 늦은 POST 응답은 화면에 적용하지 않습니다.
