# 프로젝트 안내: 시나리오와 처리 로직

현재 계약 기준: 2026-09-14. 최신 실행 결과·남은 과제는 [인계 문서](../PROJECT_HANDOFF.md), 설치·실행은 [README](../README.md)에 있습니다.

## 1. 무엇을 하는 프로젝트인가

기존 제품 SRS와 베이직 TC가 있는 상태에서 새로운 변경 요청을 받습니다. 이미 관리하는 TC로 확인할 수 있는 조건은 재사용하고, 새로 필요한 조건만 후보 TC로 만들어 시험합니다. 결과와 근거를 보고 사람이 공식 자산으로 채택할지 판단합니다.

| 용어 | 의미 |
|---|---|
| SRS | 제품이 어떻게 동작해야 하는지 정한 요구사항 |
| TC | 사전조건·절차·기대 결과·복원을 가진 테스트케이스 |
| 기존/베이직 TC | V1 기준 TC와 사람이 승인한 V2 공식 TC |
| 후보 TC | 이번 변경을 위해 만든 TC. 시험 통과 후에도 공식 승인 전에는 후보 |
| 관련 회귀 | 이번 변경과 관련 있고 여전히 유효한 기존 TC의 재실행 |
| Checkpoint(CP) | Agent 산출물의 구조·근거·값·인계를 검사하는 자동 단계 |
| Run | 변경 요청 한 번의 입력·분석·TC·시험·보고 묶음 |
| 후보 시험(Candidate Trial) | 생성한 자동화 코드를 별도 임시 위치에서 실제 실행하는 과정 |

```text
기존 SRS + 기존 TC + 변경 요청
  → Agent 1 / CP1: 확정 조건·정보 부족 분리
  → Agent 2 / CP2: 기존 TC 대조·변경분 후보 설계·SRS 개정 제안
  → Agent 3 / CP3: 후보별 UI 확인·AI 계획·컴파일·시험
  → 변경 검증: 완료 후보 확인·환경 점검·선택한 기존 TC 실행
  → Agent 4 / CP4: 원인 분류·증거/집계 확인·보고
  → 사람: SRS 개정·공식 TC 등록 승인 또는 보류
  → 승인한 자산을 다음 Run에서 기존 TC로 대조
```

Agent 1·2는 모델이 구조화 JSON을 작성합니다. Agent 3는 모델이 동작·검증 계획을 작성하고 컴파일러가 Playwright Python을 생성합니다. Agent 4는 생성형 AI를 사용하지 않습니다.

## 2. 시연 시나리오

| 사례 | 처리 | 확인할 장면 |
|---|---|---|
| 정상 변경·관련 기존 TC 재사용 | MED 적용 후 카드의 중풍 표시와 내부 fanSpeed=MED를 확인, 관련 기존 HIGH TC 선택 결과를 함께 확인 | 신규 TC → 자동화 → 실제 시험, 기존 TC 재사용 → 분류 |
| 모드별 온도 범위 | AUTO 18~30°C, COOL·HEAT 16~30°C, FAN·DRY 온도 비활성화 요청 | 조건·경계값 설계와 기대/관찰 비교 |
| 제품 불일치 | 잠금 시 온도 버튼 비활성화 요구와 실제 활성 상태를 비교 | 실패 증거와 제품 불일치 후보 분류 |
| 정상 변경의 후속 승인 | PASS 후보와 SRS 개정안을 사람이 검토 | 공식 등록 또는 보류, 이후 기존 TC 재사용 |

위 기능명·값은 시연용 예시입니다. 요구사항을 생성 규칙에 고정하지 않습니다. 최신 정상 시연은 MED 변경만 요청하며, HIGH 유지는 필수 조건이 아닙니다. 기존 TC 선택 여부는 해당 Run의 실제 결과로 확인하며 항상 HIGH를 실행한다고 고정하지 않습니다. 과거 공개 MED 입력에는 HIGH 유지 조건이 포함되어 있습니다. 일부 기대값 누락은 별도 검증 사례로 보존하되 주 영상의 세 요구사항 사례에는 포함하지 않습니다.

잠금 실패 사례는 실패 증거로 보존합니다. 제품을 고치거나 기대값을 바꿔 이 결과를 PASS로 만드는 자동 절차는 없습니다. 제품 TC가 실패해도 그 실패의 증거와 집계가 유효하면 CP4는 통과할 수 있습니다.

포폴에는 MED 변경·HIGH 재사용을 주 영상으로, 온도 범위·잠금 불일치를 보조 사례로 보여주고 마지막에 사람의 등록 판단을 연결합니다. 로컬 실제 실행 영상의 대기 구간을 편집하면 표시합니다. 공개 HTML의 저장 데모와 실제 API 실행 영상을 구분합니다. 루트 project.html은 세로 스크롤형 정적 소개 페이지이며, 실행 결과에는 풍량·잠금·미정 조건이 남은 사례를, 분석·보고 이후에는 실제 자산 등록 상태를 보여줍니다. 초기 온도 시험은 별도 추가 사례로 유지합니다. V1 원본은 보존하며, 사용자 요청으로 V2 소개에 V1의 표현 형식을 참고했습니다. 영상 미촬영 상태를 표시하고 당시 공개 증거와 최신 로컬 실행을 구분합니다.

## 3. 공통 QA 기준과 TC 구성

| 기준 | TC에 담는 내용 |
|---|---|
| 1단계 공통 QA | 해당 규칙의 정상·예외·경계·복구 관점 |
| 2단계 도메인 QA | 올바른 장비 선택, 화면·내부 상태 정합성 |
| 3단계 기능 기준 | 요구사항에 명시된 값·동작·표시 |
| 추적성 | Requirement·확정 조건·단계·기대 결과의 연결 |
| 독립성 | 다른 TC에 의존하지 않는 준비·초기 상태·복원 |
| 이중 검증 | 필요한 경우 같은 동작 직후 화면과 내부 상태 확인 |

하나의 TC는 하나의 관제점에서 하나의 업무 규칙을 검증합니다. 같은 범위의 하한·상한이나 같은 비활성 규칙의 여러 모드는 한 TC로 묶을 수 있습니다. 무관한 요구사항·제어 경로·실패 원인은 분리합니다.

| 조건 구성 | 계약 | 실행 방식 |
|---|---|---|
| 단일 흐름 | SINGLE_FLOW | 한 흐름의 동작과 판정 |
| 독립 입력 조건 | INDEPENDENT_VARIANTS | 조건 사이 재준비·초기화 기록 |
| 순차 전환 자체가 목적 | SEQUENTIAL_TRANSITION | 승인한 전환 순서 유지 |

관찰값 하나마다 기대 결과를 나누고 `verify_after_step`으로 판정 위치를 지정합니다. 화면 표시와 내부 값이라는 이유로 같은 조작을 두 번 반복하지 않습니다. Agent 3는 `after_action_id`로 해당 동작 직후 검증을 배치합니다. REQUIRED 이중 검증은 두 관찰 계층의 판정 단계 집합이 일치해야 합니다. 두 계층 모두 판정 단계가 없는 단일 흐름은 기존 종료 시점 검증을 유지합니다.

CP는 구조·명시 값·연결 관계를 검사합니다. 자연어 의미가 완전히 같은지, 모든 누락을 탐지했는지, 기준에 적은 모든 관점을 시험했는지까지 보장하는 것은 아닙니다.

## 4. Agent 1: 요구사항 분석과 CP1

변경 요청과 관련 SRS에서 변경 전·후 값, Requirement 영향, 출처가 있는 확정 조건, 제외 범위, 정보 부족을 만듭니다. 조건 역할은 변경·유지·보조 근거로 구분합니다. 현재 자동화 지원 여부를 이유로 제품 영향도를 낮추거나 명확한 조건을 버리지 않습니다.

CP1은 요청 ID·변경 유형·Requirement·값 보존, 요청/SRS 근거, 인수 조건의 전달과 진행 판정 일관성을 검사합니다.

새 실행의 CP1-011은 대상 외 VERIFY·UPDATE_REQUIRED에 `scope_evidence`를 요구합니다. 요청에서 나온 긍정 확정 조건 ID, 해당 연관 SRS 원문, 직접 요청/간접 영향 구분을 보존하며 영향 경로는 기존 `reason`에 설명합니다. SRS에 존재한다는 사실이나 같은 화면에서 실행한다는 이유만으로 범위를 추가하지 않습니다. 근거가 없는 항목은 NO_IMPACT로 검토 기록만 남기되, 명시된 요청 조건을 지워 검사를 피해서는 안 됩니다.

- 근거 누락·허위 출처·준비/제외/변경 전 문구를 근거로 사용: FAIL → 기존 제한 재작성 1회 → 미해결 시 차단.
- 직접 요청: 연결된 요청 원문에 연관 Requirement ID 또는 그 SRS 요구사항/인수 기준 전체 문장이 있는 경우 자동 대조합니다. 단순 공통 단어나 모델의 Requirement 연결만으로 직접 요청임을 인정하지 않습니다.
- 요청의 근거 연결만 수행: `VERIFY + REQUEST_TRACE_ONLY`는 요청에 이미 있는 제품 판정 조건만 연결합니다. 해당 Requirement에 연결된 조건 목록과 근거 목록이 정확히 같아야 하며, 모두 긍정 CHANGE_REQUEST 원문이고 statement가 source_text와 같아야 합니다. 추가 SRS 조건·새 기대값·UPDATE_REQUIRED는 허용하지 않습니다. Agent 2에서도 이 조건의 기대결과는 원문 한 문장을 유지하고, 상세 관찰 위치·판정 시점은 별도 항목에 씁니다. 연관 ID 이름만으로 알림·이중 검증을 강제하지 않습니다. 이는 근거 연결이며 관련 SRS 전체의 검증 완료를 뜻하지 않습니다.
- 요청 밖 간접 영향 또는 직접 요청의 다른 자연어 표현: 근거를 기록해도 CP1-011 REVIEW·PAUSE로 범위 확인을 기다립니다. 현재 규칙은 인과관계나 모든 바꿔 쓴 표현을 자동 판독하지 않습니다. 필요한 범위를 요청에 명시해 새 Run으로 확인하며, 자동 통과를 위해 요구사항을 축소하지 않습니다.

새 Agent 1 Manifest 2.6은 `scope_guard_contract=1.1`을 저장합니다. 근거 연결 전용 구분은 이 계약에서만 허용하며 1.0 또는 계약이 없는 과거 Run은 당시 검사 결과와 해시를 유지합니다. 과거 결과를 새 분류로 바꾸지 않습니다. TC 필드나 기존 공식 TC 원문은 수정하지 않습니다.

새 의미 보존 계약은 원문과 분석문의 명백한 활성/비활성·허용/차단 반전, 근거 밖 수치, 코드·수치의 부분 문자열 인용을 차단합니다. SRS 조건은 연결된 Requirement마다 인용 근거가 있어야 하므로 서로 다른 근거는 조건을 나눕니다. 요청을 유지 조건으로 분류하려면 원문에 유지·변경 없음 근거를 명시합니다. 이는 제한된 오류 검사이며 복합 조건·주체·순서·한국어의 모든 부정 표현을 판독하는 의미 검증기는 아닙니다.

| 분석 결과 | 후속 처리 |
|---|---|
| PROCEED | 확정 범위 계속 |
| PARTIAL_PROCEED | 확정 범위 계속, 정보 부족은 별도 보고 |
| WAITING_FOR_USER | 핵심 시험 범위를 정할 수 없어 보류 |
| BLOCKED 또는 CP1 FAIL | 후속 인계 차단 |

기존 REVIEW는 확정 범위가 있으면 마지막 확인 사항으로 전달합니다. 다만 CP1-011의 범위 REVIEW는 PROCEED·PARTIAL_PROCEED여도 PAUSE로 인계를 멈춥니다. 중단 Run을 이어 붙이는 재개 기능은 없으며, 입력을 보완해 새 Run을 만듭니다.

명시적 미정 인수 조건은 PARTIAL_PROCEED의 정보 부족·제외된 정보 부족·제외 범위에 같은 원문이 모두 보존될 때 CP1-008의 확정 조건 요구에서 제외합니다. 명확한 조건의 임의 제외나 기록 누락은 계속 실패입니다. 모든 자연어 모호성을 판별하는 규칙은 아닙니다.

시험 시작 전 확인·종료 후 복원 메모는 제품 판정 조건과 구분해 Agent 2로 전달합니다.

## 5. Agent 2: 기존 TC 대조·설계와 CP2

입력은 검증된 Agent 1 결과, 확정 조건, 관련 SRS, 기존 TC 카탈로그입니다. 카탈로그에는 기준 회귀와 승인 공식 TC의 ID·Requirement·함수·검증 동작이 있습니다. 승인 파일의 경로·SHA-256·TC 구조·단일 함수를 검사해 Run별 카탈로그 사본으로 고정합니다. 새 사본에는 승인 TC 원문도 보존합니다.

승인 공식 TC는 기대결과 요약 외에 검증된 명세의 사전조건·조작 절차·시험 데이터·기대결과와 판정 시점·중간 초기화·복원·독립 실행 근거도 Agent 2에 전달합니다. 검토자·등록 이력·파일 경로·자동화 코드는 이 명세 입력에 포함하지 않습니다. 명세의 절차가 실제 실행됐다는 증거는 Run에서 별도로 확인합니다. 과거 카탈로그에는 없는 상세 정보를 소급 추가하지 않으며, 기준 회귀는 기존 검증 동작 요약을 유지합니다.

모델은 조건과 기존 TC의 실제 검증 동작을 대조합니다. Requirement ID만 같다고 재사용하거나 관련 회귀를 자동 보충하지 않습니다. 모든 확정 조건은 신규 후보 또는 관련 기존 TC에 연결되어야 합니다. 기존 TC로 모두 검증되면 신규 후보 0건도 허용합니다.

| CP2 검사 | 내용 |
|---|---|
| 추적성 | 범위 밖 ID·조건 누락 차단 |
| TC 품질 | ID 고유성, 업무 규칙 묶음, 조건별 판정·중간 초기화 |
| 새 초안 상세화 | 대상 선택 순서, 선택/입력과 적용 구분, 기대결과의 확인 대상·유일한 판정 단계, 복원 확인 방법 |
| QA 기준 | 3단계 기준·독립성·필요한 이중 검증 |
| 역할 경계 | 제품 TC에 Selector·Python·구현 지시 금지 |
| 제품 경로 | 중앙 관제 패널·대상·시험 데이터 명시 |
| 정보 부족 | 불명확한 범위를 TC로 만들지 않고 원문 인계 |
| 재사용 | 카탈로그 밖 ID, 유지 조건의 중복 후보 생성, 명시 값 불일치 차단 |
| SRS 제안 | 개정 대상·현재 원문·제안·Condition 근거의 누락·중복·불일치 차단 |

같은 TC의 서로 다른 관찰값은 별도 기대 결과입니다. 모드가 단순 시험 조건인 문장은 별도 모드 표시 검증으로 추정하지 않습니다. 요구사항에 없는 행동 성공을 기대 결과로 추가하지 않으며, 기능 가능 여부가 요구사항이면 판정 가능한 표시·값·활성 상태로 구체화합니다.

새 작성 지침은 대상 선택 → 값 선택/입력 → 적용을 실제 조작에 맞춰 나누고 각 단계에 위치·대상·값·행동을 적도록 합니다. 준비·조작 확인은 preconditions/steps에, 제품 판정은 expected_results에, 복원은 restore_steps에 둡니다. 근거 없는 버튼명·선택 표시·내부 필드를 만들어 상세함을 채우지 않습니다. 단계 수를 고정하거나 읽기 전용 시험에 불필요한 조작을 만들지 않습니다.

CP2-020은 명시적으로 합쳐진 선택/입력·적용 문장, 일반적인 빈 절차, 확인 대상 누락·지나치게 일반적인 대상, 본문과 다른 확인 대상, 없거나 중복된 판정 단계 연결을 차단합니다. 모든 자연어 절차의 상세함이나 의미 일치를 판단하는 검사는 아닙니다. 각 ER의 `observation_target`은 사람이 읽는 확인 위치이며 statement에도 같은 표현으로 들어갑니다. `verify_after_step`은 단일 흐름에서도 실제 steps 한 곳에 연결합니다. UI·내부 값은 동일 조작 뒤 함께 확인하고, 복원은 선택·적용을 한 문장으로 써도 됩니다.

작성 지침에는 풍량·온도·읽기 전용 예시를 넣되, 예시의 값·문구·조건 ID를 현재 제품 기준으로 복사하지 않도록 구분합니다. CP2-021은 중앙 장비 값 조작 전에 별도 대상 선택 또는 명시적으로 선택 완료된 사전조건이 있는지 확인합니다. 복원이 필요한 TC에는 대상·초기값 또는 실행 전 관찰값·구체적인 위치에서 복귀를 확인하는 문장을 요구합니다. 입력 원문의 복원 메모는 유지하고 확인 문장을 별도 줄에 추가합니다. 대상 선택과 복원 확인을 제품 기대결과로 만들지는 않습니다. 읽기 전용·기존 TC 전용에는 불필요한 선택·적용·신규 후보를 강제하지 않습니다. 인식 가능한 명시 표현을 검사하는 규칙이지 모든 자연어의 의미나 상태 준비 완료를 증명하는 규칙은 아닙니다.

새 Agent 2 Manifest는 `contract_version=3.3`, `tc_detail_contract=1.2`, prompt 2.27입니다. CP2-021은 복원 확인의 대상별 구절에서 비교 기준이 빠졌거나 내부 코드를 근거 없는 화면 초기 표시로 사용하는 경우도 반려합니다. 화면 표시의 명시 근거가 없으면 시험 전 같은 화면의 관찰 상태와 비교하도록 작성합니다. 과거 상세화 1.0/1.1은 당시 규칙으로 읽고 기존 공식 TC를 다시 작성하지 않습니다. 새 확인 대상이 명시된 TC는 Agent 3에서 `after_action_id`가 필수이며, 연결된 조작 직후 Assertion을 실행합니다. 이 대상 필드는 Selector나 새로운 제품 기대값을 허가하지 않습니다.

Agent 3는 복원 확인 전용 줄을 추가 클릭으로 바꾸지 않습니다. 계획의 `restore_confirmations`에 TC 원문 그대로의 `source_text`와 기존 확인 대상의 `result_ids`를 연결합니다. 새 Selector·기대값 필드는 없으며 원문 목록·중복·누락·언급된 모든 관찰 대상과 ER ID가 일치해야 합니다. 기존 ER의 `observation_target`과 실제 컴파일러가 비교하는 UI·내부 초기 상태 또는 온도 복원 값에 연결될 때만 인정합니다. 명시 초기값은 같은 관찰 대상의 사전조건 증명 또는 온도 초기값과 대조합니다.

새 알림·새 관찰 대상·다른 값·복원보다 앞선 확인·확인용 가짜 Action은 반려합니다. 상세 문장의 필드 설명은 해당 TC의 사전조건·조작·연결 기대결과에 공통으로 있는 한글 표현만 제한적으로 인정하고, 새로운 코드·수치의 근거로 사용하지 않습니다. 비교 문법·대상 이름을 무제한 해석하지 않으며 지원 밖 표현은 남은 문구를 포함해 알립니다. 컴파일러도 연결을 다시 검사하고 기존 복원 비교를 수행하며, 모든 복원 비교가 성공하고 본 시험이 완료됐을 때만 `RESTORE_CONFIRMATIONS_VERIFIED` 로그에 연결 ER ID를 남깁니다. 실패를 로그 성공으로 덮지 않습니다.

새 Agent 3 Manifest는 `contract_version=4.3`, `restore_confirmation_contract=1.2`, prompt 3.26입니다. 각 복원 확인의 `comparisons`는 ER ID·원문의 연속 구절 `source_excerpt`·비교 방법 `basis`를 연결합니다. `OBSERVED_BASELINE`은 같은 관찰 대상의 시험 전 상태와 비교한다는 구절이어야 하며, `PROVED_INITIAL`은 같은 대상의 준비 상태 검사로 증명한 초기값(또는 지원되는 온도 초기값)과 연결돼야 합니다. 새 값이나 Selector는 받지 않습니다. 같은 위치를 여러 ER이 사용하는 경우 같은 구절을 참조할 수 있지만 다른 대상의 초기값·비교 표현을 빌려 쓸 수는 없습니다.

전체 원문에서 빠진 구절·새 대상·잘못된 값·부정은 차단하고, `확인하고`·`확인하며` 같은 연결 표현은 처리합니다. 복원 비교 연결 오류는 CP3-006B로 구분하며 이를 복원 조작 누락으로 중복 안내하지 않습니다. 조작 자체가 누락되면 기존 순서 검사에서도 차단합니다. 실행 진입점·후속 인계 재검증·현재 공식 승인 전 검사는 새 비교 연결을 요구하며 과거 1.0/1.1 또는 계약 없는 인계는 당시 규칙으로 읽습니다. 새 비교 필드를 과거 계약으로 위장해 읽지 않습니다. 제품 기대결과 및 실제 복원 비교값은 바꾸지 않습니다. 원문 표현의 무제한 해석이나 새 모델의 안정적인 생성 완료를 의미하지 않습니다.

복수 모드·온도는 `requested_modes`·`requested_temperatures_c`에 기록합니다. 준비·복원 전용 값은 시험 입력값에 섞지 않습니다. 기술 ID만 중복되면 의미·값·단계를 유지한 채 번호를 정리합니다.

신규 후보의 준비 메모는 사전조건/단계, 복원 메모는 복원 단계에 원문으로 보존합니다. 기존 TC 전용 요청에서는 새 후보를 강제하지 않고 메모와 선택 TC를 마지막 사람 확인 사항으로 전달합니다. 기존 코드가 그 절차를 실제 수행했다고 추정하지 않습니다.

MODIFIED·UPDATE_REQUIRED Requirement에는 현재/제안 인수 기준과 근거를 가진 `SRS_개정_제안`을 생성하고 실행·보고·사람 검토까지 전달합니다. 이 단계에서는 기준 SRS를 변경하지 않습니다.

새 계약의 기존 TC 재사용은 명시 값뿐 아니라 단일 상태의 허용/차단·활성/비활성 반전도 차단합니다. SRS 제안의 코드·수치는 현재 기준과 변경 근거 안에 있어야 하며 조건과 명백히 반대인 문구를 허용하지 않습니다. 여러 조건이 섞인 문장의 완전한 의미 일치는 자동 확정하지 않으며 사람의 SRS 동의는 계속 필요합니다.

## 6. Agent 3: 자동화 계획·컴파일·시험과 CP3

신규·수정 후보를 한 건씩 독립 처리합니다. 기존 TC의 자동화는 다시 만들지 않습니다.

1. 후보의 자동화 가능성을 확인하고 필요한 UI만 조사합니다.
2. AI가 실제 관찰 요소로 조작·검증 계획을 만듭니다.
3. CP3가 TC·값·관찰 계층·판정 시점·복원·근거를 검사합니다.
4. 필요하면 기술 계획을 최대 1회 재작성합니다.
5. 컴파일러가 허용 조작으로 Python을 생성하고 정적 검사합니다.
6. 분리된 임시 위치에서 시험하고 로그·화면·Trace·해시를 저장합니다.

API 입력에는 해당 TC, 관련 SRS와 필요한 UI 확인 결과를 사용합니다. 키·로컬 절대경로·전체 HTML·Screenshot·Trace를 넣지 않습니다.

### UI 조사와 허용 범위

기존 기능은 필요한 Selector·하네스 키만 확인합니다. 처음 보는 기능도 안정적인 ID·data-testid·접근성 이름과 단순 상태로 구현 가능한지 조사합니다.

| 구분 | 허용 범위 |
|---|---|
| 공통 조작 | CLICK, FILL, SELECT_OPTION, CHECK, UNCHECK |
| V1 호환 조작 | 해당 TC에 필요한 장비 선택·모드 선택·온도 설정·중앙 적용 |
| UI 검증 | 텍스트·값·체크·활성 상태·온도 표시·알림과 차단 의미 |
| 내부 검증 | 실제 확인한 고정 하네스 아래의 장비 필드·단순 읽기 값 |

내부 필드 사용은 실제 조사에서 확인되고, TC 기대 결과에 필드·기대값 근거가 있으며, 허용 루트 아래의 단순 읽기여야 합니다. 임의 JavaScript·쉘·파일 변경·외부 호출·Assertion 삭제·기대값 변경은 허용하지 않습니다. 드래그·Canvas·복잡한 위젯처럼 지원하지 않는 기술이 필요한 TC는 사유와 함께 제외합니다.

조사한 Selector는 일치 요소 수를 기록하고 단일 요소일 때만 조작·범용 검증에 사용합니다. 장비 필드는 다른 장비의 합집합이 아닌 고정 시험 대상 ID 1에서 수집합니다. 범용 계획은 TEST·RESTORE의 모든 조작 문장과 순서를 반영해야 합니다. 마지막 읽기 전용 확인 문장은 연결된 검증 조건으로 수행하므로 불필요한 클릭을 만들지 않습니다. 비활성을 활성 True로 검사하거나 ‘표시’ 같은 일반 단어만 검사하는 계획은 거부합니다.

변경 후 동적 텍스트는 초기 조사에 없을 수 있습니다. 승인 기대 결과가 대상 장비 카드를 명시하고 정확한 대상 카드 Selector를 사용할 때만 실행 후 텍스트 검증을 허용합니다. 다른 카드나 상위 컨테이너로 대신 검증하지 않습니다. 차단 안내는 Toast 존재만으로 통과시키지 않고 차단 의미를 확인합니다.

### 시험·복원·증거

시험은 초기 문맥 확인 → 승인된 준비 → 조건 조작 → 해당 결과 검증 → 필요한 중간 초기화/전환 → 다음 조건 순서입니다. 마지막 제품 관찰 Screenshot을 남기고 finally에서 복원·재확인한 뒤 Trace를 종료합니다. 실행 전후 대상 파일 해시를 확인합니다.

생성 코드는 같은 판정 단계의 UI·내부 관찰 묶음을 최대 2초 동안 50ms 간격으로 다시 읽습니다. 조작은 재실행하지 않습니다. 브라우저 조회 자체의 대기 때문에 전체 시간이 정확히 2초라는 뜻은 아니며, 실제 장비 응답 완료나 불변 상태의 지속 시간을 증명하지 않습니다.

고정 초기값이 없는 V1 온도·모드 묶음은 `restore_observed_hvac_state` 계약으로 실행 전 mode·setTemp를 저장하고 UI로 복원·적용한 뒤 다시 비교합니다. 고정 복원과 혼합하거나 일반 기능 내부 쓰기로 확장하지 않습니다. 범용 복원에서도 검증 대상의 관찰 상태를 실행 전후 대조합니다.

시험 결과는 PASS, PRODUCT_MISMATCH_CANDIDATE, AUTOMATION_ERROR, ENVIRONMENT_ERROR, TIMEOUT입니다. 앞의 두 상태가 필수 증거를 갖추면 완료 후보로 인계합니다. 실패·미지원 후보는 제외 사유를 남겨 다른 후보 처리를 계속합니다.

예상된 기술 실패·미지원 제외와 프로그램 내부 예외는 구분합니다. 내부 예외 또는 agent3_error.json이 있으면 다른 후보의 독립 처리를 마친 뒤 전체 상태 ERROR·종료 코드 1을 기록하고 정상 후속 인계를 차단합니다. 일부 TC만 명시 선택하면 나머지는 미선택 사유로 남기고 PARTIAL로 표시합니다. 설계에 없는 TC ID는 오류이며, 오류 기록 중 손상 JSON을 만나도 원래 오류 유형과 읽지 못한 파일명을 남깁니다.

시험 기본 제한은 90초입니다. 초과하면 pytest·Playwright 자식 프로세스를 정리하며 쓰기가 끝나지 않은 Trace는 증거에서 제외합니다. 정상 Trace도 로컬 경로·비밀정보 정제를 마친 뒤 SHA-256을 기록합니다. 과거 Run을 소급 수정하지 않습니다.

`evidence_complete`는 Screenshot·Trace 존재 확인이며 복원 성공까지 의미하지 않습니다. 실제 해시가 맞는 로그의 RESTORE_MISMATCH를 Agent 4가 확인합니다. 제품 불일치와 복원 실패가 함께 있으면 두 관찰을 보존하고 자동화 문제·HOLD로 분류합니다. 같은 TC를 두 번 집계하지 않으며 코드에 인용된 표식이나 변조 로그는 근거가 아닙니다.

임시 작업공간은 원본과의 파일 분리를 제공하며 컨테이너·OS 권한 격리를 제공하지 않습니다. 실행기는 시작 상태를 위해 브라우저 저장소를 초기화하고, 기존 회귀에는 준비·오류 주입 하네스가 있습니다. 이를 일반 사용자의 UI 조작으로 표현하지 않습니다.

### 사전조건을 실제 값으로 확인하는 절차

새 Agent 3 계획은 각 TC 사전조건 원문에 `precondition_checks`를 연결합니다. 준비 Action을 실행했다는 사실이나 UI Inventory의 초기 값만으로 충족을 확정하지 않습니다. CP3-006A는 누락·원문 불일치·미관찰 경로·기대값 변형·복합 조건의 명시 값 누락을 검사합니다. 현재 CP3의 기본값과 새 실행·현재 후보 승인은 이 검사를 요구합니다.

읽기 방식은 UI 텍스트·입력값·체크 상태·활성 상태, TC에 근거하고 관찰된 내부 단일 값, 기존 중앙제어 장비의 제한된 기본 문맥입니다. 기본 문맥은 대상 카드 표시·오류 없음·잠금 해제·온라인을 각각 확인합니다. 온라인은 가상 제품의 OPERATION/STOP/ERROR 상태이며 실제 장비 통신 증명이 아닙니다. 관리자 로그인·인증을 장비가 보인다는 사실로 대신 증명하지 않습니다.

관찰 정보에 있는 모든 상태를 검사하는 것은 아닙니다. TC 사전조건에 적힌 내용만 확인하며, 원문에 없는 온라인·선택 상태 등을 추가 요구하지 않습니다. 기본 문맥 확인이 실패하면 항목 번호·관찰 이름·연결 원문·실패 이유를 재작성 입력으로 전달합니다. 불필요한 추가 확인을 제거하는 것과 실제 조건을 삭제하는 것을 구분하며, 기존 검사 기준·최대 1회 재작성·런타임 비교는 유지합니다.

Agent 3는 각 모델 계획을 검사 전에 시도별 파일로 보존해 이후 검사 오류와 분리합니다. 공통 저장 함수는 같은 폴더의 짧은 고유 임시 파일을 쓴 뒤 원자적으로 교체합니다. 최종 경로 자체가 운영체제 제한을 넘는 경우까지 지원한다는 뜻은 아니므로 실행 루트는 짧게 유지합니다.

| 상황 | 처리 |
|---|---|
| 사전조건 확인 항목 누락·부적합 | CP3 실패, 기존 최대 1회 재작성 후에도 실패하면 해당 TC 제외 사유로 최종 보고 |
| 허용된 읽기 방식으로 확인 불가 | 지원 범위 확장 사유를 남기며 실행 코드를 만들지 않음 |
| 준비 뒤 실제 값이 기대와 다름 | 본 TEST를 시작하지 않고 사전조건 불충족 기록. 자동화 실행 문제·HOLD이며 제품 불일치가 아님 |
| 모든 확인값 일치 | 본 TEST 진행. 성공한 시험도 stdout에 읽은 값과 확인 완료 기록 보존 |

컴파일러는 모든 PRECONDITION Action 뒤, 첫 TEST 앞에서 확인합니다. 비동기 상태 반영은 기존 2초 재관찰 helper를 이용하며 준비 조작을 반복하지 않습니다. 같은 시점의 일반 복원 기준은 유지하고, 원래 HVAC 상태 복원은 별도 계약대로 준비 전 값을 사용합니다. 실패 시 Screenshot·Trace와 오류 로그를 남깁니다.

새 Manifest의 `precondition_proof_contract=1.0`은 이 계약을 사용했다는 표시입니다. 과거 Manifest가 없는 계약의 인계·조회는 역사적 동작을 유지하지만 새 증명을 완료한 것으로 해석하지 않습니다. 현재 공식 후보 승인과 승인 전 재검증에는 증명 계획이 필요하므로 과거 계획은 새 계약의 계획·시험 확보가 필요할 수 있습니다. 기존 승인 자산을 소급 취소하거나 바꾸지는 않습니다.

이 계약은 **사전조건마다 확인 근거를 연결하고 실제 값을 비교하는 것**입니다. 임의의 자연어·복합 문장 전체가 올바르게 해석됐다는 수학적 증명이나 모든 제품의 의미 동등성 보장은 아닙니다. 관찰 가능한 조건과 확인 불가능한 조건을 구분하며, 최신 프롬프트의 실제 모델 생성 검증은 별도 실행 결과로 판단합니다.

## 7. 변경 검증과 기존 회귀

`execute`는 Agent 3 Manifest·계획·코드·시험·증거를 확인하고 현재 CP3로 다시 검사합니다. 현재 컴파일러 출력과 같으면 시험 결과를 재사용하고, 다르면 별도 위치에서 재컴파일·재시험합니다.

환경 점검 TC-ENV-000을 먼저 실행하고 Agent 2가 명시한 관련 기존 TC만 중복 없이 실행합니다. 신규 후보가 없거나 전부 제외돼도 요약·환경 점검·선택 기존 TC·보고를 계속할 수 있습니다. 환경 점검이 실패하면 기존 회귀를 중단합니다.

기본 대상은 `product_baseline/virtual-controller.html`, 기존 회귀는 같은 폴더의 `tests/test_controller.py`입니다. 테스트와 HTML을 임시 Workspace에 복사하고 선택 함수만 실행합니다. 승인 공식 TC도 카탈로그 사본과 현재 자산 해시가 같아야 실행하며 기준 파일은 변경하지 않습니다.

기존 회귀도 후보 시험과 같은 프로세스 트리 종료 함수를 사용합니다. SKIPPED 여부는 임의 경고문 단어가 아닌 pytest 결과 요약 형식에서 판독합니다. 임의 테스트 프레임워크 출력 전체를 지원하는 파서는 아닙니다.

## 8. Agent 4: 분류·보고와 CP4

모델 호출이나 시험 재실행 없이 저장 결과를 제품 불일치 후보·자동화 문제·환경 문제·근거 부족·미실행으로 분류합니다. TC 설계 유형인 정상·경계·예외·상태 정합성과 실행 후 원인 분류는 별도 정보입니다.

| 상황 | 최종 권고 |
|---|---|
| 실행 범위 통과, 증거 유효, 자동화 제외·정보 부족 없음 | PASS |
| 유효한 제품 기대값 불일치 | HUMAN_REVIEW: 사람이 판단 |
| 실행한 TC는 통과했지만 자동화 제외·정보 부족이 남음 | HUMAN_REVIEW: 미확인 범위 검토 |
| 실행 결과의 자동화·환경 오류, 미실행·증거 부족 | HOLD: 보류 |
| 제품 불일치와 복원 실패 동시 발생 | HOLD, 두 관찰 보존 |
| CP4의 증거·집계 검사 실패 | HOLD, 외부 전송 차단 |

앞 단계에서 기술 실패 후보가 제외 목록으로 전달되면 자동화 제외·사람 검토 경로를 따릅니다. 의도적으로 정한 범위 밖 항목만으로 사람 검토를 강제하지 않습니다. 개별 기대 결과의 관찰 근거가 없으면 통과로 추정하지 않습니다.

CP4는 Run·입력 해시, TC 중복, 상태·종료 코드·메시지·증거, 제품/환경 집계, Agent 3→실행 전체 인계와 보고 수치를 확인합니다. V1 회귀는 기준 코드 해시, 승인 회귀는 카탈로그 사본과 승인 코드 해시로 검증합니다.

`사람_최종_검토.md`에는 기대·실제 관찰·증거, 제품 수정/요구사항 보완/자동화 재검토/환경 재실행/종결 선택지, 검토자·일자·기한·후속 조치란이 있습니다. Manifest는 생성 원본과 보고의 해시를 연결합니다. 사람이 편집한 문서는 자동 갱신으로 덮어쓰지 않으며, 미편집 원본만 `human-review --refresh`로 갱신할 수 있습니다.

CP4와 최종 보고 해시가 통과해야 Slack·Notion Payload를 생성합니다. 기본은 미리보기, CLI `--send`는 실제 전송입니다. Notion은 Run ID:TC ID로 같은 실행만 갱신하고 다른 실행을 보존합니다. 최초 전송 기록은 유지하고 후속 시도는 별도 폴더에 저장합니다. 화면은 최신 시도와 과거 실제 전송을 구분합니다.

Notion 기록은 실행 결과가 있는 TC의 제목·결과·분류·보고 요약과 상세 TC 본문입니다. Agent 2 인계 Manifest가 있고 기존 보고 소비 단계에서 해시·Checkpoint 재검증이 통과한 Run에 한해 저장된 사전조건·조작·기대결과의 확인 대상/판정 단계·복원을 `notion_payload.json`의 `tc_detail`로 전달합니다. 본문은 사전조건 → 조작 순서·단계별 기대결과 → 복원 순서입니다. 기대결과는 설계이며 실제 관찰값이나 공식 등록 승인으로 표시하지 않습니다. 승인 TC는 해시가 맞는 보존 명세를 사용하고, 원문 단계에 유일하게 연결되지 않는 과거 기대결과는 별도 목록으로 표시합니다. 상세 설계 연결이 없는 환경 점검·과거 기록에는 미기록 상태를 표시하며 내용을 추정하지 않습니다. Agent 2 초안만 별도 게시하는 기능은 없습니다.

본문은 내용 해시로 구분한 자동 기록 펼치기 블록을 추가합니다. 같은 내용은 기존 본문과 대조한 뒤 건너뛰고, 변경된 내용은 새 기록으로 남깁니다. 사람이 작성한 블록을 삭제하지 않으며 자동 기록 내부의 문구가 편집됐으면 덮어쓰지 않고 실패로 알립니다. 긴 본문은 나누어 전송하고, 중간 실패 뒤 재시도하면 확인된 부분은 유지합니다. 요약 속성 저장 후 본문 전송이 실패할 수 있으므로 상세 전송까지 끝나야 해당 건을 완료로 집계합니다. 동시에 같은 기록을 보내는 작업의 중복 방지나 오류 자동 재시도는 보장하지 않습니다. 읽기·삽입 권한과 실제 계정에서의 게시 확인은 별도로 필요합니다. 요청 크기·중첩은 [Notion 본문 추가 규격](https://developers.notion.com/reference/patch-block-children)과 [요청 제한](https://developers.notion.com/reference/request-limits)을 따릅니다.

## 9. 중앙제어 화면과 사람 승인

| 모드 | 동작 |
|---|---|
| HTML 직접 열기·공개 접속 | MED 정상 변경 저장 데모, API·시험·실제 파일 반영 없음 |
| 기본 로컬 서버 | 저장된 Run 조회 |
| --allow-live-run | 허용된 변경 요청 선택·화면 확인 뒤 Agent 1→4 실행 |
| --allow-asset-approval | 조건이 유효한 후보의 사람 승인·보류 |

로컬 입력은 `examples/change_request*.json`이며 임의 경로·쉘 명령은 받지 않습니다. Run ID를 명시하고 기존 ID 재사용을 거부합니다. 서버 SRS·승인 자산 경로를 분석·실행·승인에 함께 전달하며 저장소 단위 파일 잠금으로 중복 Live 실행을 막습니다.

쓰기 POST는 서버 포트의 localhost/127.0.0.1 Host와 동일 Origin, application/json 본문을 요구합니다. 외부 출처·Origin 없음/null·다른 Host 요청은 거부합니다. 이는 로컬 브라우저 요청 보호이며 사용자 인증이나 악성 로컬 프로그램 격리가 아닙니다. 공개 서버를 추가하지 않습니다.

제품 시험은 별도 브라우저에서 수행됩니다. 페이지는 실행 상태·결과를 조회하며 재접속 후에도 갱신합니다. 조회한 Run과 실행 중 Run을 구분하고 늦은 응답은 현재 선택을 덮지 않습니다. 연결 실패는 확인 불가로 표시·재시도합니다. GET 대기는 10초, 승인/재검증 POST는 180초이며 HTTP 대기 종료가 서버 시험 취소를 의미하지 않습니다. Run 전환 시 승인·SRS 동의·메모를 초기화합니다.

최종 보고가 없으면 중간 단계 PASS를 전체 PASS로 표시하지 않습니다. 환경 실패로 유효한 BLOCKED 실행 결과가 저장됐으면 Run·해시 확인 뒤 Agent 4로 넘기며, 결과 누락·손상이나 다른 실행 오류는 중단합니다.

TC 표는 설계·실행·제외·분류를 합쳐 유형·결과·사전조건·절차·기대·복원·관찰·증거를 보여줍니다. 기록 없는 유형·우선순위·기존 TC 상세는 추정하지 않습니다. 새 Run은 승인 TC 원문 사본을 사용하고 과거 Run은 지정된 자산 폴더와 해시를 확인합니다.

### 공식 TC 등록

1. 사람이 PASS 후보의 명세·증거·확인 사항을 검토합니다.
2. 서버가 최종 PASS, CP3·CP4 PASS, 변경 검증 PASSED, 필수 증거와 코드·현재 HTML 해시를 확인합니다.
3. HTML이 바뀌었으면 같은 후보를 현재 화면에서 모델 호출 없이 재검증합니다.
4. SRS 제안이 있으면 후보 Requirement·Condition에 연결된 개정 전후 문구를 보여주고 별도 동의를 받습니다.
5. 승인 TC·Python과 검토자·메모·출처·해시를 approved_assets에 기록합니다.
6. 다음 Agent 2가 등록 자산을 기존 TC 카탈로그에서 대조합니다.

승인 후보 코드는 Agent 3와 변경 검증 기록의 코드 해시 모두와 일치해야 합니다. 다른 코드이면 승인과 승인 전 재검증을 차단합니다. 재검증 Raw 증거는 로컬 Run에, 공개 가능한 요약은 approved_assets/provenance에 보존하고 두 해시를 구분합니다.

같은 Run·TC 중복 승인은 같은 기록을 반환합니다. 보류는 사유만 남기며 이미 승인한 자산을 보류로 되돌리지는 않습니다. 등록 중 오류가 나면 해당 승인에서 바꾼 SRS·TC·Python·Registry·임시 파일을 복구합니다. 사람 검토서 작성만으로 Registry가 바뀌지 않습니다.

기존 TC만 실행한 Run도 유효한 Agent 1/2 인계·실행·현재 제품·기존 TC 조건 연결·SRS 원문을 확인해 SRS_ONLY 승인을 할 수 있습니다. 검토자·메모·SRS 동의와 화면 확인이 필요하며 TC·Registry는 새로 만들지 않습니다. 판단 기록 실패 시 SRS를 원상복구합니다. 동일 제안은 멱등 처리하고 다른 원문으로 바뀐 SRS는 거부합니다.

## 10. 파일과 인계 계약

| 파일/경로 | 역할 |
|---|---|
| agent1_change_analysis.json, agent2_test_design.json | 분석·제품 TC·SRS 제안 |
| checkpoint1.json ~ checkpoint4.json | 자동 검사 결과 |
| agent3_selection.json | 후보 선택·사전 제외 사유 |
| agent3_candidates/각-TC/ | 후보별 계획·코드·시험·증거 |
| agent3_run_summary.json | 다중 실행의 완료·제외 요약 |
| orchestrator_manifest.json | Agent 1~3 종료와 주요 해시 |

단일 agent3 CLI는 루트 agent3_manifest.json·agent3_trial.json을 사용하며 다중 요약이 없습니다. CP4는 정확한 단일 경로·해시를 검사하고, 다중 실행에는 요약을 요구합니다. 과거 일괄 모델 호출 agent3_batch_*는 현재 실행 계약이 아닙니다.

공통 구조는 Pydantic JSON·SHA-256 인계·단계별 최대 1회 재작성입니다. 역사적 existing_procedure_review_contract, existing_behavior_values_contract, double_assert_timing_contract가 없는 Run에는 새 CP2 규칙을 소급 적용하지 않습니다. 현재 후보 재검사와 과거 증거 조회는 서로 다른 처리입니다.

새 Agent 1·2 Manifest의 meaning_guard_contract=1.0은 위 명백한 의미 오류 검사를 사용했다는 표시입니다. 이 표시가 없는 과거 인계는 당시 규칙으로 대조하며 원본 판정·해시를 바꾸지 않습니다. 과거 통과가 새 규칙 검증 완료를 뜻하지 않습니다.

공개 진입점 src/qa_pipeline_v2.py는 import·CLI 호환을 유지합니다. 내부 구현은 contracts, agent1, agent2, agent3, execution, reporting, orchestrator와 공통 io/trace, UI 표시 계층으로 나뉩니다. 테스트는 7개 역할 파일과 pipeline_test_support.py를 사용합니다.

### 후속 감사에서 보완한 연결 검사

- 신규 TC의 기대 결과는 연결된 조건의 코드·수치와 명백한 허용/차단·활성/비활성 방향을 보존해야 합니다. 테스트 입력을 정상 출력의 근거로 삼지 않습니다. 명시 범위 안의 값, 유지 조건의 사전 값, 차단할 입력을 지칭한 기대 문장은 구분합니다. 자연어 의미 전체의 동일성을 보증하는 검사는 아닙니다.
- 새 Agent 2 Manifest의 `candidate_expectation_contract=1.0`은 이 검사를 실행했다는 표시입니다. 과거 Run은 당시 CP2 판정으로 조회하되 현재 신규 자산 승인에서는 기대 결과와 CP3 계획을 다시 검사합니다.
- 상태를 확인하는 문자 검사는 고정된 제어 이름만 검사해서는 안 됩니다. 비활성 전용 전략은 명시적 비활성 기대에만 사용합니다.
- 일반 고정 복원은 TC 준비 완료 직후, TEST 이전의 상태와 비교합니다. `RESTORE_OBSERVED_HVAC`는 준비 전 모드·온도를 복원합니다. 사전조건 원문별 읽기 근거와 실행 직전 실제 값 확인은 위 사전조건 절차를 따릅니다. 임의 자연어 의미 전체의 동등성은 보장하지 않습니다.
- 보고 재사용 시 실행 JSON→Agent 4 분석→최종 보고의 해시와 공통 내용, 후보·회귀 증거, 존재하는 Agent 1·2 원본 연결을 재검사합니다. 공식 후보 승인과 승인 전 재검증은 TC→계획·관찰·CP3 연결도 확인합니다.
- 필수 UI 인터페이스 누락은 그 TC의 제외 사유이며 예기치 않은 코드 예외는 내부 오류입니다. 같은 서버의 동시 승인 요청은 잠금으로 직렬화하고 Run 전환 후 늦은 POST 응답은 화면에 적용하지 않습니다.

## 11. V1 기준 자산과 검증 경계

V1 커밋 ba62b611251180cbd0426eae0f9ab43a67a12abf에서 HTML·pytest.ini·tests/conftest.py·tests/test_controller.py 네 파일만 product_baseline에 가져왔습니다. 기존 TC는 변경분 생성 재료가 아니라 관련 회귀 실행용 기준 코드입니다. V2 HTML은 제품 보완과 Run·데모 패널 추가로 V1 원본과 전체 해시가 다릅니다.

V1의 13건은 환경 점검 1건, 제품 기능 후보 7건, 제품 불일치 분류 고정 사례 1건, 파이프라인 분류 고정 사례 4건이 섞인 자료입니다. 제품 회귀 성공률로 합산하지 않습니다. 당시 TC/요구사항 대응과 GAP 감사표는 [결정 기록의 V1 감사 부록](../DECISION_LOG.md#v1-baseline-audit)에 보존합니다.

현재 제품 범위는 중앙 관제 패널입니다. 실제 Modbus/MQTT, 역할 전환 UI, 연결되지 않은 필터·장치정보·도움말, 벽면 리모컨은 구현 범위로 소개하지 않습니다. 제품 기대값은 [SRS](01_PRODUCT_SRS.md)를 따르며 구현과의 차이를 자동으로 정상 기준으로 바꾸지 않습니다.

검증에서는 요청→조건→TC→Action/Assertion→코드→증거→보고 추적, 후보/회귀/환경 집계, 원본 불변, 승인 동의·원상복구, 공개 데모 무통신·비반영을 확인합니다. 자동 테스트 수와 제품 Run TC 수는 합산하지 않습니다. 현재 통과 이력·간헐적 오류·실제 API 검증 범위는 인계 문서에서 확인합니다.
