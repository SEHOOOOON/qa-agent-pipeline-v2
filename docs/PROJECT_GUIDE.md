# 프로젝트 안내: 현재 처리 기준

## 검사 책임과 작성 형식

새 A2 실행(`agent2-2.56`, `essential_validation_contract=1.0`)은 다음 기준을 생성·재작성·의미 검토·저장 인계에서 함께 사용합니다. 과거 Manifest에는 당시 정책을 적용합니다.

| 점검 항목 | 현재 처리 | 남겨 둔 보호 |
|---|---|---|
| 제목·purpose·test_type·묶음 설명 | 제목 중복/분류명/설명 생략만으로 반려하지 않음. 구조화 신규 후보는 분류명으로 Agent 3에서 제외하지 않음 | 고유 ID, 실제 조건 연결·TC 범위·요구된 UI/내부 확인 |
| 실행기 기록·복원 | 실행 정의가 있으면 별도 HVAC 표시나 기록/복원 키워드를 요구하지 않음 | 구조화 복원 조작·관찰 대상·BEFORE_SETUP 비교·실행 실패 처리 |
| 값·시점의 중복 작성 | 실행 정의가 실제 조작과 값/시점의 기준. test_data의 복수 나열을 문장에서 다시 추출하지 않음 | 실행 정의 누락·순서·확인 시점 검사, 원문과 실제 값의 필수 의미 검토 |
| 다른 TC 언급·유지 분류 | 단어 등장/VERIFY 분류만으로 의존·중복 생성으로 단정하지 않음 | 독립 실행 불가 선언은 차단. 기존 TC 범위·실제 의존/불필요 복제는 필수 의미 검토 |
| 초기 화면 비활성 | 기존 실행 인터페이스 계약 유지: 처음 비활성을 이후 조작 불가로 단정하지 않음 | 요소 존재·유일성·종류·대상 검사, 실행 시 Playwright 가용성·오류·복원 |
| 출처·인계·최종 승인 | 축소 대상 아님 | 원문 출처·해시·실행 증거·사람 승인 전 공식 자산 보호 |

검사 책임 이동은 자동 통과가 아닙니다. 필수 의미 검토의 반려·불확실·자료 누락은 계속 중단하며, 코드가 모든 표현의 뜻을 판단한다고 주장하지 않습니다. 상세 TC 원문은 유지하고 표현을 실행 편의에 맞춰 다시 쓰지 않습니다. 로컬 검사는 전달·차단 분기를 검증할 뿐 실제 검토 AI의 정확도를 대신하지 않습니다.

고정 기대값 계약: `FIXED_ASSERTION_TEXT`를 A2 구조 검사·A3 계획 검사·컴파일러가 공유합니다. 비활성 온도 표시의 expected_text는 생략하거나 동일한 `---`를 명시할 수 있습니다. 다른 값이나 다른 reader에서 사용하지 않는 값은 무시하지 않고 차단합니다. TC 원문과 저장 원본은 정규화로 덮어쓰지 않습니다. 출처·인계 무결성·필수 확인·복원·승인 검사는 유지합니다.

Slack 알림은 시험 내용·검사 기준과 결과·제품/환경 집계·다음 단계로 표시합니다. 검사 기준은 실제 관찰값과 구분하며 복원 확인은 저장 로그가 뒷받침할 때만 표시합니다. 긴 내용은 요약하고 상세 보고서 확인을 안내합니다. 자동 PASS는 공식 승인이나 출시 판정이 아닙니다. Notion 형식과 보고 판정 로직은 이 표시 변경의 대상이 아닙니다.

이 문서는 현재 구현의 기술 참조입니다. 소개·실행 명령은 [README](../README.md), 검증 결과와 남은 작업은 [인계 문서](../PROJECT_HANDOFF.md)에서 관리합니다. 이전 설명은 [정리 전 보존본](../archive/2026-09-28/PROJECT_GUIDE.md)에 남겼습니다.

## 1. 목적과 전체 흐름

### 기존 베이직 TC 상세 연결

`docs/basic_tc_details.json`은 기존 Python 베이직 시험의 준비·순서·기대결과와 한계를 설명한다. 원래 검사 함수·기대값은 변경하지 않는다. 현재 카탈로그 생성 시 기준 시험 파일 SHA-256을 대조하고 `baseline_details`에 상세 원문과 항목별 해시를 저장한다. A2 재사용 입력·저장 보고서·P2 A2/A3 평가 입력은 같은 Snapshot을 사용한다. 코드가 변경되면 설명을 함께 검토해야 하며, 실행 시에도 저장 명세의 코드 해시와 비교한다.

이 자료는 신규 TC의 `execution_spec`이나 새 AI 작성/검토 결과가 아니다. 다중 장비 잠금·현장 명령·오류 주입·색상·로그 등 기존 검사는 기존 함수가 수행한다. 온도/FAN/DRY의 선택 상태 시험을 장비 적용 시험으로 바꾸지 않는다. 환경 점검은 제품 시험과 구분하며 상세 제품 TC 6건에 합치지 않는다. `baseline_details`가 없는 과거 Snapshot에는 현재 상세를 채워 넣지 않는다.

`native-recovery-1.0` 기본 TC는 공통 pytest 실행 래퍼가 원래 함수 호출 전 전체 장비 객체·카드·제어패널·선택·pending 상태를 저장한다. 원래 함수의 준비/시험이 끝나거나 실패해도 finally에서 변경 여부를 확인한다. 변경되면 가상 시스템 localStorage 복구와 reload로 오류 주입·다중 잠금까지 되돌리고 동일 관찰을 다시 읽어 비교한다. 변경이 없으면 복구 조작 없이 UNCHANGED를 기록한다. 이는 제품 조작을 대신한 합격 판정이 아닌 시험 환경 정리 방식이다. 로그·알림 이력은 제품 상태 복원 비교 대상이 아니다.

복원 실패는 제품 불일치와 구분한 EXECUTION_ERROR/RESTORE_MISMATCH이며 해당 브라우저 컨텍스트를 닫는다. 다음 TC는 기존처럼 별도 프로세스/컨텍스트에서만 실행한다. 성공 종료인데 복원 JSON이 없으면 실행 오류다. `native-restoration.json`에 준비 전·복원 후 실제 관찰, 계약·어댑터 해시·TC ID를 기록하고 실행 증거 해시 목록에 연결한다. P2는 해시/TC를 검증하고 각 관찰 영역의 전후 동등 여부를 대조해 전달한다. 새 계약이 없는 과거 Snapshot은 기존 동작으로 재현하며 새 복원 성공으로 표시하지 않는다.

Windows 저장 경로: A1 시작·A2 이어 실행 전에 표준 후보/회귀 증거 경로를 검사하고, A3와 기존 회귀 실행에서 실제 후보 경로를 다시 검사한다. 최종 파일과 같은 폴더의 원자적 쓰기 임시 이름을 UTF-16 길이로 확인한다. 260 미만이라는 보수적 호환 기준이며 OS의 긴 경로 지원 설정을 변경하지 않는다. 짧은 `--runs-root`를 사용해야 하고, 읽기 전용 과거 결과 조회에는 적용하지 않는다. 임의 길이의 모든 파일명·외부 도구 경로를 보장하는 검사는 아니다.

오래된 승인 코드는 새 컴파일러가 생겨도 자동 교체하지 않는다. 원래 TC와 검증된 실행 계획을 유지한 재생성 사본은 교체 검토 후보이며, 로컬 성공만으로 공식 등록·과거 성공 기록을 바꾸지 않는다.

이 경계는 회귀검사에도 적용한다. 등록 파일은 Registry와 당시 유지보수 검증 해시로 무결성을 확인하고, 저장 계획 및 현재 생성 결과는 TC 계약과 별도로 대조한다. 최신 컴파일러의 출력과 과거 등록 파일이 바이트까지 같아야 한다고 요구하지 않는다. 코드 생성기 보완이 공식 자산의 자동 갱신이나 과거 성공 증거가 되지는 않는다.

사용자가 명시적으로 요청한 기존 자산의 형식·복원 보완은 별도 유지보수 버전으로 보존한다. `approved_assets/revisions/`의 현재 TC·코드는 registry가 해시로 가리키며 `maintenance_revision`에 이전 파일·해시, 변경 사유와 별도 승인 근거를 남긴다. 기존 `source_run_id`·승인 일시는 최초 등록 이력이지 수정본을 생성·평가한 Run이 아니다. 과거 파일·SRS 개정·저장 실행·평가 점수는 그대로 둔다. 새 TC 등록의 Checkpoint/사람 승인 절차나 런타임 자동 변환 기능을 대신하지 않는다.

기존 SRS와 TC를 기준으로 변경 요청을 분석하고, 필요한 시험을 수행한 뒤 사람이 재사용할 자산을 승인합니다. 모든 자연어 요청을 자율 처리하는 제품이 아니라 가상 중앙제어용 QA 파이프라인입니다.

| 단계 | 입력 | 출력·책임 |
|---|---|---|
| Agent 1 | 변경 요청·관련 SRS | 확정 조건·영향 범위·미정 조건·확인 질문 |
| Agent 2 | 검증된 분석·원문·기존 TC | 사용할 기존 TC·새 상세 TC·필요한 SRS 개정 제안 |
| Agent 3 | 검증된 후보 TC·제품 화면 | 자동화 코드·제품 시험·복원·실행 증거 |
| 변경 검증 | 후보 결과·선택 기존 TC | 환경 점검·관련 회귀·미실행 사유 집계 |
| Agent 4 | 실행 결과·증거 | 규칙 기반 분류·최종 보고·사람 검토서 |
| 사람 | 보고·SRS 개정안·TC·코드 | 추가 등록·선택 대체·미등록·보류. 승인 자산은 다음 요청에서 재사용 |

Agent 1·2는 모델이 작성하고 Agent 1·2·3에는 별도 의미 검토가 있습니다. Agent 4는 모델을 호출하지 않습니다. 포폴에서는 위 역할과 산출물만 설명하며 아래 내부 용어를 나열하지 않습니다.

### 범위

- 현재 실행 어댑터: 가상 중앙제어의 전원·모드·풍량·온도·잠금, 대상 장비 ID 1.
- 제품 자체의 다중 장비 지원과 자동 생성 파이프라인의 지원 범위는 다릅니다.
- 요청 유형은 MODIFIED가 현재 범위입니다. 요청에 근거한 미구현 기능의 TC는 설계할 수 있으나 실제 조작 수단이 없으면 실행하지 않습니다. ADDED·DELETED 전체 지원을 뜻하지 않습니다.
- 실제 장비 통신·임의 웹사이트·전체 회귀·무제한 자동 복구는 범위 밖입니다.
- V1은 Fixture 기반 Workflow Prototype입니다. V2의 제품 복사본과 승인 자산을 V1 원본에 소급 반영하지 않습니다.

## 2. Agent 1 · 요구사항과 범위

제품 기대값은 요청·SRS에서 정합니다. 화면 관찰값을 정답으로 복사하지 않습니다. 기존 허용 범위 안 시험값을 새 정책 변경과 혼동하지 않으며, 준비값과 본 시험의 목표값을 구분합니다.

분석은 조건 원문·근거·역할, 시험 절차, 제외, 정보 부족을 연결합니다. 요청에 SRS 번호나 전체 문장이 없다는 이유 또는 영향 분류 이름만으로 자동 보류하지 않습니다. 출처와 조건 전달은 코드가 확인하고, 요청의 의미·누락·범위 확대는 별도 모델이 검토합니다.

새 Agent 1(`agent1-2.24`, `requirement_link_contract=1.0`)은 조건 목록의 `requirement_ids` 한 곳에 연결을 작성합니다. 영향 분석의 `scope_evidence.request_condition_ids`는 같은 Requirement에 연결된 CHANGE_REQUEST 조건에서 프로그램이 계산합니다. AI 입력 스키마에는 이 중복 입력란이 없습니다. SRS 인용만으로 요청 연결을 만들거나 연결이 빠진 기준을 임의로 추가하지 않습니다. 완성된 같은 분석을 CP1·의미 검토·Agent 2가 사용합니다.

모델 원본과 계산된 인계 결과를 별도로 보존하고 해시·재계산 결과를 대조합니다. 계산된 연결이 있다는 사실만으로 의미 검토를 통과시키지 않습니다. 기존 실행은 당시 계약과 원본을 유지하며 새 형식으로 자동 보정하지 않습니다.

- 확정된 범위가 독립적이면 미정 항목을 남긴 부분 진행이 가능합니다.
- 핵심 조건이 불명확하거나 검토 모델이 판단을 유보하면 인계를 중단합니다.
- Agent 1의 진행 결정은 시험 설계 가능 여부이지 사람의 SRS 승인 동의가 아닙니다.
- 질문은 원문 그대로 최종 확인 사항에 전달합니다. 답을 추정하지 않습니다.
- 로컬 화면은 Agent 1의 `WAITING_FOR_USER`, CP1 `PASS/PAUSE`, 해당 Run의 단계 종료와 저장 해시가 일치하면 ‘사용자 확인 대기’와 질문 원문을 표시합니다. 이는 저장된 중단 사유의 표시이며 의미 재판정·인계 허가·자동 재개가 아닙니다. 실제 오류, 검토 실패, 누락·불일치 기록을 정상 대기로 바꾸지 않습니다.
- SRS 인용의 `|`는 두 기능 또는 특정 열 의미로 단정하지 않고 실제 인용 조각의 출처를 확인합니다.

## 3. Agent 2 · 상세 TC와 기존 TC 재사용

기존 TC는 이름이나 Requirement ID만 같다고 재사용하지 않습니다. 사전조건·조작·기대결과를 요청과 대조합니다. 기존 TC 전체가 명시적인 제외 범위와 충돌하면 일부 검사만 지워 재사용한다고 가정하지 않습니다.

| TC에 필요한 내용 | 기준 |
|---|---|
| 사전조건 | 시험 대상·시작 상태·준비 절차 |
| 조작 단계 | 선택·설정·적용을 실제 행동 순서로 작성 |
| 기대결과 | 확인할 대상·기대값·판정 시점. 독립된 사실은 구분 |
| 출처 | 요구사항·확정 조건과 연결 |
| 복원 | 유형에 맞는 복원·확인 절차 |
| 실행 정의 | 조작·관찰의 논리 항목·값·순서·시점. DOM 선택자는 포함하지 않음 |

상세 문장과 실행 정의는 한 TC에 포함되지만 별도 필드입니다. 모든 표현을 하나의 필드에서 자동 생성한다고 설명하지 않습니다. 두 표현의 의미 일치는 검토 대상이고 모델 오판 가능성이 남습니다.

새 TC가 필요 없으면 후보 0건도 정상입니다. 기존 TC 선택과 해당 TC가 확인한 조건의 연결은 별도로 확인합니다. TC 전체 검사 범위를 실제보다 넓게 완료했다고 표시하지 않습니다.

새 A2 계약 `agent2-2.56 / tc_execution_alignment_contract=1.0 / essential_validation_contract=1.0`은 다음을 공통 적용합니다. 실행 정합성 연결은 2.55에서 도입했고, 2.56은 위 작성 형식 정리를 적용합니다. 과거 실행의 저장 검사·검토 입력은 당시 계약으로 재구성합니다.

- 재사용 대상 연결은 요청 대상의 변경 조건뿐 아니라 유지·재확인 조건도 인정합니다. 보조 근거만의 연결, 다른 요구사항·알 수 없는 TC는 충분하지 않습니다. 실제 조작·값·필수 검사 범위는 기존 의미 검토가 계속 대조합니다.
- 경계 TC에 유효한 실행 정의와 본시험 조작이 있으면 모드·온도 요청값의 중복 입력을 강제하지 않습니다. 상대 버튼 조작에 유지 기대값을 입력값으로 채우지 않습니다. 원문·기대값·시점 누락 검사와 의미 검토는 유지합니다.
- 공통 복원이 실제로 연결되는 TC에만 A3와 같은 복원 기능 근거를 A2 검토에도 전달합니다. 준비 전 전체 관제 상태 기록과 복원 후 비교를 설명할 뿐 제품 기대값의 근거나 실제 화면 가용성·복원 성공으로 취급하지 않습니다. 지원되지 않거나 잘못 연결된 복원에는 근거를 만들지 않습니다.

SRS 개정은 제품 기준이 실제 달라질 때 제안합니다. 기존 기준을 시험하는 것만으로 개정하지 않으며 이미 반영된 동일 문장을 다시 제안하지 않습니다. 제안이 있어도 사람 승인 전 기존 SRS를 덮어쓰지 않습니다.

한 흐름·독립 입력 조합·순차 전환은 구조화된 실행 방식으로 구분합니다. 정상·경계·예외 등의 QA 분류와 상세 작성 예시는 작성 지침이며, 설명 문체만으로 통과를 결정하지 않습니다.

## 4. Agent 3 · 자동화와 실제 시험

현재 신규 `controller-map-1.0` TC는 제품 연결표로 실행 위치를 확인하고 TC 정의를 복사해 조립합니다. 위치 생성용 AI 호출·재작성은 없습니다. 미지원 항목을 비슷한 다른 기능으로 대체하거나 과거 모델 계획 경로로 우회하지 않습니다.

- 코드가 조작·기대값·시점·원문 참조의 동일성을 확인합니다.
- 별도 모델 검토는 원래 TC와 실제 관찰 위치·지원 여부의 연결을 검토합니다.
- 허용 목록 기반 컴파일러가 Playwright Python을 생성합니다. AI가 자유 Python 코드를 직접 실행하는 방식이 아닙니다.
- 실행 정의가 없는 과거 TC는 당시 계획 생성·검토 계약으로 읽습니다. 과거 호환을 현재 신규 경로로 소개하지 않습니다.

### 화면 조사와 제품 시험 구분

새 A3 실행의 `execution_interface_contract=1.0`은 화면 수집 시점과 조작 시점을 구분합니다. CP3는 요소 존재·유일성·조작 종류·TC 연결을 검사하지만, 초기 `visible/enabled`만으로 이후 동작을 반려하지 않습니다. 대상 선택·준비 뒤 실제 조작 시 Playwright가 실행 가능 여부를 확인하고, 계속 사용할 수 없으면 오류·복원 결과를 남깁니다. 제품 기대결과의 활성/비활성 검사와 복원 실패 후 중단은 그대로입니다. 사용할 수 없는 요소를 실행 전에 전부 판별하는 보장은 없으며 늦은 오류가 날 수 있습니다.

같은 계약의 의미 검토에는 `EXECUTION_INTERFACE`를 전달합니다. 온도 설정의 대표 위치는 표시창이지만 실제로는 표시값을 읽고 올림/내림 버튼을 사용합니다. 연결표·컴파일러·검토 자료의 온도 위치는 같은 상수를 사용합니다. 두 온도 버튼을 함께 읽는 검사와 패널/카드 상태 읽기도 복합 읽기임을 명시합니다. 이 자료는 구현 방식과 관찰된 요소의 근거이지 시험 성공 증거가 아닙니다. 기대값·순서·필수 검사·대상 연결은 계속 검토합니다.

지원하는 모든 검사 전략에 읽는 대상·비교 방식·실제 기대값·확인 시점을 전달합니다. 계획의 값은 그대로 사용하며, 비활성 온도 표시처럼 전략에 고정된 값은 실행 코드와 같은 상수를 사용합니다. 설명만으로 검토를 통과시키거나 과거 판정을 변경하지 않습니다. 입력이 변경되면 기존 검토 해시를 재사용할 수 없습니다.

저장된 검토를 재사용할 때는 계약 형식·단계·입력 해시를 따로 확인하고, 불일치 원인을 구분해 안내합니다. TC·계획이 같아도 검토자에게 주는 실행 방식 설명이나 출처가 바뀌면 입력은 달라집니다. 이는 제품 불일치 판정이 아니라 이전 판정의 재사용 중단입니다. 원본을 보존하고 변경 내용을 확인한 뒤 현재 입력을 별도로 검토해야 합니다. 자동으로 과거 해시를 갱신하거나 API를 다시 호출하지 않습니다.

실행 인터페이스 계약은 `agent3-3.44/3.45`부터 적용합니다. 현재 새 실행은 실행 정의가 있으면 `agent3-3.46`, 과거 형식이면 `agent3-3.47`이며 `value_comparison_contract=1.0`도 기록합니다. 새 자동화의 동등 비교는 참/거짓과 숫자를 구분하되 숫자 21과 21.0은 같은 값으로 봅니다. 복합 내부값과 복원 비교에도 적용하고, 문장 의미나 문자열 대소문자를 새로 해석하지 않습니다.

신규 실행·재작성·저장 결과 재검사·승인 재검사가 같은 버전 옵션을 사용합니다. 과거 Run은 당시 비교 방식과 입력 해시·판정을 보존하며 공식 자동화를 자동 교체하지 않습니다. 새 설명으로 과거 의미 검토를 통과시키지도 않습니다.

UI Inventory는 실제 요소의 존재·표시·활성·단일성, 장비 식별과 필요한 내부값을 수집합니다. 조작 종류는 DOM 태그·역할·입력 종류와 요소에 직접 연결된 `onclick` 함수로 기록하며 버튼 설명 문구를 조작 코드로 비교하지 않습니다. 같은 판별 함수를 지정 요소 수집과 일반 탐색에 사용하고, 검토에도 그 결과를 전달합니다. 입력창·체크박스 등의 전용 조작을 클릭으로 바꾸지 않으며 함수 본문을 수집·전송하지 않습니다.

클릭 힌트는 실제 동작 성공의 증거가 아닙니다. 커서 모양·설명·연결표 등록만으로 클릭 가능을 추정하지 않습니다. 직접 연결되지 않은 이벤트 리스너나 상위 요소의 위임 이벤트는 이 수집 방식으로 확인하지 못할 수 있습니다. 기존 장비 선택 실행은 클릭 후 선택된 장비 ID를 확인하고, 이어서 TC의 화면·내부값과 복원을 검사합니다. 과거 관찰 파일과 그 검토 판정은 소급 수정하지 않습니다.

작성 목록과 수집할 내부값은 같은 제품 연결표를 기준으로 합니다. 없는 값은 추측해서 채우지 않습니다. 연결표는 제품 위치를 정할 뿐 시험 정답을 정하지 않습니다. 화면이 바뀌면 유지보수가 필요합니다.

Inventory 성공은 제품 시험 PASS가 아닙니다. Candidate Trial에서 실제로 조작하고 화면·내부값과 TC 기대결과를 비교합니다. 임시 작업 폴더는 OS 권한 격리를 제공하는 보안 샌드박스가 아닙니다.

### 시험·복원·증거

| 유형 | 실행 책임 |
|---|---|
| 조회 전용 | 불필요한 상태 변경·복원 없이 요청한 값 확인 |
| 값 변경 | 준비 전 상태 기록 → 준비·본 시험 → 복원·확인 |
| 변경 차단 | 명시된 금지 동작과 유지할 상태를 확인. 실제 변경과 준비 중 변경은 복원 |
| 복원 실패 | 증거를 남기고 같은 환경에서 후속 시험을 계속하지 않음 |

차단 시험이라는 이유만으로 모든 관제점 불변이나 UI 비활성을 추가하지 않습니다. 요청이 무엇을 금지하고 무엇을 유지하라는지 구분합니다. 제품 합격 조건과 복원 비교는 별개입니다.

시작 조건은 본 시험 직전에 실제 값으로 확인합니다. 맞지 않으면 제품 결함으로 판정하지 않고 준비·자동화 문제로 보고합니다. 준비 전 자동 기록에 별도 제품 기대값을 억지로 요구하지 않습니다.

새 공통 복원은 다섯 관제점의 관련 화면·내부값을 확인합니다. 과거 HVAC 복원이나 승인 TC에 없는 검사를 자동 추가·재승인하지 않습니다. 최신 재시험과 원래 증거도 분리합니다.

V2 제품 패널은 적용 전 편집값을, 적용 후 성공·차단 여부와 관계없이 선택 장비의 실제값을 표시합니다. 복수 선택에서는 마지막 선택 장비가 표시 기준입니다. 이는 제품 정책이며 시험 기대값을 실제 구현에 맞춰 자동 변경하는 규칙이 아닙니다.

## 5. 공통 검토와 진행·중단

새로 생성하는 온도 자동화의 준비·본시험·복원은 같은 조절 함수를 사용한다. 목표 도달은 성공적으로 반환하고, 이미 거친 표시값이 다시 나타나거나 표시를 읽지 못하면 실행 오류로 중단한다. 최대 조작 횟수는 기존 40회로 유지한다. 준비·복원은 정확한 목표 도달을 요구하며 표시가 변하지 않아도 성공으로 처리하지 않는다. 본시험의 범위 제한 요청은 기존처럼 표시값이 더 이상 변하지 않으면 조작을 종료하고 TC의 별도 기대결과 검사로 판정한다. 반복 중단은 제품 결함 확정·지원 불가 확정·합격이 아니며 기존 실행 오류/HOLD 경로를 따른다. 특정 소수점이나 1°C 단위를 하드코딩하지 않고 SRS·기대값·과거 승인 코드/기록도 변경하지 않는다.

조작·관찰 중 예외가 나고 최종 캡처가 없으면 복원 전에 오류 화면 캡처를 시도한다. 기존 캡처는 덮어쓰지 않으며 캡처 자체가 실패하면 `EVIDENCE_CAPTURE_FAILED`를 남기고 원래 예외를 다시 전달한다. 캡처 성공은 시험 PASS가 아니고, 캡처 실패도 복원 생략 사유가 아니다. 기존 실행 오류 분류와 승인 차단은 유지한다.

| 상황 | 처리 |
|---|---|
| A1·A2의 보완 가능한 초안 오류 | 단계별 최대 1회 재작성 후 다시 검사 |
| 신규 연결표 A3 오류 | 같은 연결을 AI에 재작성시키지 않고 사유 기록 |
| 유효한 검토의 근거 부족 판정 | 해당 단계의 허용된 보완 경로. 한도 초과 시 중단 |
| 판단 불확실 | REVIEW, 다음 단계로 추측 인계하지 않음 |
| 없는 ID·검토 항목 누락 등 검토 응답 오류 | ERROR. 잘못된 피드백으로 TC를 재작성하지 않음 |
| API/내부 오류 | ERROR. 이후 후보의 추가 호출 중단·미실행 기록 |
| 정상적인 미지원 제외 | 사유 보존. 독립된 다른 후보·보고는 가능 |
| 제품 기대결과 불일치 | 실패 증거 유지. 기대값 수정으로 PASS로 바꾸지 않음 |

공통 검토 모델은 제공된 근거 ID를 선택하며 프로그램이 원문 전체를 연결합니다. 누락·중복·변조·없는 ID는 검사하지만 유효한 ID의 의미가 맞는지는 모델 판단이므로 오판할 수 있습니다. 응답 배열 순서가 바뀌어도 항목 ID로 대응하며 과거 기록은 당시 계약을 따릅니다.

새 응답 스키마는 원본 ID 허용 목록과 형식 한도를 적용합니다. 한도 초과 시 목록을 잘라서 보내지 않고 중단합니다. SHA-256으로 입력·산출물·검토 기록을 연결하고 후속 인계·승인에서 다시 확인합니다.

SDK 통신 자동 재시도는 0회입니다. 새 후보 1건의 재작성 없는 정상 경로는 생성 2회와 검토 3회이며, 후보 수·재작성에 따라 늘어납니다. 실제 호출 상한은 실행 전에 별도로 승인받습니다. CLI 전체에 보편적인 전역 예산 기능이 있다고 설명하지 않습니다. 저장 기록 재검사는 모델 호출과 다릅니다.

## 6. 실행 집계와 Agent 4 보고

완료 후보 증거와 관련 기존 TC를 검증합니다. 환경 점검을 제품 TC 성공률에 섞지 않고 후보·기존 회귀·제외·미실행을 구분합니다. 후보가 없거나 모두 제외됐다는 사실만으로 전체 요청을 PASS 처리하지 않습니다.

Agent 4의 우선 분류는 환경 문제 → 준비 불일치 → 복원 실패 → 제품 기대값 불일치 → 기술 오류/시간 초과 → 미실행입니다. 제품 불일치와 복원 실패가 함께 있으면 복원 문제로 보류하되 제품 관찰도 보존합니다.

| 표기 | 의미 |
|---|---|
| 제품 시험 PASS | 해당 TC의 기대결과를 실행에서 확인 |
| Checkpoint PASS | 해당 자동 검사 통과. 사람 승인 아님 |
| 최종 PASS | 보고·증거 및 해당 실행 범위의 조건 충족. 공식 등록 아님 |
| HUMAN_REVIEW | 제품 불일치 후보 또는 남은 확인 사항에 대한 사람 판단 |
| HOLD | 환경·자동화·증거 부족·미실행 등으로 판정/진행 보류 |

로그의 실제 결과 행을 판정에 사용하고 실패 출력에 함께 찍힌 소스 문자열을 제품 실패로 오인하지 않습니다. 보고서는 원본 실행·후보·기존 TC·분석 해시를 다시 확인합니다.

신규 컴파일 코드의 본시험 관찰 로그 계약은 `assertion-observations-1.0`입니다. `QA_ASSERTION_OBSERVED`에는 Run/TC, 계획상 장비·검사 정의, 실제 읽은 값, 기대값 일치 여부가 들어갑니다. 대기 중 모든 표본이 아니라 마지막 관찰 시도의 기록을 남깁니다. 본시험 관찰이 끝나면 `QA_ASSERTIONS_COMPLETE`를 남기며 이것은 제품 PASS나 복원 성공을 뜻하지 않습니다. 중간 읽기 오류에는 부분 기록만 남을 수 있습니다. 기존 준비·복원 검사와 실패 시 중단 규칙은 유지합니다. 원래 관찰값을 기대값으로 바꾸거나 P2 점수를 P1 판정에 반영하지 않습니다.

P2는 계획과 이 실행 기록을 대조하고, 생성기의 실제 읽기 위치·컴파일 동작은 로컬 회귀검사로 별도 확인합니다. 기록 자체는 같은 실행기가 남긴 증거이며 외부 독립 관찰의 보장은 아닙니다. 과거 Run·등록 코드는 변경하지 않으므로 해당 기록이 없는 과거 실행의 새 항목 점수를 추정하지 않습니다.

Slack·Notion은 기본 미리보기입니다. 실제 게시에는 별도 설정·명시적 전송이 필요합니다. Notion 상세 TC는 검증된 명세를 연결하며, 게시를 공식 자산 승인으로 취급하지 않습니다.

## 7. 사람 승인과 자산 관리

승인 가능 여부와 승인 전 재검증은 `validation_manifest.json`의 후보 원본 연결을 함께 사용한다. 단일 CLI의 Run 루트와 통합 실행의 `agent3_candidates/<tc_id>`를 지원하며, 해당 TC·Run·단계·해시 및 다중 후보 요약 연결을 대조한다. 파일을 검색해 대신 선택하거나 단일/다중 기록이 섞인 경우를 추정하여 승인하지 않는다. 원본 연결 필드가 없는 과거 다중 형식은 기존 위치를 읽되 기존 전체 인계 검사를 그대로 적용한다. 경로 해석은 위치 확인일 뿐이며 최종 보고·실행/복원 증거·현재 제품 및 사람의 추가/대체 선택 검사를 생략하지 않는다.

사람은 결과, TC·코드, 필요한 SRS 변경 전후 문구와 미결 사항을 검토합니다. 승인·미등록·보류를 기록하며, 미등록·보류는 기존 기준을 바꾸지 않습니다.

- 신규 공식 TC 등록은 최종 결과·CP·실행 증거·TC/코드/제품 연결을 확인한 뒤 진행합니다.
- SRS 제안이 있으면 별도 동의가 필요합니다. 기존 TC만 사용한 경우에는 새 TC 등록 없이 SRS_ONLY 승인이 가능합니다.
- 제품 HTML이 달라졌다면 승인 전 재시험이 필요합니다. 재시험은 모델 생성이 아니라 저장 후보의 현재 제품 확인입니다.
- 재시험 시작 기록을 먼저 남기고 현재 파일과 일치하는 최신 결과를 과거 PASS보다 우선합니다. 미완료·실패는 승인 근거가 아닙니다.
- 같은 Run·TC 중복 승인은 기존 기록을 반환합니다. 이미 승인된 자산을 보류 클릭으로 취소하지 않습니다.
- 공식 목록에 등록된 후보의 실행별 승인 기록이 없거나 보류 등 다른 상태이면 새 판단을 저장하지 않고 두 기록을 확인하도록 중단합니다. 등록 사실을 미등록/보류로 다시 쓰거나 실제 수행하지 않은 대체를 기록하지 않습니다. 기록의 자동 복구·승인 취소는 하지 않습니다.
- 후보 TC 비교는 다섯 관제점에 같은 처리를 사용한다. 이번 TC와 기본/승인 TC의 근거·준비·절차·기대결과·복원을 표시하고, 같은 요구사항 ID에 연결된 TC를 우선 배치한다. 나머지 TC와 대체 이력도 펼쳐 볼 수 있다. 요구사항 연결 누락이나 복합 시험 때문에 관련 TC가 나머지 목록에 있을 수 있으므로 의미상 중복을 자동 확정하지 않는다. 기본 TC는 저장된 검증 범위 요약만 표시하며 없는 상세 절차를 생성하지 않는다.
- 사람은 ADD(기존 유지·추가), REPLACE(직접 선택한 기존 TC 대체), DECLINE(등록하지 않음), HOLD(보류)를 선택한다. 대체·미등록·보류 사유는 필수다. 미등록·보류는 SRS·공식 목록을 바꾸지 않으며 SRS 개정만 승인하는 우회가 아니다. 별도 SRS_ONLY 경로는 기존 동작을 유지한다.
- REPLACE는 등록 조건·SRS 동의를 그대로 확인하고 검토한 비교 목록의 SHA-256과 현재 목록을 대조한다. 화면은 ADD에도 비교 해시를 보내며, 기존 ADD 함수 호출의 선택 인자는 호환을 유지한다. 새 공식 TC를 만들면서 registry의 supersessions에 선택한 기존 TC·대체 TC·사람·사유·시각·비교 해시를 기록한다. 기존 TC/코드 파일은 수정·삭제하지 않는다.
- 새 Agent 2 카탈로그와 저장 Snapshot 재구성은 대체된 기본·승인 TC를 제외한다. 과거 Snapshot 자체는 바꾸지 않는다. 대체 전 선택을 저장한 Run이 다시 회귀를 실행하려 하면 현재 대체 기록을 확인해 중단하고 새 Run을 안내한다. 이미 시작된 개별 시험을 실시간 취소하는 기능은 아니다. 같은 Run·후보 재승인은 기존 결정을 반환하며 자동 교체나 대체 취소 기능은 없다.
- 일반 오류·중단에 대한 보상 복구는 있으나 전원 종료·강제 종료·복구 중 추가 장애까지 원자성을 보장하지 않습니다.
- 공식 자산과 과거 실행 원본은 촬영을 위해 원복하거나 해시만 다시 맞추지 않습니다.

구현: [승인 UI·처리](../src/qa_pipeline_ui.py). 현재 공식 자산·실제 승인 기록과 최신 검증 범위는 인계 문서에서 구분합니다.

## 9. 시연과 공개 자료

정상 변경·관련 기존 TC, 제품 불일치, 미정 조건 분리의 세 사례를 비교합니다. 기존 TC는 요청의 실제 범위에 따라 선택하며 특정 관제점의 TC를 항상 실행하도록 고정하지 않습니다.

MED/HIGH의 과거 정상·승인 기록을 현재 신규 등록처럼 반복하지 않습니다. 새 실행에서 이미 등록된 기준을 재사용하는 것과 과거 등록 장면 조회를 구분합니다. 잠금 실패는 당시 요청과 제품의 비교이며 현재 기본 SRS 전체의 결함 확정으로 확대하지 않습니다.

포폴은 입력 → Agent별 결과 → 실제 시험 → 보고 → 사람 판단을 간단히 설명합니다. 내부 연결표·계약 버전·검사 함수는 이 기술 문서에서 다룹니다. 사용자 검토 전 공개 페이지와 영상을 갱신하지 않습니다.
