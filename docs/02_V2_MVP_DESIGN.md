# V2 MVP 설계

## 1. 목적

V2는 프로젝트 1의 4-Agent QA 절차를 실제 모델 호출과 실행 증거로 연결합니다. 새 QA 방법론이나 범용 변경관리 플랫폼을 만드는 것이 목적이 아닙니다.

## 2. V1 정렬 원칙

| 분류 | 내용 |
|---|---|
| 유지 | 3단계 QA 기준, Requirement 추적성, TC 독립성, 조건부 UI·내부 이중 검증, 원인 분류 |
| 추가 | Agent 1~3 실제 구조화 모델 호출, 단계 인계 검증, 제한된 코드 생성, 실제 시험 증거 |
| 내부 처리 | SHA-256, 입력 Preview, 정적 검사, 증거 완전성, 로컬 실제 Run 조회 화면 |
| 제외 | 과거 일괄 Agent 3 모델 호출, 복잡한 Batch 인계 호환, 중단 Run 재개 UI, 정식 자산 자동 등록 |
| 후순위 | ADDED·DELETED, Full Regression, Self-Healing, 다중 모델 평가 |

V1에서 V2 독립 실행에 필요한 가상 중앙제어 HTML, Pytest 설정, 사람이 작성한 기존
회귀 테스트와 실행 설정만 `product_baseline/`에 복사했습니다. Agent 3는 V2 HTML을
시험 대상으로 사용하고, 관련 기존 회귀는 같은 폴더의 테스트 코드에서 선택해 임시
Workspace에서 실행합니다. 제품 제어 동작은 유지하고, 팀장·Agent 버튼에는 V2 Run
증거 조회 패널만 추가했습니다. Project1 원본에는 적용하지 않습니다.

## 3. 사용자 흐름

~~~text
변경 요청
  → 요구사항 분석
  → 기존 TC 대조와 변경분 TC 설계
  → 신규·수정 후보 TC 자동화·시험
  → 관련 기존 회귀 실행
  → 결과 분류·최종 보고·외부 전달
  → 사람의 최종 확인
~~~

Checkpoint와 해시 검사는 각 화살표 안에서 자동으로 수행합니다. 사용자가 별도 승인 단계를 반복하는 구조가 아닙니다.

## 4. 단계

### Agent 1

변경 전·후, 관련 요구사항 영향, 확정 조건, 제외 범위, 정보 부족을 구분합니다. 현재 자동화 지원 여부는 영향도 판단 근거로 사용하지 않으며, 확정된 제품 조건을 Agent 2에 빠짐없이 전달합니다.

- PROCEED: 확정 범위 전체를 계속 진행
- PARTIAL_PROCEED: 확정 범위만 계속 진행하고 나머지는 보고
- WAITING_FOR_USER: 시험 범위를 확정할 수 없어 현재 Run 중단
- BLOCKED: 입력 또는 근거가 계약과 충돌해 중단

중단된 Run을 이어 붙이는 별도 재개 기능은 MVP에 포함하지 않습니다. 내용을 보완한 새 변경 요청으로 다시 실행합니다.

### Agent 2

확정된 범위를 기존 사람 작성·자동화 TC 카탈로그와 먼저 대조합니다. 카탈로그에는 V1 기준 회귀와 사람 승인 Registry의 공식 TC가 함께 들어가며, 공식 자산은 파일·SHA-256·구조화 TC를 확인한 뒤 Run Snapshot으로 고정합니다. 카탈로그는 Requirement ID뿐 아니라 실제 검증 동작을 제공하며, 해당 동작이 확정 조건을 그대로 검증할 때만 기존 TC로 선택합니다. 실제로 새로 필요하거나 기대 결과·절차가 바뀌는 부분만 변경 검증 후보로 만들고, 재사용할 수 없는 기존 TC는 선택하지 않은 이유를 남깁니다.

Agent 1은 Condition마다 `변경`·`유지`·`보조_근거`를 구조화합니다. Agent 2가 Condition과 카탈로그 검증 동작을 대조해 명시적으로 선택한 기존 TC만 사용하며, Requirement ID만으로 회귀를 자동 보충하지 않습니다. 기존 TC가 변경 후 조건을 전부 검증하면 신규 후보 없이 기존 TC만 실행할 수 있습니다.

각 TC는 다음을 가져야 합니다.

- 요구사항·확정 조건 추적
- 공통 QA 기준
- 도메인 QA 기준
- 기능 Requirement
- 독립 실행을 위한 초기 조건과 복원
- 필요할 때 UI·내부 상태 이중 검증

TC는 입력값 하나마다 나누지 않고 하나의 관제점·업무 규칙을 기준으로 묶습니다. 같은 범위 규칙의 하한·상한이나 같은 비활성 규칙을 공유하는 입력 조건은 한 TC에 둘 수 있습니다. 독립 조건은 중간 초기화를 명시하고, 순차 전환 자체가 검증 목적이면 승인된 전환 순서를 유지합니다. 각 기대 결과는 어떤 단계 직후 판정하는지 연결하며, 서로 다른 UI 관찰값은 같은 TC 안에서도 별도 기대 결과로 둡니다.

불명확한 범위는 TC로 만들지 않고 최종 보고로 전달합니다.

MODIFIED·UPDATE_REQUIRED Requirement는 현재 SRS 인수 기준, 제안 인수 기준, 근거 Condition과 사유를 `SRS_개정_제안`으로 함께 만듭니다. CP2는 대상 누락·중복·현재 원문 불일치·근거 불일치를 차단하며, 이 제안은 실행 결과와 Agent 4 사람 검토까지 전달됩니다.

### Agent 3

신규·수정이 필요한 변경 검증 후보만 한 건씩 독립 처리합니다. 관련 기존 회귀는 Agent 3에서 다시 구현하지 않습니다.

1. 해당 TC의 자동화 가능 여부 확인
2. 필요한 UI와 읽기 가능한 상태만 확인
3. AI가 동작·검증 계획 생성
4. CP3가 TC 의미·값·조건별 검증 시점 보존 여부 검사
5. 허용 목록 컴파일러가 Playwright Python 생성
6. 원본과 분리된 위치에서 한 번 시험
7. 실행 결과와 증거 저장

처음 보는 유사 UI는 안정적인 Selector와 상태를 제한적으로 조사합니다. 기능명이 처음 등장했다는 이유로 제외하지 않고 관찰된 공통 클릭·입력·선택·체크·상태 읽기로 구현 가능한지 먼저 판단합니다. 지원하지 않는 기술이 실제로 필요하면 그 TC만 제외하고 다음 TC를 계속합니다.

기존 중앙 관제 온도·모드 묶음 TC의 초기값이 요구사항으로 고정되지 않았으면 컴파일러가 실행 직전 `mode`·`setTemp`를 저장합니다. 조건 실행 후 저장값으로 복원·적용하고 실제 내부 상태가 원래 값과 같은지 확인합니다. 이 복원은 관찰된 V1 온도·모드 인터페이스에만 적용하며 일반 기능의 내부 값을 임의로 쓰지 않습니다.

### 변경 검증·기존 회귀

Agent 3 완료 후보를 현재 CP3·컴파일러 기준으로 다시 확인합니다. Agent 2가 기존 TC 카탈로그와 조건을 대조해 선택한 영향 범위의 기존 TC만 중복 없이 실행합니다. 신규 후보가 필요 없거나 모두 자동화 제외돼도 Agent 3 요약을 남기고 환경 점검·선택된 기존 회귀·Agent 4 보고를 계속합니다. 역사적 Run은 Requirement 기반 선택을 호환 경로로 읽습니다. 환경 사전 점검이 실패하면 기존 회귀는 실행하지 않습니다.

### Agent 4

생성형 API를 호출하거나 테스트를 재실행하지 않습니다. 저장된 결과를 제품 불일치 후보, 자동화 실행 문제, 환경 문제, 근거 부족, 미실행으로 분류합니다. 최종 권고는 PASS, HOLD, HUMAN_REVIEW 중 하나입니다. CP4와 최종 보고 해시가 통과한 경우에만 Slack·Notion Payload를 만들며 기본은 Dry-run입니다. `--send`에서만 Slack Webhook과 Notion TC-ID Upsert API를 호출하고 결과를 별도 증거로 저장합니다.

Agent 4는 JSON 보고와 함께 사람이 직접 작성할 `사람_최종_검토.md`를 생성합니다. 이 문서는 관련 TC·Requirement, 기대 결과, 실제 관찰, 증거 링크, 판정 선택지, 검토자·검토일·후속 조치란을 포함하며 별도 Manifest가 원본 최종 보고와 자동 생성 시점의 문서 SHA-256을 연결합니다. 사람이 작성란을 채운 뒤 문서 해시가 달라지는 것은 정상이며, 자동 갱신은 그 사람 판단을 덮어쓰지 않습니다.

수동 확인 TC도 제외 사유를 최종 보고에 남기며, 실패 로그에 없는 개별 기대 결과는 통과로 추정하지 않습니다. Notion은 `Run ID:TC ID`를 키로 써 실행별 결과를 보존하고 같은 실행 재전송만 갱신합니다.

### 중앙제어 Run 화면

V1 포트폴리오의 유형별 TC 표와 행 펼침 형식을 V2의 실제 저장 Run에 연결합니다. TC 유형, 제목, 실행 결과, 원인 분류와 전제조건·절차·기대 결과·복원·증거 파일명을 표시합니다. 유형은 설계값으로 유지하고 실패 원인과 혼합하지 않습니다. 기록에 없는 우선순위와 기존 회귀의 상세 명세는 추정하지 않습니다.

`qa_pipeline_ui`는 V2 HTML과 같은 호스트에서만 동작하는 로컬 연결부입니다. 기본 모드는
기존 `runs/`의 허용된 JSON만 읽어 Agent 1~4 상태와 사람 검토·외부 보고 기록을
요약합니다. 새 실행은 `--allow-live-run`으로 서버를 시작하고 화면에서 한 번 더 확인한
경우에만 허용된 `examples/change_request*.json`을 입력으로 Agent 1→4를 실행합니다.
임의 경로·쉘 명령·외부 보고 실제 전송은 받지 않습니다.
조회 시에는 CLI 후속 전송 기록도 반영합니다. 환경 점검 실패로 관련 회귀가 중단돼도
유효한 실패 결과가 저장됐으면 Agent 4 분석·보고를 계속하며 테스트 성공으로 표시하지 않습니다.

화면은 저장 결과 조회와 API 비용이 발생하는 새 실행을 별도 구역으로 표시합니다.
`--allow-asset-approval`을 명시하면 PASS 후보의 사람 승인·보류를 기록할 수 있습니다.
승인 전에는 최종 권고·CP3·CP4·검증 결과·증거와 현재 HTML SHA-256을 다시 확인합니다.
HTML이 바뀌었으면 기존 Run을 덮어쓰지 않고 후보 Python만 현재 화면에서 재실행해 새
Screenshot·Trace를 남깁니다. 승인된 TC와 자동화는 별도 `approved_assets/`에 원본 해시와
함께 등록하며 기존 사람 작성 회귀와 Run은 바꾸지 않습니다. SRS 개정 제안이 있으면 현재
후보의 Requirement·Condition에 연결된 제안만 표시하고, 별도 동의가 있어야 공식 자산과
기준 SRS를 함께 반영하며 변경 기록과 전·후 SHA-256을 남깁니다. 등록 도중 파일 복사나
기록에 실패하면 이 승인에서 바뀐 SRS·TC·자동화·Registry·임시 파일을 원상복구합니다.
이는 사람 판단 뒤의 제한된 등록이며, PASS를 자동으로 정식
자산이나 SRS로 만드는 기능은 아닙니다.

## 5. 코드 생성 경계

Agent 3 AI는 Python을 직접 생성하지 않고 구조화된 행동·검증 계획을 생성합니다. 컴파일러는 승인된 TC 값, 실제 확인한 Selector와 내부 필드, 허용 조작, Expected Result와 연결된 Assertion만 코드로 바꿉니다. 묶음 TC는 `동작 → 해당 결과 검증 → 필요한 초기화·전환 → 다음 동작 → 해당 결과 검증` 순서로 생성합니다.

제품별 기능명·모드·값·Selector는 공통 계약에 새로 고정하지 않습니다. 신규 기능은 관찰된 UI와 승인 TC를 공통 조작·검증에 연결하고, 기존 V1 전용 조작은 해당 기준 화면을 실제로 사용하는 TC의 호환 코드에만 포함합니다.

임의 JavaScript, 쉘 실행, 파일 변경, 외부 호출, Assertion 삭제·기대값 변경은 허용하지 않습니다.

## 6. 현재 제품 경계

- 중앙 관제 패널 조작만 지원합니다.
- 벽면 리모컨이나 별도 로컬 조작 경로는 없는 것으로 봅니다.
- 예시 변경 요청의 특정 기능·값을 일반 규칙으로 하드코딩하지 않습니다.
- Project1 원본은 읽기 전용 기준 자산입니다.
- Agent 3 시험 대상은 V2의 `product_baseline/virtual-controller.html`이며 Run 동안 읽기 전용으로 취급합니다.
- 기존 회귀 원본은 `product_baseline/tests/test_controller.py`이며 전체가 아니라 Agent 2가 선택한 허용 TC만 실행합니다.
- 임시 시험 위치는 원본 분리를 제공하지만 OS·컨테이너 보안 경계는 아닙니다.

## 7. 완료 기준

- 서로 다른 변경 요청이 서로 다른 Agent 1·2 구조화 결과로 이어집니다.
- 앞 단계 산출물이 다음 단계 입력으로 실제 사용됩니다.
- 승인 TC의 의미·ID·경계값이 자동화 계획과 코드까지 추적됩니다.
- 실행 가능한 여러 TC가 독립적으로 계속 처리됩니다.
- 불명확하거나 자동화할 수 없는 TC는 제외 사유와 함께 보고됩니다.
- 신규 자동화, 관련 기존 회귀, Agent 4 보고 수치와 증거가 일치합니다.
- 기존 TC를 신규 후보로 중복 생성하지 않고, 영향받는 기존 TC만 회귀로 선택합니다.
- 모든 확정 Condition이 변경분 후보 또는 관련 기존 TC 중 최소 한 곳에 연결되며 조용히 누락되지 않습니다.
- CP4를 통과한 최종 보고만 Slack·Notion 전달 대상으로 허용됩니다.
- 사람이 판단해야 하는 항목은 기대·관찰·증거와 작성란을 가진 최종 검토 문서로 제공됩니다.
- 기존 SRS·TC·자동화 원본을 덮어쓰지 않습니다.
- 팀장·Agent 버튼에서 표시하는 상태가 선택한 실제 Run 산출물과 일치하며 새 API 실행은 기본 잠금입니다.
