# 시나리오로 이해하는 V2 QA 처리 흐름

기준일: 2026-09-10

> 기존 TC가 있는 제품에 변경 요구사항이 들어오면, 변경분을 검증하고 결과를 사람이 판단해 다음 테스트 자산으로 남깁니다.

이 문서는 처음 읽는 사람도 프로젝트의 목적, 실행 시나리오와 중요한 분기를 이해하기 위한 안내입니다. 세부 검사 규칙은 [Agent·Checkpoint 명세](03_AGENT_AND_CHECKPOINT_SPEC.md)에 있습니다. 아래 예시의 기능명·값은 설명용이며 공통 실행 규칙에 고정하는 값이 아닙니다.

## 1. 먼저 알아둘 용어

| 용어 | 쉬운 설명 |
|---|---|
| SRS | 제품이 어떻게 동작해야 하는지 정리한 요구사항 문서 |
| TC | 사전조건·조작 순서·기대 결과를 가진 테스트케이스 |
| 기존 TC / 베이직 TC | 이미 관리하고 있는 테스트 자산. V1 기준 TC와 사람이 승인한 V2 공식 TC를 포함 |
| 신규·수정 후보 TC | 이번 변경을 검증하려고 만든 TC. 시험에 통과해도 공식 등록 전에는 후보 |
| 관련 회귀 | 이번 변경과 관련 있는 기존 TC를 다시 실행해 기존 동작을 확인하는 것 |
| Checkpoint / CP | Agent 산출물의 근거·구조·값·인계를 검사하는 자동 확인 단계 |
| Run | 변경 요청 한 번을 처리하며 만든 분석·TC·자동화·실행 증거·보고서의 묶음 |
| Candidate Trial | 새로 생성한 자동화 후보를 원본과 분리된 임시 위치에서 실제 시험하는 것 |

현재 제품 조작 범위는 가상의 중앙 관제 패널입니다. 실제 장비 통신이나 벽면 리모컨 조작을 검증하는 프로젝트로 설명하지 않습니다.

## 2. 기본 시나리오는 하나입니다

```text
기존 SRS + 기존 TC + 변경 요구사항
  → Agent 1: 무엇이 바뀌고 무엇을 확인할지 분석
  → CP1: 입력 근거와 전달할 조건 확인
  → Agent 2: 기존 TC 대조, 필요한 변경분 TC 설계
  → CP2: QA 기준·기대 결과·추적성·기존 TC 선택 확인
  → Agent 3: 신규·수정 후보의 자동화 계획·코드 생성과 시험
  → 환경 점검 + 관련 기존 TC 실행
  → Agent 4 / CP4: 결과 분류·증거와 집계 확인·보고
  → 사람: 결과 검토, SRS 개정·공식 TC 등록 승인 또는 보류
  → 승인 자산은 다음 Run의 기존 TC 대조에 사용
```

Agent 1·2는 실제 모델이 구조화된 분석과 TC를 작성합니다. Agent 3에서는 실제 모델이 조작·검증 계획을 만들고, 허용 목록 기반 컴파일러가 Playwright Python 코드를 생성합니다. Agent 4는 생성형 AI가 아닌 규칙 기반 분석기입니다.

기존 TC는 이미 PASS했다는 이유로 항상 건너뛰지 않습니다. 변경과 관련 있고 검증 동작이 그대로 유효하면 다시 실행합니다. 반대로 관련 없는 기존 TC를 전부 실행하는 Full Regression은 현재 범위가 아닙니다.

## 3. 포트폴리오에서 보여줄 사례

| 사례 | 입력과 처리 | 보여줄 의미 | 증거 상태 |
|---|---|---|---|
| ① 명확한 변경 요구사항 | MED 표시 변경은 신규 TC로, 유지되는 HIGH 동작은 기존 TC로 검증 | 변경분 생성과 기존 자산 재사용 | 최신 실제 API·브라우저 실행 성공 |
| ② 일부 기대 결과 누락 | 확정 범위는 진행하고 분리 가능한 불명확 범위는 제외·보고 | 없는 기대값을 임의로 채우지 않도록 통제 | 포폴용 실제 실행 증거 추가 확보 필요 |
| ③ 제품 동작 불일치 | 잠금 시 온도 버튼 비활성화 요구와 실제 활성 상태의 차이를 보고 | 실패 증거 보존과 원인 영역 분류 | 과거 실제 실행 공개 증거 있음 |
| ①의 후속: 공식 등록 | 사람이 PASS 후보를 검토해 공식 TC·자동화로 등록하거나 보류 | 자동 통과와 사람의 자산 승인 구분 | 기능과 기존 HIGH 승인 기록 있음. 최신 MED는 승인 전 |

### 사례 ①: 명확한 변경과 기존 TC 재사용

변경 요청은 다음 내용을 담았습니다.

- 오류와 잠금이 없는 단일 장비를 중앙 관제 패널에서 조작합니다.
- MED 풍량 적용 직후 카드에 `중풍`이 표시되고, 같은 시점에 내부 `fanSpeed=MED`여야 합니다.
- 기존 HIGH의 `강풍` 표시와 내부 `fanSpeed=HIGH`는 유지합니다.
- LOW 풍량 시작 상태를 확인하고 시험 후 LOW로 복원합니다.

| 단계 | 실제 처리 |
|---|---|
| Agent 1 | MED 변경과 HIGH 유지 조건을 분석. 첫 응답에서 대상 사전조건의 전달 누락이 CP1에 걸려 1회 재작성 |
| Agent 2 | MED 후보 1건 생성, 기존 HIGH 공식 TC `TC-V2-001` 선택 |
| Agent 3 | MED 적용 한 번 뒤 화면·내부 값을 함께 확인하고 LOW 복원 검사. 첫 계획·시험 통과 |
| 변경 검증 | 신규 후보의 검증된 시험 결과를 재사용하고 환경 점검·기존 HIGH를 실행 |
| Agent 4 | 제품 2건 + 환경 1건, 총 3건 PASSED. CP4와 최종 권고 PASS |
| 사람 판단 | SRS 개정 제안과 MED 후보 공식 등록은 승인 대기 |

실제 Run은 `RUN-20260910-101352-9C9021`입니다. 모델은 `gpt-5.6-terra / medium`, 호출은 Agent 1 두 번·Agent 2 한 번·Agent 3 한 번이며 누적 사용량은 43,419토큰입니다. 원본은 Git에서 제외되는 로컬 `runs/`에 보존합니다. 이 문서는 결과 요약이며 새 Run의 원본 증거 묶음을 공개한 것은 아닙니다. [기존 공개 MED 사례](../examples/results/agent1-agent2-agent3-agent4-medium-fan/README.md)는 9월 3일 당시 결과로 구분합니다.

이번 실행의 자동화 제외·정보 부족·오류 분류 항목은 0건입니다. 사람의 SRS 승인 확인 사항은 별도로 남아 있습니다. Slack·Notion은 미리보기만 생성했습니다. 제품 HTML의 실행 전후 해시는 동일하며, 제품을 고쳐 PASS로 만든 실행이 아닙니다.

### 사례 ②: 일부 기대 결과가 빠진 요구사항

설명용 예시는 “MED의 중풍 표시·내부 코드는 명확하지만, 함께 요청한 알림 색상 변경은 어떤 색상인지 빠진 경우”입니다. 이는 아직 실행한 결과가 아니라 시연을 위해 준비할 입력 예시입니다.

| 누락 상태 | 의도한 처리 |
|---|---|
| MED는 명확하고 알림 색상만 불명확하며 분리 가능 | MED 확정 범위는 진행. 색상 미정 내용을 제외된 정보 부족으로 최종 보고 |
| 변경 요청의 핵심 기대 결과 자체를 알 수 없음 | 요구사항 분석 단계에서 보류하고 필요한 정보 안내 |

일부 범위를 실행한 결과가 모두 PASS여도 정보 부족이 남으면 최종 권고는 사람 검토입니다. 이번 실행을 “요구사항 전체 통과”로 표현하지 않습니다.

사람이 요구사항을 보완하면 새 Run으로 확인합니다. 실제 모델이 기대한 분기로 처리하는지는 시연용 입력으로 실행해 확인해야 합니다. 자동 검사만으로 모든 자연어 누락을 탐지한다고 보장하지 않습니다.

### 사례 ③: 요구사항은 명확하지만 제품 동작이 다름

| 항목 | 잠금 사례의 실제 기록 |
|---|---|
| 요구사항 | 잠금 설정 시 온도 내림·올림 버튼 비활성화 |
| 관찰 | 내부 `locked=true`지만 두 온도 버튼은 활성 상태 |
| 제품 TC 결과 | 기대 결과 불일치로 실패 |
| 보고 | 제품 불일치 후보로 분류, 최종 권고 사람 검토 |
| 후속 판단 | 제품 수정·요구사항 확인 등은 사람이 증거를 보고 결정 |

[공개 잠금 Run](../examples/results/agent1-agent2-agent3-agent4-lock-disable/README.md)은 `RUN-20260827-114925-507176`의 당시 증거입니다. 총 4건 중 3건 통과·1건 실패이며 CP4는 PASS였습니다. Slack·Notion 실제 전송 기록도 이 과거 Run에 있습니다. 최신 MED의 미리보기와 혼동하지 않습니다.

**제품 TC가 실패했는데 CP4가 통과할 수 있습니다.** CP4는 제품을 정상이라고 승인하는 것이 아니라, 그 실패 결과와 보고의 증거·집계가 유효한지 확인하기 때문입니다.

## 4. 중요한 처리 분기

| 판단 지점 | 상황 | 처리 |
|---|---|---|
| 요구사항 | 기대 결과 명확 | TC 설계로 진행 |
| 요구사항 | 일부 불명확, 분리 가능 | 확정 범위만 진행하고 누락 내용 보고 |
| 요구사항 | 핵심 기대 결과 판단 불가 | 후속 실행 보류 |
| TC 대조 | 기존 TC가 변경 후 조건을 그대로 검증 | 기존 TC 재사용, 신규 후보 0건도 허용 |
| TC 대조 | 기존 TC의 기대 결과·절차로 변경분을 검증할 수 없음 | 신규·수정 후보 설계 |
| Agent 산출물 검사 | CP1·CP2·계획 CP3의 규칙 실패 | 해당 단계 최대 1회 재작성. 계속 실패하면 해당 인계 차단 |
| 후보 자동화 | 수동 확인 대상이거나 구현·시험을 신뢰하기 어려움 | 해당 후보 제외·사유 기록, 다른 후보와 관련 회귀·보고는 가능한 범위에서 계속 |
| 후보 시험 | 유효한 증거와 제품 기대값 불일치 | 실패 결과를 보존해 최종 분류로 전달 |
| 기존 회귀 실행 전 | 환경 점검 실패 | 기존 회귀 중단. 유효한 차단 결과가 있으면 Agent 4 보고 |
| 인계·증거 | 원본 변경·해시 불일치·필수 증거 누락 | 관련 후속 처리 차단. 손상된 결과를 제품 통과로 사용하지 않음 |
| 최종 판단 | 사람이 등록 조건을 충족한 후보 승인 | 공식 자산으로 저장 |

CP1·CP2는 뒤 단계가 공통으로 사용할 분석·TC 설계를 검사하므로 인계에 실패하면 후속 실행을 막습니다. Agent 3는 후보별 처리이므로 한 후보의 실패·제외가 다른 후보까지 무조건 중단시키지는 않습니다.

UI 확인은 Selector·표시·활성 상태·조회 가능한 내부 상태를 조사하는 단계입니다. 실제로 제품이 요구사항대로 동작하는지는 뒤의 브라우저 시험에서 확인합니다.

## 5. QA 기준은 TC에 어떻게 적용되나요?

| 기준 | TC에서 확인할 내용 |
|---|---|
| 공통 QA 기준 | 정상·예외·경계·복구 등 해당 업무 규칙에 필요한 관점 |
| 도메인 기준 | 올바른 장비 선택, 화면·내부 상태 정합성 등 해당 기능에 적용할 관점 |
| 기능 기준 | 이번 요구사항에 명시된 값·동작·표시 |
| 추적성 | 기대 결과가 어느 Requirement와 확정 조건에서 나왔는지 |
| 독립성 | 다른 TC가 먼저 실행돼야만 통과하는 구조가 아닌지, 필요한 준비·복원이 있는지 |
| 이중 검증 | 필요한 경우 같은 동작의 화면 표시와 내부 상태를 함께 확인하는지 |

기준 목록에 적었다고 그 관점의 모든 테스트를 수행한 것은 아닙니다. 실제 TC의 절차·기대 결과·자동화·실행 증거까지 연결해 확인합니다.

### TC를 묶을 때와 나눌 때

| 상황 | 구성 |
|---|---|
| 같은 관제점의 같은 범위 규칙에서 하한·상한 확인 | 한 TC의 여러 조건으로 묶을 수 있음 |
| 같은 비활성 규칙을 공유하는 여러 모드 | 한 TC에 조건별 조작과 판정을 둘 수 있음 |
| 앞 상태와 무관하게 각 조건을 시험해야 함 | 조건 사이에 초기화·재준비 |
| 특정 상태에서 다음 상태로 넘어가는 순서가 시험 목적 | 순차 전환 TC로 구성 |
| 업무 규칙이나 실패 원인이 서로 다른 기능 | 별도 TC로 분리 |

각 조건의 결과는 그 조건의 조작 직후 확인합니다. 하한을 조작하고 상한까지 바꾼 다음 마지막 상태만 보고 하한도 통과했다고 추정하지 않습니다. 하나의 동작에 대한 화면·내부 결과는 별도 기대 결과로 기록하되 같은 판정 단계에 연결합니다. 관찰값이 둘이라는 이유로 조작을 두 번 반복하지 않습니다.

현재 생성 코드는 기대한 관찰값이 반영되는지 약 2초의 재관찰 기한을 두고 확인하며 조작은 반복하지 않습니다. 각 브라우저 조회의 자체 대기 시간이 있으므로 모든 처리가 정확히 2초 안에 끝난다는 뜻은 아닙니다. 실제 장비의 응답 완료나 미변경 상태의 지속까지 검증하는 범용 계약도 아닙니다.

## 6. 재작성·실패·분류를 구분합니다

| 종류 | 의미 | 예시 |
|---|---|---|
| Agent 산출물 재작성 | 분석·TC·실행 계획이 자동 규칙을 어겨 다시 작성 | 입력 조건 누락, 기대 결과의 판정 위치 오류 |
| 제품 시험 실패 | 실제 관찰값이 TC의 기대 결과와 다름 | 잠금 상태인데 온도 버튼 활성 |
| 자동화 실행 문제 | 코드 실행·시간 초과·복원 등으로 결과 신뢰 확인이 필요 | 복원 실패 로그 |
| 공식 자산 승인 | 사람이 앞으로 재사용할 테스트로 채택 | PASS 후보의 명세·증거 검토 후 등록 |

모델의 재작성은 요구사항·기대값을 보존하도록 검사합니다. 제품 시험 실패를 없애기 위해 Assertion을 삭제하거나 제품 HTML을 수정하는 흐름이 아닙니다. 첫 실패 산출물과 재작성 기록도 보존합니다. 다만 자연어 의미의 모든 변경을 자동으로 차단한다고 주장하지 않습니다.

### Agent 4 최종 권고

| 결과 | 최종 권고 |
|---|---|
| 실행 대상 통과, 증거 유효, 자동화 제외·정보 부족 없음 | PASS |
| 유효한 실행에서 제품 기대값 불일치 | HUMAN_REVIEW: 사람이 검토 |
| 실행 결과가 통과했어도 자동화 제외·정보 부족이 남음 | HUMAN_REVIEW: 미확인 범위 검토 |
| 실행 결과에 환경·자동화 오류, 미실행 또는 증거 부족이 있음 | HOLD: 신뢰 가능한 판정을 위해 보류 |
| 제품 불일치와 복원 실패가 함께 있음 | HOLD: 복원 실패를 근거로 보류하고 제품 불일치 관찰도 보존 |
| CP4가 증거·집계 불일치로 통과하지 못함 | HOLD, 외부 전송 차단 |

앞 단계에서 자동화 실패 후보가 제외 목록으로 전달된 경우에는 최종 보고의 자동화 제외·사람 검토 경로를 따릅니다. 모든 기술 오류가 동일한 형태의 실행 결과로 전달되는 것은 아닙니다.

사전에 의도적으로 정한 범위 밖 항목은 정보 부족과 구분합니다. 예를 들어 단일 장비 시험에서 복수 장비를 범위 밖으로 정했다는 이유만으로 실패나 사람 검토를 강제하지 않습니다. 최종 PASS 역시 해당 실행 범위의 자동 권고이며 전체 제품 품질 보장은 아닙니다.

Slack·Notion은 기본적으로 전송할 내용만 만드는 미리보기입니다. 실제 전송은 별도로 명시한 경우에만 수행합니다. TC 유형인 정상·경계·예외와 실행 후 원인 분류도 서로 다른 정보입니다.

## 7. 베이직 TC에 포함할지는 사람이 결정합니다

1. 사람은 최종 보고서에서 신규 후보의 명세·기대 결과·실행 증거와 확인 사항을 검토합니다.
2. 시스템은 최종 PASS, 필요한 단계 검사·시험 통과, 코드·증거·현재 제품의 일치 등 등록 조건을 확인합니다. 제품이 달라졌으면 후보를 현재 제품에 재검증해야 합니다.
3. SRS 인수 기준의 개정이 필요하면 변경 전·후 문구를 확인하고 별도로 동의합니다.
4. 승인하면 공식 TC와 자동화를 저장하고, 검토자·메모·출처 Run을 등록 기록에 남깁니다. 보류하면 해당 후보를 새 공식 자산으로 등록하지 않습니다.
5. 다음 Agent 2 실행은 승인된 TC를 기존 목록에 포함하고, 이번 변경에 맞는 경우에만 재사용합니다.

공식 TC를 등록한다는 것은 V1의 기존 테스트 파일에 코드를 무조건 덧붙인다는 뜻이 아닙니다. V2의 `approved_assets/`에 별도로 관리하고, 다음 실행에서 기존 기준 TC와 함께 대조합니다.

신규 후보 없이 기존 TC만 실행한 Run도 조건을 충족하면 SRS 문구만 사람이 승인할 수 있습니다. 이때 TC·자동화를 새로 만들지 않습니다. 현재 승인된 HIGH 자산은 [공식 Registry](../approved_assets/registry.json)에 있으며, 최신 MED 실행에서 실제 재사용됐습니다. MED 후보는 아직 공식 등록하지 않았습니다.

사람 검토서의 판단란을 작성하는 것과 프로그램의 공식 자산 등록 처리는 별개입니다. 문서에 체크했다는 이유만으로 Registry가 자동 변경되지는 않습니다.

## 8. 포폴에서 어디까지 보여주면 되나요?

| 구성 | 내용 |
|---|---|
| 본문 | V1의 QA 기준 설명과 V2의 실제 실행 연결 |
| 주 영상 | 명확한 변경 → 신규·기존 TC 분리 → 실제 시험 → 결과 분류 → 사람 등록 판단 |
| 보조 사례 | 일부 누락과 제품 불일치의 처리 차이 |
| 상세 펼쳐보기 | 이 문서의 처리 분기·TC 구성·최종 권고 표 |
| 실행 증거 | 사례별 Run·일자·결과·실제 전송 여부. 설명 예시와 실제 결과 구분 |

포폴 공개를 위해 인터넷 API 실행 서버를 추가 운영할 필요는 없습니다. 로컬 실제 실행을 녹화하고, 대기 구간을 편집했다면 표시합니다. 공개 페이지나 HTML 직접 실행에서는 MED 풍량 정상 변경 1건의 저장된 V2 데모를 보여주며, Agent 결과와 승인 미리보기를 조작해도 API·제품·SRS·공식 TC 파일은 바뀌지 않습니다. 로컬 페이지의 실제 실행 버튼은 별도 자동화 브라우저에서 제품 복사본을 시험하게 하며, 방문자가 보는 카드가 그대로 자동 조작되는 구조는 아닙니다. 공개 데모와 로컬 실제 API 실행을 명확히 구분합니다.

현재 207건 자동 테스트는 파이프라인 코드의 검증 건수입니다. MED Run의 제품 2건·환경 1건과 합쳐서 제품 테스트 수로 소개하지 않습니다. 최신 MED는 CLI에서 실제 실행했으며, 페이지 버튼부터 시작한 최신 전체 API 실행과 누락 사례 시연은 별도로 확인해야 합니다. 과거 잠금 결과를 최신 코드 재실행으로 표현하지 않습니다.

사전조건 분류 지침과 자동 검사 사이의 해석 차이, 카드 전체 문구를 비교하는 복원 검사의 범위, 별도 SRS·자산 경로를 쓸 때의 페이지 실행 설정 전달 등은 후속 검토 사항입니다. 이번 문서 작성으로 해결된 것으로 표시하지 않습니다. 기존 TC 전용 SRS 승인도 임시 파일 기반 검증과 실제 공식 문서 승인을 구분합니다.

현재는 MODIFIED 변경, 관찰 가능한 중앙 관제 UI, 관련 기존 회귀 중심의 MVP입니다. 모든 자연어 오류·UI 기술·실제 장비 통신을 지원하거나 한 번의 성공으로 반복 안정성을 증명하지 않습니다. 반복 평가는 별도 프로젝트 2에서 다룹니다.
